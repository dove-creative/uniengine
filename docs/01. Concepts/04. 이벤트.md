# 이벤트

## 개요

- 이벤트의 개념을 정의하고, 객체 연결을 통한 이벤트의 전달 방식을 소개한다.
- 이벤트 전파 도중 새로운 수신자가 등록되거나 삭제될 때의 상황을 다룬다.
- 이벤트 전파 상황에서 발생할 수 있는 예외의 처리 원칙을 설명한다.

## 목차

1. 이벤트와 이벤트의 전파
2. 이벤트 전파 도중의 수신자 변경과 처리
3. 이벤트 전파 상황의 예외 처리 원칙
4. 결론

## 1. 이벤트와 이벤트의 전파

이벤트란 특정 시점에서 발생한 상태 변화를 나타내는 정보이다.

이벤트 전파는 발신자 객체와 수신자 객체 간의 연결을 통해,
발신자가 수신자에게 이벤트를 전달함으로써 이루어진다.

이벤트는 다음 두 가지 방식으로 전달될 수 있다.

### 1-1. 패시브 연결

패시브 연결은 정보 교환 후 연결이 즉시 해제되는 일회성 방식이다.

- 구현이 단순함
- 연결 관리 부담이 적음
- 반복 이벤트 발생 시 비효율적 (매번 연결 필요)

```csharp
void Run()
{
    var sender = new Sender();
    var listener = new Listener();

    sender.SendEvent(listener);
}

class Sender
{
    public void SendEvent(Listener listener) =>
        listener.OnEventOccurred();
}

class Listener
{
    public void OnEventOccurred() =>
        Console.WriteLine("Event occurred");
}
```

### 1-2. 액티브 연결

액티브 연결은 정보 교환 이후에도 연결이 유지되는 방식이다.

- 지속적인 이벤트 전파 가능
- 발신자가 원하는 시점에 이벤트 전달 가능
- 연결 유지 관리 필요

```csharp
void Run()
{
    var sender = new Sender();
    var listener = new Listener();

    sender.OnEventOccurred += listener.OnEventOccurred;
    sender.SendEvent();
}

class Sender
{
    public event Action OnEventOccurred;

    public void SendEvent() =>
        OnEventOccurred?.Invoke();
}

class Listener
{
    public void OnEventOccurred() =>
        Console.WriteLine("Event occurred");
}
```

### 1-3. 핸들을 이용한 이벤트 연결 관리

액티브 연결에서는 연결을 해제하려면, 일반적으로 연결을 생성한 객체에 다시 접근하여 `-=` 연산이나 별도의 해제 메서드를 호출해야 한다.

이때 연결을 생성할 때 함께 반환되는 작은 객체 하나에 '이 연결을 나중에 어떻게 해제할 것인가'를 담아 둘 수 있다. 연결을 생성한 쪽은 해제 방법을 이 객체 안에 넣어 반환하고, 연결을 사용하는 쪽은 그 객체만 보관했다가 필요할 때 해제를 요청할 수 있다.

UniEngine에서는 이러한 반환 객체를 `Handle`이라고 부른다. `Handle`은 연결 자체가 아니라 연결을 해제할 수 있는 권한과 방법을 담은 반환값이며, 생성 시점에 연결 해제에 필요한 동작을 내부에 저장하고 `Dispose()`가 호출되면 저장된 동작을 실행하여 연결을 해제한다.

- 연결 해제를 캡슐화
- 추가 접근 없이 연결 해제 가능
- 연결 생성 시점의 해제 방법을 함께 반환

```csharp
void Run()
{
    var sender = new Sender();
    var listener = new Listener();

    listener.Connect(sender);
    sender.SendEvent();
    listener.Disconnect();
}

class Sender
{
    public event Action OnEventOccurred;

    public IDisposable Subscribe(Action action)
    {
        OnEventOccurred += action;
        // Handle은 이 연결을 어떻게 해제할지를 기억하는 객체이다.
        return new Handle(() => OnEventOccurred -= action);
    }

    public void SendEvent() =>
        OnEventOccurred?.Invoke();
}

class Listener
{
    private IDisposable _handle;

    void OnEventOccurred() =>
        Console.WriteLine("Event occurred");

    public void Connect(Sender sender) =>
        _handle = sender.Subscribe(OnEventOccurred);

    public void Disconnect()
    {
        _handle?.Dispose();
        _handle = null;
    }
}

sealed class Handle : IDisposable
{
    private Action _disconnect;

    public Handle(Action disconnect) =>
        _disconnect = disconnect;

    public void Dispose()
    {
        _disconnect?.Invoke();
        _disconnect = null;
    }
}
```

위 예시에서 `sender.Subscribe(...)`는 단순히 구독만 수행하는 것이 아니라,
해당 구독을 해제하는 방법까지 담은 `Handle`을 함께 반환한다.
따라서 `Listener`는 이후 `Sender`를 다시 참조하지 않아도 `_handle.Dispose()`만으로
자신의 이벤트 연결을 안전하게 해제할 수 있다.

## 2. 이벤트 전파 도중의 수신자 변경과 처리

이벤트 전파 중에는 수신자의 추가 및 삭제가 발생할 수 있다.
UniEngine은 다음 원칙을 따른다.

- 추가된 수신자 → 다음 전파부터 적용
- 삭제된 수신자 → 즉시 제거

### 2-1. 수신자 추가 처리 원칙: 다음 전파부터 적용

#### 2-1-1. Snapshot 순회 정책 준수

- 순회 중 추가된 객체는 현재 순회에 포함되지 않음

#### 2-1-2. Rx와의 일관성 유지

- 이벤트 중 등록된 구독자는 이후부터 반영

### 2-2. 수신자 삭제 처리 원칙: 즉시 제거


#### 2-2-1. 객체 활동 원칙 준수

- 삭제의 무결성
  → 삭제된 객체는 영향 남기면 안 됨
- 활동의 존중
  → 다른 객체의 실행 영역 침해 금지

#### 2-2-2. 실제 문제 방지

- 이미 삭제된 객체 호출 방지
- 접근 오류 및 예외 방지

### 2-3. 이벤트 전파 원칙의 적용

#### 2-3-1. 초기화 → 갱신 → 삭제 객체 처리

- 등록 시: 다음 전파부터 이벤트 반영
- 안정적인 생애주기 유지

```csharp
class TimerController
{
    private readonly AdaptiveAction _eventQueue = new();
    private Timer _timer;
    private bool _creationRequested;

    public void Initialize()
    {
        _eventQueue.Add(() =>
        {
            if (!_creationRequested) return;

            _creationRequested = false;
            if (_timer is not null) return;

            _timer = new Timer(); // 이벤트 전파 중 등록
            _eventQueue.Add(_timer.Tick);
        });
    }

    public void RequestTimerCreation() =>
        _creationRequested = true;

    public void Tick() =>
        _eventQueue.Invoke();
}

class Timer
{
    public int RecordedTicks { get; private set; }

    public void Tick() =>
        RecordedTicks++;
}
```


#### 2-3-2. 즉시 반영이 필요한 객체

일부 객체는 등록 즉시 이벤트 반영이 필요함

예: 외부 상태를 추적하는 객체

- 등록 후 즉시 `Tick()` 호출

```csharp
class TrackerController
{
    private readonly AdaptiveAction _eventQueue = new();
    private StateTracker _tracker;
    private bool _creationRequested;
    private int _sourceValue;

    public void Initialize()
    {
        _eventQueue.Add(() =>
        {
            if (!_creationRequested) return;

            _creationRequested = false;
            if (_tracker is not null) return;

            _tracker = new StateTracker(() => _sourceValue);
            _tracker.Tick(); // 등록과 동시에 현재 상태 반영
            _eventQueue.Add(_tracker.Tick);
        });
    }

    public void SetSourceValue(int value) =>
        _sourceValue = value;

    public void RequestTrackerCreation() =>
        _creationRequested = true;

    public void Tick() =>
        _eventQueue.Invoke();
}

class StateTracker
{
    private readonly Func<int> _readValue;

    public StateTracker(Func<int> readValue) =>
        _readValue = readValue;

    public int Value { get; private set; }

    public void Tick() =>
        Value = _readValue();
}
```

#### 2-3-3. 삭제 시 즉시 중단

- 삭제 요청 발생 시 즉시 전파 중단
- 불필요한 호출 및 오류 방지

발신 이벤트 객체가 전파 도중 Dispose 요청을 받으면 그 요청을 즉시 기록한다. 실행 중인 수신자 콜백을 강제로 중단하지는 않지만, 해당 콜백이 반환된 뒤에는 다음 수신자를 호출하지 않고 필요한 정리를 수행한다. 정상적으로 시작한 전파가 이 과정에서 중단되는 것 자체는 예외가 아니다.

폐기 요청은 취소하지 않는다. 요청 이후 새 전파나 연결을 시도하면 폐기된 객체에 대한 요청으로 처리한다. 수신자 하나의 연결만 해제한 경우에는 그 수신자를 이후 호출에서 제외하고 다른 수신자에 대한 전파는 계속한다.

```csharp
class TimerController
{
    private readonly AdaptiveAction _eventQueue = new();
    private Timer _timer;
    private bool _creationRequested;
    private bool _deletionRequested;

    public void Initialize()
    {
        _eventQueue.Add(() =>
        {
            if (_creationRequested)
            {
                _creationRequested = false;
                if (_timer is not null) return;

                _timer = new Timer();
                _eventQueue.Add(_timer.Tick);
            }
            else if (_deletionRequested)
            {
                _deletionRequested = false;
                if (_timer is null) return;

                // 이벤트 전파 중 삭제
                _eventQueue.Remove(_timer.Tick);
                _timer.Dispose();
                _timer = null;
            }
        });
    }

    public void RequestTimerCreation() =>
        _creationRequested = true;

    public void RequestTimerDeletion() =>
        _deletionRequested = true;

    public void Tick() =>
        _eventQueue.Invoke();
}

class Timer : IDisposable
{
    private bool _isDisposed;

    public int RecordedTicks { get; private set; }

    public void Tick()
    {
        if (_isDisposed) throw new ObjectDisposedException(GetType().Name);
        RecordedTicks++;
    }

    public void Dispose()
    {
        if (_isDisposed) return;
        _isDisposed = true;
    }
}
```

## 3. 이벤트 전파 상황의 예외 처리 원칙

### 3-1. 이벤트와 예외 처리

UniEngine에서는 객체가 스스로 처리할 수 없는 예외가 발생할 경우, 예외 전파(Exception Propagation)를 통해 호출한 객체로 예외를 전달하는 것을 원칙으로 한다.

다만 다수의 수신자를 관리하는 이벤트 객체에는 예외 격리 원칙을 추가로 적용한다. UniEngine에서 이벤트 객체는 서로 캡슐화된 시스템 사이를 연결하는 역할을 수행한다고 취급되며, 한 수신자의 예외가 해당 수신자와 무관한 다른 시스템의 동작까지 중단시키지 않도록 안전성을 우선한다.

따라서 이벤트 객체는 각 수신자의 호출을 격리하고, 예외가 발생하면 해당 수신자를 제거한 뒤 Exception Handler에 보고한다. 보고가 정상 반환하면 나머지 수신자에 대한 이벤트 전파를 계속한다. 이 원칙은 연결 객체를 통한 수신과 Updated·Disposing·Disposed 같은 이벤트의 직접 구독에 모두 적용한다.

Exception Handler가 예외를 다시 던지면 이를 삼키지 않고 호출자에게 전파하며, 현재 이벤트 전파를 중단한다. 핸들러가 등록되지 않아 원래 예외가 재전파되는 경우도 동일하다. 예외가 빠져나가더라도 전파 중 상태를 복구하고, 폐기 요청이 있었다면 필요한 정리를 수행해야 한다.

#### 3-1-1. 처리 방식

예외 발생 시:

- 해당 수신자 제거
- Exception Handler에 보고
- 보고가 정상 반환하면 나머지 수신자에 대한 이벤트 전파 계속
- 보고가 예외를 던지면 현재 전파를 중단하고 호출자에게 예외 전달
- 전파 중 상태 복구와 필요한 정리는 정상·예외 종료 모두에서 수행

### 3-2. Disposed 이벤트 객체 처리

새 작업은 폐기 요청을 받은 시점부터 잘못된 사용을 드러내도록 예외를 발생시킨다. 정리 작업은 폐기 완료 상태로 전환되기 전까지 필요한 연결을 해제하며, 이미 폐기가 완료되었거나 연결이 제거된 경우에는 무시하여 반복 호출해도 안전하게 처리한다. IsDisposed를 제공하는 객체에서는 해당 값이 true로 전환된 시점을 폐기 완료로 본다. Disposed·OnDisposed 같은 완료 알림은 이 상태 전환 이후에 전달할 수 있다.

| 요청 종류 | 처리 방식 |
|----------|----------|
| 폐기 요청 이후 새 데이터 전파: Update·OnNext | ObjectDisposedException |
| 폐기 요청 이후 새 연결·구독 | ObjectDisposedException |
| 폐기 완료 이후 연결·구독 해제 | 무시 |
| 반복 Dispose | 무시 |
| 종료 후 반복 OnCompleted·OnError | 무시 |

폐기 여부는 비활성화 상태, 이벤트 필터, 연산자 처리보다 먼저 확인한다. 아직 폐기되지 않은 객체의 비활성화 상태는 기존 전파 제어 규칙을 따른다. TerminationMode는 스트림을 폐기하는 시점을 정하며, 폐기 후 요청 처리 방식은 바꾸지 않는다.

## 4. 결론

UniEngine의 이벤트 시스템은 다음 원칙을 따른다:

- 순회 안정성 (Adaptive)
- 생애주기 일관성
- 예외 격리 (Fault Isolation)
- 즉시 제거 (삭제 안정성)

이를 통해 안정적인 이벤트 전파 환경을 제공한다.
