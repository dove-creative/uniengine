# PhysicalSpace 구조 결정

PhysicalSpace의 위치, 공개 핸들과 물리 소스 전략, 이름과 수명 계약의 기준에 대한 결정 기록이다. 설계는 [PhysicalSpace](README.md)에 있다.

## 결정

| 항목 | 결정 |
| --- | --- |
| 물리의 위치 | 공개 핸들과 전략 인터페이스를 UniEngine.dll의 Infrastructure 모듈 03-M.4-PhysicalSpace에 둔다 |
| 공개 형식 | 물리 소스와 관계없이 공개 핸들 하나만 두고 공개 핸들이 소스별 전략을 사용한다 |
| 수명 상태 | 공개 핸들만 가지며 전략은 수명 상태를 갖지 않는다 |
| 유니티 | 유니티용 전략을 소스로 제공하고 유니티 프로젝트가 UniEngine.dll과 함께 컴파일한다. UniEngine.dll은 UnityEngine을 참조하지 않는다 |
| 공개 API의 이름 | 월드는 PhysicalSpace2D·PhysicalSpace3D이다. 그 밖의 공개 형식은 Uni 접두사를 유지하며 멤버 이름은 유니티 6을 우선하여 PascalCase로 쓴다 |
| 의미의 차이 | 유니티와 맞지 않으면 UniEngine 문서를 따른다 |
| 시점과 수명 | 공개 핸들의 상태 계약은 공통으로 두고 실제 시간 진행과 제거 시점은 물리 소스를 따른다 |

## 공개 핸들을 UniEngine.dll에 둔 이유

공개 핸들과 전략 인터페이스는 특정 물리 엔진을 참조하지 않는다. 물리 엔진을 아는 코드는 소스별 전략에만 있으므로 공개 API를 본체에 두어도 물리 소스를 교체할 수 있다. Core와 Services도 필요할 때 공개 핸들을 사용할 수 있다.

## 전략 패턴을 사용한 이유

도메인 코드는 공개 핸들 하나만 사용한다. 폐기 상태, 사용 거부, 알림 횟수와 이벤트 같은 공통 계약은 공개 핸들에서 한 번만 구현한다. 공개 추상 형식을 소스마다 상속하면 이 계약이 소스마다 어긋날 수 있다.

공개 핸들과 전략이 별개 객체이지만 수명 상태를 공개 핸들에만 두므로 두 객체의 폐기 상태를 맞추지 않는다. 대신 강체와 콜라이더마다 객체가 둘이 되고 호출 단계가 하나 늘어난다. 전략은 씬을 만들거나 얻을 때 정하고 바꾸지 않는다.

## 유니티용 전략을 소스로 두는 이유

유니티용 전략은 UnityEngine을 참조하므로 UniEngine.dll에 넣을 수 없다. 유니티 프로젝트가 직접 컴파일하면 유니티 버전별 이름 차이를 조건부 컴파일로 맞출 수 있다. 파일 전체를 조건으로 감싸 일반 dotnet 빌드에서는 빈 파일이 되게 한다.

공통 지침은 다른 프로젝트에 소스가 아니라 DLL로 전달하도록 정한다. 유니티용 전략은 일반 dotnet 빌드가 참조하지 않는 UnityEngine에 의존하므로 이 소스에만 예외를 둔다. UniEngine 본체는 DLL로 전달한다. 전략 인터페이스는 다른 어셈블리에서 구현할 수 있도록 공개한다.

## 시점과 수명을 물리 소스에 맡긴 이유

유니티의 물리 객체 파괴는 현재 Update 루프 뒤로 미루어지고, 시간은 유니티가 진행하며, 물리 씬은 유니티 Scene에 묶인다. 공개 핸들의 폐기 상태, 사용 거부, 재호출과 알림 횟수처럼 C# 객체에서 지킬 수 있는 계약만 공통으로 두고 실제 제거 시점은 소스별로 문서화한다.

## 후속 결정 사항

- 유니티 밖에서 사용할 물리 소스와 배포 구성을 정한다.
- 전략 인터페이스의 이름과 구성, 공개 핸들에서 소스의 고유 객체를 얻는 방법을 정한다.
- 유니티 프로젝트에 UniEngine.dll과 유니티용 전략 소스를 전달하는 형식과 지원할 최소 유니티 버전을 정한다.
- 공통 API의 확인 필요 항목, 여러 객체 상태의 묶음 전달과 Dispose하지 않고 버린 씬의 처리를 정한다.
