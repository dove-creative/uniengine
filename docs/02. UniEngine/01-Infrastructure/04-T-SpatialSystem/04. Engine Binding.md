# Engine Binding

엔진별 연결은 독립 월드를 소유하고 공통 생성·진행·질의·알림을 외부 엔진에 연결한다. 실제 충돌 판정과 운동 계산은 외부 엔진이 수행한다.

## 목차

- 소개
- 대리자와 상속
- Unity 월드 생성과 소유권
- 객체 생성과 등록
- 독립 설정과 진행
- 자동 알림
- 수명과 해제
- 실행 조건과 제한

## 소개

| 항목 | 설명 |
| --- | --- |
| 개요 | 공통 계약과 외부 엔진 사이의 생성·호출·값·식별·알림·수명을 연결한다. |
| 목적 | 공통 소비자가 엔진 선택과 native 객체 구조를 몰라도 독립 월드를 사용할 수 있게 한다. |
| 구현 | 엔진별 래퍼가 공통 클래스를 상속하며 역할별 Func·Action 묶음을 구성한다. |

현재 구현 범위는 CollisionSpace 공통 소스와 Unity 연결이다. PhysicalSpace와 공개 강체 기능은 미구현이다. Unity 2022.3을 기준으로 하며 Unity 6의 변경 API는 조건부 컴파일로 처리한다. Rapier 연결은 후속 범위이다.

## 대리자와 상속

| 묶음 | 내용 |
| --- | --- |
| `SpatialProperty<T>` | Read·Write 대리자 |
| `ColliderBindings2D/3D` | 자세·설정·유효성·해제, 선택적 IsActive·Prepare |
| `CollisionSpaceBindings2D/3D` | 유효성·질의·Subscribe·필수 World 묶음·해제 |
| `CollisionWorldBindings2D/3D` | Update·레이어 정책·기본 형상 생성 |

묶음은 생성 시 필수 대리자를 받는다. 별도의 전략 인터페이스 구현체는 요구하지 않는다. Subscribe는 공통 알림 수신자를 받고 해제용 Action을 반환한다. 공통 소비자는 이 연결을 직접 구성하지 않는다.

CollisionSpace2DUnity는 CollisionSpace2D를, CollisionSpace3DUnity는 CollisionSpace3D를 상속한다. BoxCollider2DUnity → BoxCollider2D → Collider2D와 같은 방식으로 구체 형상에 엔진 고유 접근을 더한다.

## Unity 월드 생성과 소유권

`new CollisionSpace2DUnity()`, `new CollisionSpace3DUnity()`가 각각 전용 Unity Scene을 만들고 `LocalPhysicsMode.Physics2D/Physics3D`를 지정한다. 기존 Scene·PhysicsScene을 받는 생성자는 제공하지 않는다.

- 소유한 Scene과 PhysicsScene2D/PhysicsScene은 어댑터 내부 자원이다. UnityScene·월드 Source를 공개 API로 제공하지 않는다.
- 기존 게임 씬의 오브젝트를 자동 탐색·이동·복제하지 않는다. 서로 다른 공간은 좌표가 같아도 객체와 물리 시간이 분리된다.
- 생성 객체에는 Collider·Rigidbody·내부 알림 중계만 둔다. Renderer와 시각 객체는 자동 생성하지 않는다.
- Scene은 실행 중 Hierarchy에 나타나는 실제 런타임 씬이다. 카메라·렌더러가 없는 물리 전용 월드이며 에디터용 PreviewScene은 아니다.
- 물리 객체에 `HideInHierarchy`·`DontSave` 계열 플래그를 설정하지 않는다. 이 플래그는 Unity의 [물리 씬 소속에 영향을 줄 수 있다](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/HideFlags.html). 내부 중계만 Inspector에서 숨긴다.

월드 생성과 사용은 Play Mode 또는 실행 중인 Player의 메인 스레드에서 수행한다. Edit Mode 생성은 `NotSupportedException`이다.

## 객체 생성과 등록

기본 객체는 공통 CreateBoxCollider·CreateCircleCollider·CreateSphereCollider·CreateCapsuleCollider로 생성한다. Collider마다 전용 GameObject를 만들며 공통 API에는 body 인자와 AttachedRigidbody를 제공하지 않는다. 접촉 알림에 필요한 native 고정 강체는 연결 코드가 구성한다.

| Unity 대상 | 선택되는 래퍼 | 공통 기반 |
| --- | --- | --- |
| 2D Box·Circle·Capsule | BoxCollider2DUnity, CircleCollider2DUnity, CapsuleCollider2DUnity | 기본 형상 |
| 2D Polygon·Edge | PolygonCollider2DUnity, EdgeCollider2DUnity | Collider2D |
| 3D Box·Sphere·Capsule | BoxCollider3DUnity, SphereCollider3DUnity, CapsuleCollider3DUnity | 기본 형상 |
| 3D Mesh·Terrain | MeshCollider3DUnity, TerrainCollider3DUnity | Collider3D |
| 그 밖의 Collider | Collider2DUnity, Collider3DUnity | 차원별 Collider |

`CreateUnityCollider<T>(pose = null)`은 Unity 전용 형상을 소유 월드 안에 생성한다. 구체 래퍼의 형식이 지정된 `Source`로 Polygon 경로, Mesh, TerrainData 등을 설정한다. 외부에서 할당한 Mesh·TerrainData 같은 자산은 래퍼가 파괴하지 않는다.

개발자가 직접 만든 native Collider를 월드에 넣고 Wrap으로 등록하는 기능은 제공하지 않는다. 공통 생성 API와 CreateUnityCollider가 만든 객체만 관리하며, native 객체와 핸들의 대응은 어댑터 내부 책임이다. 같은 객체의 질의 결과는 살아 있는 동일 핸들을 반환하고, Unity ID 외에 실제 객체 참조와 생존 구간을 확인한다. 공개 Wrap 진입점은 제거하였다.

시스템의 생성 API가 객체 등록과 자동 알림 연결까지 구성한다. 질의에 나타났다는 이유만으로 개발자가 직접 넣은 객체를 자동 등록하지 않는다. 시스템이 관리하지 않는 객체는 정상적인 질의 대상으로 인정하지 않으며, 오사용을 정상적인 빈 결과로 숨기지 않는다. 이 경우 InvalidOperationException으로 오사용을 알리며 자동 등록하지 않는다.

복잡한 형상 데이터와 native 구조 제약은 Unity 규칙을 따른다. CompositeCollider2D는 지원하지 않으며 생성을 NotSupportedException으로 거부한다. 지원하지 않는 이유와 만들 조건은 [TODO](TODO.md)를 따른다. 수동 등록과 월드 직접 조작을 허용하지 않는 기준은 [Rules](02.%20Rules.md), 공개 경로 제거와 검증 상태는 [ISSUES](ISSUES.md)의 SP-08을 따른다.

## 독립 설정과 진행

| 공통 기능 | Unity 연결 |
| --- | --- |
| `Update(deltaTime)` | 등록 핸들의 유효성을 점검하고 설정을 적용한 뒤 해당 PhysicsScene의 Simulate를 한 번 호출한다. |
| 레이어 충돌 행렬 | 기본 전체 허용, 대칭 32×32 정책. Collider includeLayers/excludeLayers와 우선순위로 적용한다. |
| 질의 필터 | 별도의 LayerMask·IncludeTriggers를 native 질의 인자로 전달한다. |

공통 설정이 사용하는 native 레이어 override와 내부 강체의 중력·고정 설정은 연결 코드가 관리한다. 공통 소비자는 자세를 명시적으로 바꾸며 운동 적분·힘·속도 API를 사용하지 않는다.

전역 `Physics.gravity`, `Physics2D.gravity`, `IgnoreLayerCollision`, 자동 시뮬레이션 모드, autoSyncTransforms는 변경하지 않는다. 전역 값을 잠시 바꾼 뒤 되돌리는 방식도 쓰지 않는다. 호출자는 자신의 루프에서 공통 Update에 시간을 전달한다. Unity의 FixedUpdate만으로 이 로컬 월드가 자동 진행되지는 않는다.

질의는 시간 진행이나 Transform 동기화를 추가하지 않는다. 자세 변경 후 질의의 관측 시점은 Unity의 동기화 규칙을 따른다. 보통 명시적 Update 뒤에 결과를 읽는다. Unity의 [SyncTransforms](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Physics.SyncTransforms.html)는 다른 씬에도 영향을 주는 전역 API이므로 공간별 동기화 기능처럼 노출하거나 개발자가 직접 호출해야 하는 월드 사용 절차로 요구하지 않는다.

## 자동 알림

소비자는 OnCollision·OnTrigger를 구현하거나 MonoBehaviour 중계를 에디터에서 직접 붙이지 않는다. 연결 코드가 등록 시 자동으로 알림 경로를 구성한다.

설정 적용 시점과 공통 알림의 기준은 [Rules](02.%20Rules.md)를 따른다. Enabled·IsTrigger는 다음 Update에 최종 설정을 적용하며, 비활성화로 끝난 기존 관계의 종료는 엔진이 알림을 제공하지 않아도 보장해야 한다. 허용되지 않은 직접 조작 등 외부 원본의 변경을 발견하면 다음 Update에서 관측한 상태를 보호 동작으로 반영하고, Dispose·외부 파괴는 Disposed로 통지한다. 공통 관계 처리는 소스에 반영했으며 SP-04·SP-05의 Unity 실행 검증은 남아 있다.

- 3D 접촉은 [Physics.ContactEvent](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Physics.ContactEvent.html)를 사용하며 등록 Collider의 providesContacts를 켠다. 이 이벤트는 Trigger를 포함하지 않는다.
- 2D 접촉과 2D·3D Trigger는 내부 MonoBehaviour 중계가 받는다. 중계는 Collider 전용 객체마다 하나씩 두며 그 객체와 함께 제거한다.
- native 알림은 순서대로 큐에 넣고 시뮬레이션 반환 후 Update 종료 전에 전달한다. Update 사이에 native가 보낸 알림도 다음 Update에서 전달한다.
- 전달 순서는 공간 → 쌍의 First → Second이다. 중복은 동일 쌍의 시작·종료 전이로 정리하고 같은 프레임 Exit→Enter는 유지한다.
- 콜백에서 객체 생성·해제는 가능하다. 같은 월드의 Update 재진입은 거부한다. 콜백 중 새로 생긴 native 알림은 다음 Update에 전달한다.
- 공통 계층이 최종 설정으로 종료된 관계를 알리고, 새 관계의 시작은 native 알림으로 확인한다. 관계 식별자는 큐에서 지연된 이전 종료가 새 관계를 끝내지 않도록 구분한다. 어댑터는 native 알림을 수신할 때 식별자를 확정하며 전달할 때 새 관계의 식별자로 바꾸지 않는다.
- 진행 중인 관계와 식별자는 Collider별 연결이 보관하며, 종료·해제할 때 양쪽 연결에서 지운다.
- 동일 관계의 중복 알림은 같은 식별자를 사용한다. native 단계 안의 실제 종료·재진입에는 새 식별자를 부여하며, 이미 종료한 관계의 시작을 이전 식별자로 다시 보내지 않는다. Unity가 관계 식별자를 제공하지 않는 콜백에서는 직렬 시뮬레이션의 수신 순서를 사용하므로, 이 대응과 native 지연 종료의 실제 순서는 두 Unity 버전에서 확인해야 한다.
- 시스템의 객체별 연결 점검·대리자 실패는 ExceptionHandler에 보고하고 소속 핸들을 해제한다. 소비자 콜백 실패는 보고한 뒤 공간에 등록한 콜백이면 그 구독을, Collider에 등록한 콜백이면 그 알림의 양쪽 Collider를 해제한다. 처리기가 없으면 정리 후 예외를 재전파하며, 정상 반환하면 유효한 나머지 객체와 구독을 처리한다. 중간에 해제된 핸들의 늦은 알림은 전달하지 않는다.
- 어댑터가 다른 공간의 객체를 포함하는 등 잘못된 알림을 보내거나 월드 진행 중 식별하지 못한 예외를 던지면 ExceptionHandler에 보고하고 그 알림을 버리거나 그 Update를 끝낸다. 월드는 유지하며, 처리기가 없으면 예외를 재전파한다.
- 어댑터가 외부 프레임워크 실패로 식별하여 처리한 오류는 `SpatialEngineException`과 원본 InnerException으로 전달한다. 이 오류는 공통 ExceptionHandler에 다시 보고하거나 임의의 Collider를 제외하는 근거로 사용하지 않는다. Unity 연결은 native 속성·질의·시뮬레이션의 UnityException과 2D Simulate 실패를 이 경로로 전달한다. 자동 재시도나 시간 진행 성공을 보장하지 않는다.

Trigger의 자기 Collider를 식별할 수 없는 배치는 생성 연결과 다음 Update의 IsTrigger 적용·점검 시 거부한다.

1. Trigger GameObject에 같은 차원 Collider가 둘 이상 있는 경우.
2. Trigger가 소유 Rigidbody와 같은 GameObject에 있고 같은 강체의 다른 자식 Collider도 있는 경우.

공통 생성 API는 Collider별 전용 GameObject와 필요한 내부 강체를 구성한다. 여러 센서를 만들 때도 각각 독립된 객체로 생성하며, 수동 Source 구조를 자동 변경해 모호함을 해결하지 않는다.

현재 2D는 형상 종류를 구분하지 않고, 3D는 Box·Sphere·Capsule에 중력과 이동을 막고 수면하지 않는 내부 Dynamic 강체를 둔다. native 이벤트 발생 조건을 충족하기 위한 구현 세부이며 공개 강체 핸들은 제공하지 않는다. 복잡한 형상은 Unity의 정적 형상·convex·강체 조합 제한을 따르고, 두 정적 복잡 형상의 접촉을 별도 계산해 이벤트로 만들지 않는다.

## 수명과 해제

| 동작 | 논리적 결과 | Unity 자원 |
| --- | --- | --- |
| Collider Dispose | 즉시 무효화·연결 정리·Disposed 1회 | 시스템이 생성한 Collider 전용 GameObject 파괴 요청 |
| 월드 Dispose | 모든 하위 핸들 해제 후 월드 Disposed 1회 | 중계·구독 해제 후 소유 Scene의 비동기 unload 요청 |
| 외부 Destroy | 발견 시 이전 핸들 무효화·정리 | Unity의 지연 Destroy 완료 전에는 실제 소멸로 판단하지 않음 |
| 외부 씬 unload | 월드와 하위 핸들 무효화 | sceneUnloaded 구독으로 반영 |

Disposed는 모든 SpatialHandle과 ICollisionComponent에서 제공한다. 보통 월드 종료 때 일괄 해제하며, 객체가 먼저 필요 없어지면 개별 Dispose도 가능하다. 논리적 해제 완료와 Unity native 파괴 완료는 다르다. 월드 이벤트는 비동기 씬 언로드 완료를 기다리지 않는다.

매 프레임 순회하는 Observer는 없다. 유효성은 핸들 접근, 명시적 Update와 알림 전달 경계에서 확인한다. IsValid가 무효 원본을 발견하면 Dispose 경로로 정리한다. 소멸 직후 모든 핸들에 즉시 통지를 보장하지 않는다.

Dispose는 멱등이다. 모든 하위 핸들의 구조 정리와 native 해제를 시도한 뒤 Disposed를 하위 핸들에서 월드 순서로 전달한다. 정리·알림 실패도 ExceptionHandler 정책을 따르며, 미처리 예외 뒤의 나머지 알림은 중단한다. 해제 후 속성·Source·질의·새 이벤트 등록은 ObjectDisposedException이다. IsValid/IsDisposed/Space, 이벤트 제거, 반복 Dispose는 가능하다.

해제한 native 객체가 지연 파괴를 기다리는 동안에도 내부 연결에서 새 핸들로 다시 사용하지 않는다. 개발자가 Source를 통해 객체를 다른 씬으로 옮기는 것은 오사용이며, 발견된 소멸·이탈은 보호 동작으로 무효화하고 정리한다.

## 실행 조건과 제한

공통 설정의 독립 범위는 레이어 충돌 정책·명시적 시간 진행이다. Unity의 전역 solver, 기본 재질·접촉 설정, Contact Pairs Mode, callbacksOnDisable, 수면·접촉 생성 규칙까지 월드별 엔진 설정으로 바꾸지는 않는다. 특히 Kinematic/Static 또는 복잡한 형상의 native 알림 제한은 남는다. 연결 이전 접촉이나 Stay·Exit를 질의로 합성하지 않는다.

Collider의 Source는 Unity 고유 형상·재질 등의 편집 범위에서 사용하는 확장 지점이다. 전용 객체의 구조·소속·수명을 임의로 바꾸거나 native 월드의 Simulate를 직접 호출하는 것은 오사용이다. 월드 조작은 시스템 API를 통해서만 수행한다. 복잡한 형상의 데이터 편집과 예상 물리 결과는 Unity 실행 검증이 필요하다.

씬 전환 중 월드 유지는 지원하지 않는다. Unity의 [로컬 물리 씬 수명](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SceneManagement.LocalPhysicsMode.html)은 소유 Scene에 종속되며, [Single 로드](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SceneManagement.LoadSceneMode.Single.html)는 기존 씬을 닫는다. 따라서 Single 로드를 수행하면 소유 Scene이 내려가 월드가 해제된다. 씬을 전환한 뒤에는 새 월드를 만든다.

3D Box 질의는 전체 Size를 halfExtents로 변환한다. 질의 배열이 가득 차면 두 배로 늘려 재조회하며 일부 결과를 조용히 누락하지 않는다.

Unity 소스는 `UNITY_2022_3_OR_NEWER`, Unity 6 차이는 `UNITY_6000_0_OR_NEWER`로 분기한다. 일반 .NET에서는 Unity 소스가 제외된다. 이번 단계는 소스와 정적 분석까지이며 asmdef·별도 DLL·패키지·배포와 실행 검증은 진행하지 않는다.
