# Spatial System Rules

Spatial System의 Rules는 외부 엔진과 관계없이 소비자에게 보장할 설정 변경·접촉 알림·수명과 오류 처리의 기준이다.

## 목차

- 적용 범위
- 월드 조작의 경계
- 갱신과 설정 변경
- 비활성화와 재활성화
- Trigger 전환
- 해제와 외부 소멸
- 외부 변경의 보호 처리
- 오류 처리와 유효성 조회
- 씬 전환과 월드 수명
- 구현과 검증 상태

## 적용 범위

공간의 정의와 전체 구조는 [Overview](01.%20Overview.md)를 따른다. 이 문서는 2D·3D의 CollisionSpace와 각 엔진 연결이 지켜야 하는 공통 동작을 정한다. 아래 설정 변경 규칙은 접촉 관계의 전환에 관련된 Enabled·IsTrigger를 대상으로 한다.

| 대상 | 결정한 규칙 |
| --- | --- |
| 설정 변경과 알림의 적용 시점 | 다음 Update에서 설정을 적용하고 해당 Update의 알림 전달 단계에서 관계 변화를 알린다. |
| 같은 Update 전의 반복 변경 | 마지막에 지정한 설정만 적용한다. |
| IsTrigger 변경 | 관계 종류가 바뀌면 기존 관계를 종료하고, 새로운 종류의 시작은 엔진이 확인한 뒤 전달한다. |
| Dispose·외부 파괴 | Disposed로 수명 종료를 통지하며 Exit는 보장하지 않는다. |
| 월드 직접 조작과 수동 객체 등록 | 오사용이다. 객체 생성·등록·제거·월드 진행은 시스템이 제공하는 API를 통해서만 수행한다. |
| 외부 원본의 예기치 않은 변경 | 보호 동작으로 다음 Update에서 발견한 상태를 반영하며, 관측하지 못한 중간 변경 이력은 복원하지 않는다. |
| 외부 프레임워크의 오류 | 해당 프레임워크의 어댑터에서 처리한다. |
| Spatial System 측 책임의 객체 처리 오류 | ExceptionHandler에 보고한 뒤 문제 객체를 해당 월드에서 제외한다. 유효성 조회 중의 오류도 같은 규칙을 따른다. |
| 공간에 등록한 콜백의 예외 | ExceptionHandler에 보고하고 그 구독을 해제한다. 월드와 양쪽 Collider, 다른 구독은 유지한다. |
| Collider에 등록한 콜백의 예외 | ExceptionHandler에 보고하고 그 알림의 양쪽 Collider를 해당 월드에서 제외한다. 월드와 공간에 등록한 구독은 유지한다. |
| 어댑터의 잘못된 알림과 월드 진행 예외 | ExceptionHandler에 보고하고 그 알림을 버리거나 그 Update를 끝낸다. 월드와 객체는 유지한다. |
| 예외 처리기 미등록 | 문제 객체 제외나 구독 해제를 보장한 뒤 예외를 재전파하여 현재 호출을 중단한다. |
| 씬 전환 | 씬을 전환하는 동안 월드를 유지하는 기능은 지원하지 않는다. 월드의 외부 자원이 내려가면 외부 소멸로 다룬다. |

접촉 여부와 새로운 겹침의 발견은 외부 엔진이 담당한다. 시스템은 엔진이 확인한 관계와 상태 변경을 근거로 알림의 의미를 맞춘다. 형상 간 충돌을 다시 계산하거나 Overlap 결과를 반복 비교하여 접촉 이벤트를 만들지 않는다.

이 문서는 구현이 충족해야 할 기준이며, 현재 소스가 모든 규칙을 충족한다는 의미는 아니다.

## 월드 조작의 경계

월드와 내부 엔진 객체의 구성·등록·제거·시간 진행은 Spatial System과 해당 엔진 어댑터가 책임진다. 개발자는 시스템이 제공하는 생성·설정·Update·Dispose API를 통해 사용한다.

개발자가 직접 만든 native Collider를 월드에 넣고 Wrap으로 등록하는 흐름은 오사용이며 지원하지 않는다. 외부 코드가 월드의 씬이나 시뮬레이션 객체를 직접 조작하는 공개 진입점도 제공하지 않는다. 외부 객체를 시스템이 소유한 월드에 넣었다는 이유만으로 정식 등록 대상으로 인정하지 않는다.

어댑터가 내부에서 자신이 생성한 엔진 객체와 공통 핸들을 연결하는 작업은 필요하다. 이 내부 연결을 개발자가 호출하는 수동 등록 기능으로 노출하지 않는다. 복잡한 형상도 시스템의 엔진별 생성 API를 통해 만들고 명시적으로 제공한 형상 편집 기능을 사용한다.

Collider의 Source가 형상 데이터 편집을 위해 노출되더라도, 이를 통해 월드의 구조나 객체 소속·수명·진행을 직접 바꾸는 것은 허용되지 않는다. 외부 변경을 발견하여 무효화하거나 정리하는 보호 처리는 직접 조작을 정상 사용법으로 인정한다는 의미가 아니다.

## 갱신과 설정 변경

공통 핸들에서 Enabled·IsTrigger를 변경하면 다음 Update의 적용 대상이 된다. 적용 전 getter는 마지막 예약값을 반환하며 native 상태는 아직 바뀌지 않는다. 소비자에게 접촉·Trigger 알림을 전달하는 시점은 해당 월드의 Update 안이며, 속성 설정만으로 콜백을 즉시 호출하지 않는다.

하나의 Update에 적용할 설정은 갱신 경계에서 확정한다. 그 Update의 알림 콜백에서 발생한 설정 변경은 다음 Update의 대상이다. 같은 월드의 Update 재진입은 허용하지 않는다.

같은 Update 전에 여러 번 바꾼 설정은 최종값만 적용한다. 중간에 지정했지만 갱신에 적용되지 않은 값만으로 관계를 종료하거나 시작하지 않는다. 이 규칙은 설정 변경을 묶는 기준이며, 엔진이 실제로 확인한 종료 후 재진입까지 하나로 합치는 기준은 아니다.

자세·형상·레이어의 상세 계약과 질의의 관측 시점은 [Collision System](03.1.%20Collision%20System.md)과 [Engine Binding](04.%20Engine%20Binding.md)을 따른다.

## 비활성화와 재활성화

Update에 비활성화가 적용되면 해당 Collider가 참여하던 공통 접촉·Trigger 관계도 종료된다. 이미 시작을 전달한 관계에는 종료를 한 번 전달하며, 엔진이 비활성화에 따른 종료 알림을 제공하지 않아도 같은 의미를 보장한다.

이 종료는 기존 접촉 기록과 비활성화라는 상태 변경을 근거로 한다. 이미 종료한 관계에 대한 엔진의 종료 알림이 뒤늦게 도착하더라도 중복 전달하지 않는다.

비활성화를 적용한 Update가 중단되어 종료를 전달하지 못했다면, 이후 설정을 되돌리더라도 그 관계는 끝난 것으로 다루고 다음 Update에서 종료를 전달한다. 전달을 기다리던 시작도 그 관계가 끝났으면 전달하지 않는다.

다시 활성화했다는 이유만으로 시작을 만들지 않는다. 외부 엔진이 새로운 접촉·겹침을 확인한 뒤 시작을 전달한다. 이전 관계의 지연된 종료가 재활성화 이후의 새로운 관계를 끝내지 않도록 구분해야 한다.

아래 예시는 이미 시작을 전달한 관계가 있고, 표에 적힌 변경 외에 이동·파괴 등 다른 변화가 없는 경우이다.

| 변경과 갱신 | 소비자가 받는 알림 |
| --- | --- |
| Enabled를 false로 지정한 뒤 Update | 기존 관계의 Exit 한 번 |
| Enabled를 false, true 순으로 지정한 뒤 Update | 최종값이 기존과 같은 true이므로 설정 변경만으로는 Exit·Enter 없음 |
| 비활성화가 적용된 뒤 Enabled를 true로 지정하고 Update | 엔진이 새 접촉·겹침을 확인하면 Enter |
| 비활성화를 적용한 Update가 중단된 뒤 Enabled를 true로 지정하고 Update | 끝난 관계의 Exit 한 번. 이후 엔진이 새 접촉·겹침을 확인하면 Enter |
| 종료한 관계에 대한 native Exit가 중복 도착 | 추가 Exit 없음 |
| 새 관계가 시작된 뒤 이전 관계의 native Exit가 도착 | 새 관계를 종료하지 않음 |

쌍의 역순으로 도착한 알림도 같은 관계로 취급한다. 접촉과 Trigger 관계는 구분하며, 실제 종료 후 재진입은 같은 프레임에 발생하더라도 유지한다. 연결 이전의 접촉이나 Stay를 합성하지 않는다.

## Trigger 전환

IsTrigger도 다음 Update에서 최종 설정을 적용한다. 그 결과 두 Collider 사이의 관계 종류가 바뀌면 이전 종류의 관계를 먼저 종료한다. 새로운 종류의 관계는 엔진이 확인한 뒤 시작한다.

예를 들어 접촉 중이던 쌍이 Trigger 관계로 바뀌면 CollisionExit를 전달하고, 엔진이 새 겹침을 확인하면 TriggerEnter를 전달한다. 반대 전환은 TriggerExit 이후 엔진이 확인한 접촉에 대해 CollisionEnter를 전달한다.

설정 변경만으로 새 관계가 존재한다고 판단하지 않는다. 다른 Collider도 Trigger여서 쌍의 관계 종류가 유지되는 경우에는 IsTrigger 값 변경만을 이유로 종료·시작을 만들지 않으며, 전달을 기다리던 시작도 그대로 전달한다. 종류 변경을 적용한 Update가 중단된 경우에는 비활성화와 같은 기준을 따른다.

## 해제와 외부 소멸

Dispose·외부 파괴는 비활성화와 구분한다. 비활성화된 핸들은 다시 사용할 수 있지만, 해제된 핸들은 사용할 수 없다.

명시적 Dispose는 논리적으로 즉시 해제하고 Disposed를 한 번 통지한다. 외부 파괴는 시스템이 소멸을 발견했을 때 핸들을 무효화하고 같은 해제 경로로 처리한다. 외부 객체의 실제 파괴 시점과 공통 핸들의 해제 시점은 같지 않을 수 있다.

이 경로에서는 Exit를 보장하지 않는다. 관계 기록을 정리하고 해제된 핸들에 대한 늦은 접촉 알림은 전달하지 않는다. 소비자는 접촉 종료와 객체 수명 종료를 각각 Exit와 Disposed로 처리한다.

Dispose는 반복 호출할 수 있으며 Disposed를 중복 통지하지 않는다. 월드를 해제할 때는 하위 핸들을 먼저 해제한 뒤 월드의 Disposed를 통지한다.

## 외부 변경의 보호 처리

월드의 직접 조작은 정식 사용 경로가 아니지만, 원본의 예기치 않은 변경을 발견했을 때 유효하지 않은 상태를 계속 사용해서는 안 된다. Source를 통한 Collider 비활성화나 GameObject 비활성화를 발견하면 다음 Update에서 관측한 상태를 보호 동작으로 반영한다. 해당 핸들이 유효하지만 충돌에 참여하지 않는 상태가 되었다면 기존 관계를 종료한다. 엔진이 보낸 종료 알림과 중복하여 전달하지 않는다.

Source 변경은 래퍼의 설정 예약 경로를 거치지 않는다. Update 사이에 직접 껐다가 다시 켜서 갱신 시점에 활성 상태만 관측된다면, 관측하지 못한 비활성화 이력을 복원하여 종료를 만들지 않는다. 그 사이 엔진이 실제 관계 전이를 보고한 경우에는 해당 알림을 공통 관계에 맞게 처리한다.

Collider 자체의 Enabled와 GameObject의 활성 상태는 서로 다른 값이다. 엔진별 연결은 실제 충돌 참여 여부를 확인하되 두 속성을 같은 값으로 취급하지 않는다.

외부 객체가 파괴되었다면 비활성화 규칙 대신 해제와 외부 소멸 규칙을 적용한다. 이 규칙은 Source를 통한 임의의 구조 변경이나 직접적인 시뮬레이션 호출까지 지원한다는 의미는 아니다.

## 오류 처리와 유효성 조회

오류가 발생하면 다음 원칙에 따라 정리한다.

- 월드에 등록한 것에서 발생하면 그 구독을 해제한다.
- 객체에 등록한 것에서 발생하면 그 객체를 해제한다. 상호작용 중에 발생했다면 상호작용하던 모든 객체를 해제한다.

상호작용은 접촉·Trigger 알림을 전달하는 동안이며, 상호작용하던 객체는 그 알림의 쌍이다. 구독도 객체도 아닌 어댑터의 오류로는 월드를 해제하지 않는다. 아래에 각 경우의 세부 기준을 정한다.

외부 프레임워크의 오류는 해당 프레임워크에 대응하는 어댑터에서 처리한다. 엔진 고유의 오류 해석과 자원 처리는 그 어댑터의 책임이다. 예외를 발견한 위치만으로 책임을 정하지 않으며, Spatial System의 잘못된 연결이나 상태 관리 때문에 발생한 오류는 시스템 측 책임으로 다룬다.

Spatial System 측 책임으로 등록 객체를 정상적으로 처리할 수 없으면 [ExceptionHandler](../03-M.2-ExceptionHandler/ExceptionHandler.md)에 예외를 보고한 뒤 문제 객체를 해당 월드에서 제외한다. 제외한 객체는 더 이상 그 월드의 시뮬레이션·질의·알림에 참여하지 않으며, 기존 핸들은 해제·무효화하여 늦은 알림을 차단한다. 엔진 객체의 정리는 해당 어댑터가 맡는다.

ExceptionHandler는 예외의 최종 처리 경로이며 문제 객체를 월드에서 제거하는 기능은 제공하지 않는다. 객체 제외는 Spatial System이 책임지고, 보고 과정에서 예외가 재전파되더라도 제외가 누락되지 않도록 보장한다.

ExceptionHandler의 처리기가 정상 반환하면 문제 객체를 제외한 나머지 작업을 계속한다. 처리기가 등록되지 않았으면 문제 객체 제외를 보장한 뒤 예외를 재전파하여 현재 호출을 중단한다. 처리기 자체가 예외를 던진 경우에도 기존 ExceptionHandler 계약에 따라 호출자에게 전파한다. 처리기 미등록을 기본 무시나 자동 계속 실행으로 처리하지 않는다.

접촉·Trigger 알림의 콜백이 예외를 던지면 콜백을 등록한 곳에 따라 처리한다. 시작과 종료 중 어느 알림인지와 관계없이 같다.

- 공간에 등록한 콜백은 월드의 모든 쌍을 받으므로 특정 쌍의 문제로 다루지 않는다. [EventStream](../../02-Core/02-E.3-EventStream/EventStream.md)의 콜백 실패와 같은 원칙으로 ExceptionHandler에 보고하고 그 구독을 해제한다. 월드와 양쪽 Collider, 다른 구독은 유지하며, 처리기가 정상 반환하면 같은 알림의 남은 콜백에 계속 전달한다.
- Collider에 등록한 콜백은 ExceptionHandler에 보고하고 그 알림의 양쪽 Collider를 모두 월드에서 제외한다. 월드와 공간에 등록한 구독은 유지하며, 제외한 Collider에 등록한 구독은 그 Collider와 함께 정리한다. 처리기가 정상 반환하면 다른 쌍의 알림을 계속 전달한다.

두 경우 모두 처리기가 없거나 예외를 다시 던지면 구독 해제나 객체 제외를 보장한 뒤 현재 Update를 중단한다. 중단된 알림의 남은 콜백에는 다시 전달하지 않으며, 아직 전달을 시작하지 않은 다른 쌍의 알림은 다음 Update에서 전달한다.

콜백 안에서 객체의 속성을 읽다가 실패한 것은 그 객체의 오류이므로 그 객체만 제외한다. 처리기가 정상 반환하면 이 실패로 중단된 콜백을 다시 보고하거나 그 구독을 해제하거나 쌍의 상대를 제외하지 않으며, 쌍이 유효한 동안 남은 콜백에 계속 전달한다. 안쪽 호출에서 이미 보고되어 재전파 중인 예외와 어댑터가 식별한 엔진 오류도 구독 해제나 객체 제외의 근거로 사용하지 않고 그대로 전달한다. 이미 해제된 핸들을 콜백이 사용하여 발생한 ObjectDisposedException은 콜백의 예외로 다룬다.

IsValid 조회, 무효 원본의 정리와 Disposed 전달 중 발생한 오류에도 같은 책임 구분과 처리 규칙을 적용한다. 시스템 측 오류를 처리하고 객체를 제외한 뒤에는 IsValid가 false를 반환한다. ExceptionHandler가 재전파하는 경우에는 객체 제외를 보장한 뒤 그 예외가 호출자에게 전달된다.

이미 사라진 외부 원본을 발견하는 것 자체는 정상적인 무효화이며 오류로 보고하지 않는다. 정리 과정의 실패는 위 규칙으로 처리한다. 월드 자체의 손상처럼 문제를 특정 객체에 한정할 수 없는 경우에 임의의 Collider를 골라 제거하지 않으며 월드도 해제하지 않는다. 어댑터가 다른 공간의 객체를 포함하는 등 잘못된 알림을 보내면 ExceptionHandler에 보고하고 그 알림만 버린다. 월드를 진행하다 엔진 오류로 식별되지 않은 예외가 발생하면 보고한 뒤 그 Update를 끝내며, 전달하지 못한 종료와 알림은 다음 Update에서 전달한다. 처리기가 없거나 예외를 다시 던지면 그 예외를 호출자에게 전달하여 현재 Update를 중단한다.

월드의 유효성 확인 자체가 예외를 던지면 월드가 살아 있는지 알 수 없으므로 유효성 조회의 규칙에 따라 월드를 해제한다.

## 씬 전환과 월드 수명

씬을 전환하는 동안 월드와 소속 핸들을 유지하는 기능은 지원하지 않는다. 씬 전환으로 월드의 외부 자원이 내려가면 외부 소멸 규칙에 따라 월드와 소속 핸들을 해제하고 Disposed로 통지하며, Exit는 보장하지 않는다.

월드의 수명은 애플리케이션이 관리한다. 씬을 전환한 뒤 충돌 기능이 필요하면 새 월드를 만들고 객체를 다시 생성한다. 애플리케이션이 명시적으로 월드를 Dispose하면 해제 규칙을 적용한다.

## 구현과 검증 상태

2026-11-25 소스에 Enabled·IsTrigger의 지연 적용, 최종값 기준 관계 전환, 비활성화 종료와 관계 식별자에 따른 지연 종료 구분을 반영하였다. SP-04·SP-05는 Unity의 실제 native 알림 순서와 전환을 실행 검증해야 한다.

SP-07은 유효성 조회를 포함하여 ExceptionHandler 보고와 객체 제외, 처리기 미등록 시 정리 후 재전파를 연결하였다. 공간에 등록한 콜백의 예외는 그 구독을 해제하고, Collider에 등록한 콜백의 예외는 그 알림의 양쪽 Collider를 제외한다. SP-08의 공개 Wrap·월드 Source·UnityScene을 제거하고 생성 API가 만든 객체만 내부에서 연결한다. 질의에서 미등록 native 객체를 발견하면 자동 등록하지 않고 오사용 오류를 반환한다.

소스 정적 분석과 전체 .NET 테스트를 수행하였다. Unity 테스트는 실행하지 않았다.

구현은 중복 종료가 없는지, 이전 관계의 종료가 새 관계를 끝내지 않는지, 같은 Update 전의 설정 변경과 서로 다른 Update에 적용한 변경이 구분되는지 확인해야 한다. Trigger 전환, Source 직접 변경, Dispose·외부 소멸도 위 기준에 따라 확인한다.

큐의 구성이나 엔진별 연결 방식은 이 계약을 충족하기 위한 구현 사항이다. 구체적인 테스트 절차와 실행 결과는 각각 [테스트 계획](../../../../tests/01-Infrastructure/04-T-SpatialSystem/docs/02.%20Plans.md)과 [테스트 결과](../../../../tests/01-Infrastructure/04-T-SpatialSystem/docs/03.%20Results.md)에 둔다.
