# EventStream 순서 그룹

순서 그룹은 구독자가 값을 받는 단계를 명시하는 경로 연산이다. EventStream은 UE 이벤트 전파 원칙을 루트·Order 단위에 적용한다. 구독 시점에 기대지 않고 필요한 실행 순서를 ForOrder·ForOrderAsync로 표현한다.

## 순서 보장

같은 위치의 그룹은 열거형의 int 값이 작은 쪽부터 호출한다. 같은 값에서는 ForOrderAsync를 마친 뒤 ForOrder를 호출하며, 두 실행 방식을 합쳐 하나의 Order 단위로 취급한다. 예를 들어 Async(0), Sync(0), Async(1), Sync(1) 순서이다. int 범위를 벗어나는 값은 거부한다.

일반 노드·형제 경로·같은 위치의 구독 사이에는 등록 순서나 생성 순서를 보장하지 않는다. 순서 없는 구독과 Order 묶음 사이의 우선순위도 없다. Where → Take → Subscribe처럼 한 경로에 작성한 연산의 적용 순서는 유지된다. 순서가 필요하면 같은 위치의 명시적인 Order로 나눈다. 순서 미보장은 병렬 실행을 뜻하지 않으며, 병렬 실행은 ForOrderAsync 아래에서만 지정한다.

같은 위치·Order·실행 방식 안에서는 Where 조건을 공유한다. 같은 숫자라도 Async와 Sync의 조건 경로는 별개이다. 중첩 Order는 그 위치의 그룹 사이에만 순서를 정한다.

## 등록·삭제의 반영 경계

전파 단위 내부의 구독 구성·노드 순서를 즉시 변경하는 것은 원칙적으로 금지한다. 공개 API의 등록·삭제 요청은 보관했다가 루트 또는 Order 종료 때 반영한다. 이 규칙은 동기·병렬 콜백과 조건 평가에 동일하게 적용한다. 전파 밖의 변경은 즉시 반영한다.

- Order 안의 요청은 현재 가장 가까운 Order 종료 때, Order 밖의 요청은 루트 종료 때 반영한다. Where·Flags·Debug는 별도 반영 경계가 아니다.
- 변경 대상이 실행 중인 상위 루트·Order에 속하면 그 상위 단위가 종료될 때까지 미룬다. 아직 실행하지 않은 뒤 Order의 구독 삭제는 요청한 앞 Order 종료 때 반영할 수 있다.
- 같은 Order의 Async에서 Sync 구독을 삭제해도 해당 Sync 구독은 이번 값까지 받는다. 뒤 Order의 구독을 삭제하면 뒤 Order에서는 이번 값도 받지 않는다.
- 새 구독은 소유 스트림에서 이미 진행 중인 발행에는 참여하지 않는다. 앞 Order에서 뒤 Order에 등록해도 다음 발행부터 받는다. 등록 버전의 기준은 각 스트림의 루트 발행이다.
- Subscribe는 대기 상태에서도 Handle과 호환되는 해제 가능한 핸들을 반환한다. 반영 전에 해제하면 연결하지 않는다. 기존 구독의 IsDisposed는 실제 해제가 반영된 뒤 true가 된다.
- 한 콜백 안의 요청 순서는 유지한다. 서로 다른 콜백의 요청 간 순서는 보장하지 않으므로, 충돌하는 변경의 결과가 중요하면 Order를 나눈다.

Enabled 변경도 같은 경계를 따른다. 활성 루트의 Enabled를 바꾸는 요청은 루트 종료 때 반영되며, 그 전에는 기존 상태로 현재 발행을 처리한다.

## 병렬 실행과 동기 반환

ForOrderAsync는 EventPath를 반환하는 동기 함수이다. Subscribe는 동기 콜백을 받고 OnNext는 모든 내부 작업과 필요한 정리를 끝낸 뒤 반환한다. async void 콜백이나 콜백이 별도로 시작한 작업의 완료는 추적하지 않는다.

병렬 실행 단위는 Subscribe 한 건이다. 서로 다른 구독은 작업 스레드에서 동시에 실행할 수 있으며 시작·완료 순서를 보장하지 않는다. 하나의 구독에 전달한 멀티캐스트 대리자는 C#의 내부 호출 순서를 유지한다. 공유 데이터의 동시 접근은 호출자가 보호하고, 메인 스레드 전용 작업은 ForOrder에 둔다.

Where·ForFlags·Debug는 발행 스레드에서 처리한다. 다음 대기 지점까지 받을 구독을 먼저 수집하므로 그 구간의 조건은 콜백 실행 전에 평가된다. 서로 다른 일반 노드에 속한 구독도 같은 병렬 구간에서 실행할 수 있다.

그룹 종료·중첩 Order 진입·스트림 연결 진입에서 현재 병렬 작업을 모두 기다린다. 대기 자체가 변경 반영을 의미하지는 않는다. 등록·삭제는 해당 루트·Order가 끝날 때까지 보관한다. 중첩 Order는 자신의 실행 방식을 따르고, Branch·Merge·Take 및 EventStream 관찰자 연결은 발행 스레드에서 하나씩 완료까지 호출한다. 연결된 스트림에는 부모의 병렬 설정을 상속하지 않는다.

콜백 본문에서 다른 스트림의 OnNext를 직접 호출하면 그 스트림의 루트 전파가 동기적으로 완료된다. 실행 중인 상위 단위에 대한 변경은 여전히 상위 경계까지 미룬다. 다른 병렬 콜백과 이 명시적 발행 사이의 순서·동시 접근은 호출자가 관리한다. 같은 스트림에 대한 전파 중 재진입은 거부한다.

## 종료와 예외

Dispose·OnCompleted·OnError 요청은 즉시 기록하여 새로운 발행·구독을 거부한다. 실제 정리와 통지는 경계에서 수행한다. 루트 종료를 요청하면 현재 가장 안쪽 Order의 Async·Sync를 마친 뒤 후속 전파를 중단하고 상위 단위를 정리한다. Order 밖에서는 루트가 현재 단위이므로 루트 전파를 마친다. 명시적 Dispose는 완료를 통지하지 않는다. 반복 종료 요청은 무시한다.

콜백이 실패하면 해당 구독을, 조건이 실패하면 해당 경로를 정리 대상으로 삼고 ExceptionHandler에 보고한다. 보고가 정상 반환하면 전파를 계속한다. 보고가 다시 던지거나 처리기가 없으면 새 콜백 호출을 중단한다. 이미 시작한 병렬 작업은 모두 기다리지만, 수집만 된 작업과 같은 Order의 미실행 Sync 콜백은 시작하지 않는다.

예외로 중단해도 변경 큐와 연결 참조는 정리하고 처음 기록한 미처리 예외를 발행자에게 전달한다. 이미 시작한 작업의 실패는 각각 보고하되, 실패한 전파의 정리 중 새로운 완료 통지를 시작하지 않는다. 병렬 작업의 실패 보고와 변경 반영은 발행 스레드에서 수행한다.

이 계약은 EventStream 내부 전파에 관한 것이다. 외부 스레드가 같은 스트림을 임의로 동시에 조작하는 일반적인 스레드 안전성은 제공하지 않는다.
