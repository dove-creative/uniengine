# EventStream 설계 결정

EventStream이 지금의 형태에 이르기까지 내린 결정을 기록한다. 결정마다 선택한 형태, 그 전에 쓰거나 검토한 형태, 얻은 것과 치른 대가를 함께 적는다. 이전의 작업 목록, 승인 기록, 본 구현 보고서, 프로토타입 평가를 이 문서 하나로 정리했다.

현재 동작의 기준은 [EventStream](../EventStream.md)에, 최신 측정의 방법과 세 구조의 비교 수치는 [벤치마크](Benchmark.md)에 있다. 이 문서의 그 밖의 수치는 결정 당시의 측정 기록이며, 측정한 날과 구현이 서로 다르므로 같은 표 안의 값끼리만 비교한다.

## 목차

- 결정 요약
- 전달 구조
    - 구독자 그래프로 값을 나눈다
    - 그래프는 트리로 두고 합류 노드를 두지 않는다

- 공개 단위와 입력
    - 기본 단위는 EventStream 하나이다
    - 모든 스트림이 값을 직접 받는다
    - 상위 연결은 InputGate가 받는다
    - 새 스트림은 첫 구독 때 연결한다

- 노드 구조
    - 그래프는 객체 참조로 두고 재귀로 순회한다
    - 키 연산은 위치마다 노드 하나와 키 행으로 둔다
    - 노드 형식을 역할별로 나눈다
    - 구독자는 출구에서만 관리한다
    - 경로 등록은 스트림이 그래프에 연결한다
    - 경로 깊이를 256단계로 제한한다

- 상태 있는 연산자
    - 상태는 연산자가 만든 스트림이 가진다
    - 연산 노드는 파생 스트림의 중첩 형식으로 둔다
    - 종료는 그 시점의 활성 구독에 알린다

- 조건 공유와 등록 검색
    - 조건은 대리자로 받고 동등성으로 공유한다
    - 등록 검색은 조건 수에 따라 선형 검색과 색인을 나눈다
    - 비트 조건은 ForFlags 경로로 나눈다
    - 값 조건은 When 경로로 나눈다

- 순서 그룹
    - 순서는 별도 스트림이 아니라 경로 연산으로 정한다

- 실패 처리
    - 실패한 부분만 정리하고 첫 예외를 돌려준다

- 측정과 문서
    - 벤치마크는 별도 실행 파일로 둔다
    - 문서는 성격에 따라 위치를 나눈다

- 보류 항목
- 확인하지 못한 사항

## 결정 요약

| 영역 | 선택한 형태 | 주된 대가 |
| --- | --- | --- |
| 전달 구조 | 같은 위치의 같은 키가 행을 공유하는 트리 | 구독자가 적거나 대부분이 받으면 이점이 없고, 같은 값이 두 분기를 지나면 두 번 전달한다. |
| 공개 단위 | EventStream 하나, 외부 입력은 `IObservable<T>` | 공급원 계약과 Chain·Connect 같은 공개 API가 사라졌다. |
| 입력 | 모든 스트림이 OnNext로 직접 받고, 상위는 InputGate로 받는다 | 발행 권한은 형식으로만 제한하고, 상위마다 입구 객체가 하나 생긴다. |
| 순회 구조 | 객체가 다음 객체를 참조하고 관리 호출 스택으로 재귀 순회하는 키 행 구조 | 동적 PGO가 켜진 .NET에서 작은 그래프 발행이 키 행 개편 전 구현보다 느리고, 중규모 K는 배열, 대규모 K는 표보다 느리다. 경로 깊이만큼 호출 스택이 깊어진다. |
| 노드 구조 | 위치마다 종류별 키 노드 하나, 내부 키 행, 공통 Connection과 출구 전용 OutputGate | 같은 위치의 Where 행이 한 노드 차례에 모여 이전 형제 방문 순서가 바뀐다. |
| 경로 등록 | EventStream과 EventPath가 서로 참조하며, 스트림이 PathInfo 체인을 그래프에 등록한다 | 두 형식이 서로 의존하고, 등록마다 단계 수만큼 기록 객체를 할당한다. |
| 상태 있는 연산자 | 새 스트림이 상태를 가지고, 연산 노드는 그 스트림의 중첩 형식 | 같은 스트림의 구독자끼리 상태를 공유하고, 호출마다 스트림을 만든다. |
| 조건 공유 | `Func<T, bool>`의 동등성 | 비교와 해시가 객체 참조보다 비싸 등록이 느려졌다. |
| 등록 검색 | Where·Flags는 16행까지 선형 검색, 17행부터 노드별 해시 색인 | 색인만큼 메모리가 늘고, 선형 검색의 최대 길이는 16행이다. |
| 비트 조건 | ulong 스트림의 ForFlags와 위치별 FlagsNode, 같은 마스크 비트의 항목 공유 | 서로 다른 마스크 수만큼 검사하며, enum 형식이 달라도 같은 비트는 공유한다. 성능은 측정하지 않았다. |
| 값 조건 | When과 위치별 WhenNode, 동등한 target의 항목 공유와 사전 분기 | 발행마다 해시를 계산하고 비교 실패는 같은 위치의 모든 target 경로를 해제한다. 성능과 PathInfo 크기는 측정하지 않았다. |
| 순서 그룹 | 경로 연산 ForOrder와 OrderedNode의 순서 값별 행 | 그룹 사이에 조건을 공유하지 않는다. |
| 실패 처리 | 실패한 부분만 정리하고 순회 뒤 첫 예외를 전달 | 한 값에서 여러 번 실패해도 밖으로는 첫 예외 하나만 나간다. |

## 전달 구조

### 구독자 그래프로 값을 나눈다

- 선택: 같은 위치의 같은 조건을 기다리는 구독자가 WhereNode의 행 하나를 공유하는 그래프로 값을 전달한다. 조건은 값마다 한 번 평가하고, 거짓이면 그 행 뒤의 연결 전체를 건너뛴다.
- 이전 형태: 그래프가 없는 이전 EventStream과, 비트마스크로 수신자를 고르는 EventRouter였다. EventRouter를 없앤 뒤 마스크 판정은 조건 대리자로 표현했으며, 이후 별도의 ForFlags 경로를 추가했다.
- 장점: 비용이 전체 구독자 수가 아니라 조건 수와 값을 받는 구독자 수를 따른다. 2026-11-06 측정에서 같은 스트림의 구독자가 각자 조건을 검사하는 개별 순회와 비교하면, 64명 중 4명이 받을 때 3.0배, 1024명 중 64명이 받을 때 17.9배, 공통 조건이 거짓일 때 33.2배 빨랐다. 본 구현 당시인 2026-11-04 Unity Windows 플레이어에서 이전 EventStream의 공유 Where와 비교하면, 64명 중 4명이 받는 경우가 Mono 2.30 → 0.27 µs, IL2CPP 1.47 → 0.24 µs였다.
- 대가: 구독자가 16명 정도면 이점이 없고, 구독자 대부분이 값을 받으면 통과한 Where마다 노드와 출구를 더 거쳐 12–19% 느리다. 조건 수가 구독자와 함께 늘면 비용도 함께 늘어 구독자 100만 명, 조건 25만 개에서 6.33 ms였다. 본 구현 당시 Unity에서는 공통 조건 하나로 전부 탈락하는 경우가 Mono 6.2%, IL2CPP 10.3% 더 오래 걸렸다.

### 그래프는 트리로 두고 합류 노드를 두지 않는다

- 선택: 노드마다 부모가 하나인 트리로 둔다. 여러 입력을 합치는 일은 Merge가 만든 새 스트림이 한다.
- 검토한 형태: 같은 그래프의 분기끼리 합치도록 부모가 여럿인 합류 노드를 두는 형태였다. 이 경우 같은 값이 두 분기를 모두 통과할 때의 중복 처리와 부모별 완료 집계를 함께 만들어야 했다.
- 장점: 순회와 정리가 단순하다. 빈 노드는 루트 방향 한 경로로 제거된다.
- 대가: 두 입력을 모두 통과한 값은 두 번 전달한다. 한 번만 전달하려면 두 조건을 합친 Where 하나를 쓴다. 같은 값을 한 번으로 셀 사용 사례가 없었고, 외부 발행 두 건을 합치면 값이 같아도 두 번 전달해야 하므로 이 동작을 유지한다.

## 공개 단위와 입력

### 기본 단위는 EventStream 하나이다

- 선택: 사용자가 다루는 형식은 EventStream과 EventPath이다. 별도의 공급원 계약은 없고, 외부 입력은 `IObservable<T>`를 생성자에 넘긴다. EventStream은 `IObserver<T>`도 구현해 다른 공급원의 수신자가 될 수 있다.
- 이전 형태: 본 구현은 기존 EventStream을 공급원 EventSource로 바꾸고, 새 EventStream이 공급원 하나와 그래프를 소유했다. 이후 EventSource, IEventSource, 공급원 형식 `Merge<T>`를 없앴다. 한때 `IObserver<T>` 구현이 빠졌다가 이전 공개 API와 비교하며 되살렸다.
- 장점: 값을 넘기는 단계가 하나 줄고, 예외 규칙이 그래프 하나로 통일된다. 구독마다 래퍼 대리자를 만들던 경로가 사라져 AdaptiveCollection에 더했던 준비된 등록 경로도 되돌렸다.
- 대가: Chain·Connect, IPassiveObserver, TerminationMode, 공급원의 파생 지점이 공개 API에서 사라졌다. 외부 공급원의 수명은 호출자에게 남는다.

### 모든 스트림이 값을 직접 받는다

- 선택: 사용자가 만든 스트림뿐 아니라 연산자·Branch·Merge가 만든 스트림도 OnNext로 값을 받는다. 넣은 값은 위에서 온 값과 같게 처리하고 그 스트림 아래로만 흐른다. 첫 구독 전에도 Take·Skip의 횟수와 TakeWhile·SkipWhile의 조건 상태에 반영한다.
- 이전 형태: 값을 넣으려면 공급원이 필요했다.
- 장점: 공급원 없이 값을 넣을 수 있고, 어느 스트림에서든 같은 규칙으로 재현하고 시험할 수 있다.
- 대가: 스트림을 넘겨받은 쪽은 누구나 값을 넣을 수 있다. 발행 권한을 막으려면 EventPath나 `IObservable<T>`로 넘긴다. 구독 전 직접 입력으로 Take·TakeWhile이 끝나면 상위 연결 없이 폐기되고 이후 구독을 거부한다.

### 상위 연결은 InputGate가 받는다

- 선택: 상위 하나당 InputGate 하나를 두고, InputGate가 상위의 값·완료·끊김을 받아 스트림에 전달한다. InputGate는 트리에 속하지 않는다.
- 검토한 형태: 스트림 자신을 상위의 관찰자로 등록하는 형태였다.
- 장점: 사용자가 부른 OnCompleted와 상위의 완료를 구분하고, 상위가 완료 없이 폐기된 것도 알 수 있다. Merge가 입력별로 완료를 셀 수 있다.
- 대가: 상위마다 객체가 하나 늘고, 연결 상태를 트리 밖에서 따로 관리한다.

### 새 스트림은 첫 구독 때 연결한다

- 선택: 연산자·Branch·Merge가 만든 스트림은 첫 구독 때 상위에 연결하고, 마지막 구독이 떠나면 스스로 폐기된다.
- 이전 형태: 프로토타입의 Branch는 생성 직후 부모에 연결되어, 한 번도 구독하지 않으면 부모 종료나 명시적 Dispose까지 남았다.
- 장점: 구독하지 않은 스트림이 상위 그래프에 노드를 남기지 않는다.
- 대가: 연결 전에 상위에서 온 값은 받지 못하고 직접 입력만 상태에 반영된다. 부모의 폐기는 구독 전 스트림에도 따로 적용해야 한다.

## 노드 구조

### 그래프는 객체 참조로 두고 재귀로 순회한다

- 선택: 그래프의 논리 구조와 객체 구조를 같게 둔다. 노드·키 행·Connection·Gate가 다음 객체를 직접 참조하고, 전파·종료·정리는 이 참조를 따라 관리 호출 스택에서 재귀로 진행한다. 2026-11-12에 키 행 구조 7f9e1e2를 최종 구조로 확정하고 순회 구조의 성능 실험을 마쳤다.
- 이전 형태: 키 행 개편 전의 구현 5478bbd도 객체 참조와 재귀 순회였으며, 키별 항목을 노드로 표현했다.
- 검토한 형태: 다음 세 가지를 검토했으며 아래 장점의 이유로 채택하지 않았다.
    - 배열 순회 cab9d8e: 자식과 Where·Flags 행 체인을 참조 배열로 바꾸고, 순회 중 제거는 칸을 비운 뒤 가장 바깥 순회가 끝날 때 압축한다. 실험 브랜치 experiment/array-children에 보존한다.
    - 표 기반 그래프 d818fe7: 노드·행·구독을 그래프가 소유하는 표의 칸으로 두고 명시적 스택과 반복문으로 순회한다. 실험 브랜치 experiment/table-graph에 보존한다.
    - 구독 경로를 미리 모두 펼쳐 두고 발행 때 경로별로 병렬 계산하는 방식은 구현·측정하지 않았다.
- 장점: 논리 구조를 객체에서 그대로 읽을 수 있다. Gate 우선 순서, 등록 가시성, 즉시 제거, 중첩 종료와 정리 계약이 각 객체의 방문 코드에 있으므로 계약을 바꿀 때 그 객체만 고치면 된다. 배열은 칸 번호·순회 깊이·압축을, 표는 칸 번호와 세대·재사용 지연·참조 표·명시적 스택을 계약마다 함께 맞춰야 한다. 성능이 최우선인 처리는 EventStream의 구조를 바꾸지 않고 ECS로 다룬다.
- 근거: 2026-11-12에 다섯 구현을 같은 실행기로 비교한 결과이다. 세 구조의 수치는 [벤치마크](Benchmark.md)의 결과 비교 장에 있고, 배열과 cb62332의 수치는 같은 측정 결과 폴더 jit-conditions-20261112의 table1-structures.md에 있다. 아래는 같은 실행 안의 상대비이다.
    - 키 행 개편 전 구현 5478bbd 대비: 동적 PGO를 켠 조건에서는 작은 그래프 발행 8개 시나리오가 15~41% 느리고 3개가 빠르다. PGO를 끈 두 조건에서는 63개 중 46~50개가 10% 미만, 2~3개가 보류, 9~12개가 빠르고 2개가 느리다. 빠른 항목에는 조건 64종(약 14%), 100만 R(약 10~15%), 100만 K(약 32~34%)가 있다. 이전 구현은 PGO에서 얻는 이득이 커서 PGO를 켠 조건에서만 작은 그래프가 더 빨랐다.
    - 배열 대비: 배열이 1만 K에서 약 39~41%, 10만 K에서 약 21~25% 빠르다. PGO를 끈 조건에서는 배열이 B32·C2·D에서 약 22~41% 느리다.
    - 표 대비: 표가 10만 K에서 약 13~20%, 100만 K에서 약 51% 빠르다. A~F와 1,000 규모 K의 작은 시나리오 39개 중 37~38개에서는 표가 느리고, 64명 모두가 받는 B는 2.3~2.6배이다.
    - cb62332 대비: cb62332가 1만 K에서 약 25~32% 빠르지만 100만 L·R에서 약 15~44% 느리며, 전체적으로 빠르다고 할 수 없다.
- 대가: 동적 PGO를 켠 .NET에서는 작은 그래프 발행이 키 행 개편 전 구현보다 느리다. 중규모 K는 배열보다, 대규모 K는 표보다 느리다. 경로 깊이만큼 호출 스택이 깊어지며, 2026-11-11 측정에서 깊이 256의 Where 구독 콜백은 521프레임이었다. 표 구현은 깊이와 무관하게 8프레임이었다. 스택 넘침은 경로 깊이 256단계 제한으로 막는다.

### 키 연산은 위치마다 노드 하나와 키 행으로 둔다

- 선택: 같은 부모 연결 위치마다 WhereNode·WhenNode·FlagsNode·OrderedNode를 종류별로 하나씩 둔다. 각 노드는 키 하나와 뒤의 Connection을 가진 내부 행을 관리한다. 행은 Node·NodeChild를 상속하지 않으며 NodeCount에도 포함하지 않는다. 다음 단계 노드는 행의 연결이 참조하는 별도 노드이다.
- 이전 형태: Where는 predicate마다 노드를 만들었고 WhenEntry·FlagsEntry와 순서 그룹의 Node가 키별 하위를 가졌다. Where 등록 색인은 그래프의 부모별 표가 소유했다.
- 장점: 키 검색과 그래프 노드의 책임을 분리한다. 루트·Debug·Counter·Condition도 자기 Connection 하나를 사용하므로 Gate 우선 순서, 자식 체인, Registration과 정리 규칙을 공유한다. 자식은 소속 연결을 알고 행은 자기 키를 알아 빈 행을 키로 바로 지우며, 역방향 표와 그래프의 형식별 정리 분기가 필요 없다.
- 순서 계약: 연결마다 Gate를 구독 순서로 방문한 뒤 자식 노드를 생성 순서로 방문한다. Where·Flags 행은 등록·생성 순서, When의 종료 행은 생성 순서, Order 행은 순서 값 순서이다. 완료·오류·폐기도 같은 순서로 모든 행에 전달한다.
- 대가: Where(a), ForFlags(m), Where(b)를 같은 위치에 등록하면 이전의 a → flags → b에서 a, b행 → flags로 바뀐다. 행과 다음 노드의 수명은 분리되지만 연결이 비면 행을 제거하고 마지막 행이 사라지면 부모 연결에서 노드를 제거해야 한다.
- 크기 계약: 경로 연산 하나는 깊이 한 단계이며 최대 256단계이다. NodeCount는 경로 노드와 스트림 연결 전용 OutputGate를 세고 루트·공유 구독 Gate·행·Connection은 세지 않는다.

### 노드 형식을 역할별로 나눈다

- 선택: 자식 자리에 들어가는 NodeChild 아래에 노드 형식 Node 하나를 두고 모든 경로 노드가 이를 상속한다. 키가 없는 루트·Debug·파생 스트림의 Counter·Condition은 Node의 연결 하나를 쓰고, 키 노드는 그 연결을 두지 않고 내부 행마다 연결을 가진다. 다음 단계 노드와 Gate는 Connection이 관리하며 행은 노드 상속 계층에 넣지 않는다.
- 이전 형태: Node 한 형식이 경로 정보, 구독 목록, 자식 목록을 모두 가졌고, 전파 함수가 연산 종류로 분기했다. 키 행 개편 때는 공통 기반 NodeBase와 연결 하나를 가진 Node를 나누고, 키 노드가 NodeBase를 바로 상속했다.
- 검토한 형태: 출구까지 Node를 상속하거나 공통 노드 인터페이스를 모두 구현하게 하는 형태는 출구가 노드가 아니므로 기각했다. 키별 항목을 모두 노드로 표현하던 형태는 키 행으로 대체했다. 키 노드에도 연결을 만들어 두는 형태는 쓰지 않는 빈 연결이 생기고 그 연결에 자식을 붙이는 실수를 막지 못해 기각했다.
- 장점: 형식마다 자기 방문 동작을 가진다. 노드 상속이 NodeChild → Node 한 단계라 키 노드와 키 없는 노드를 같은 형식으로 다루고, 연결을 하나 두는지 행마다 두는지는 형식별 차이로 남는다. 출구는 자식 목록 없이 자식 자리에 들어가고, 순서 사전은 OrderedNode에만 있어 각 형식이 기반 형식의 약속을 그대로 지킨다.
- 대가: 자식 방문이 가상 호출이다. 키 노드는 비어 있는 연결 필드 하나를 가지며, 그 필드를 읽는 IsEmpty·Visit·VisitEnd를 반드시 재정의해야 한다. 같은 부모 아래 조건이 수천 개인 경우를 조사했을 때, 가상 호출과 예외 영역을 없앤 변형은 1만 구독에서 일부 빨랐지만 2만·4만 구독에서는 차이가 없었다.

### 구독자는 출구에서만 관리한다

- 선택: 구독 목록은 OutputGate에만 둔다. 같은 연결 위치의 구독자는 Gate 하나를 공유하고, Connection은 이 Gate를 자식 노드보다 먼저 방문한다. 새 스트림으로 가는 연결은 연결마다 Gate를 따로 둔다.
- 이전 형태: 노드가 구독 목록과 자식 목록을 함께 가졌다.
- 장점: 경로 노드는 값을 거르는 일만 맡는다. 구독자를 먼저 만들어진 자식보다 앞서 호출하는 순서가 Gate의 위치로 보장된다.
- 대가: 구독 위치가 새로 생길 때마다 Gate가 하나 생긴다. 2026-11-08의 키별 노드 구조 조사에서 새 위치당 약 16 ns와 72 B였다. 당시 Gate와 구독 객체가 형제 Where 노드 사이에 할당되는 배치가 발행 비용에 영향을 주었다. 키 행 구조 전체의 발행·등록 비용은 [벤치마크](Benchmark.md)의 결과 비교 장에서 비교했으며, 새 위치당 Gate 비용만 따로 측정하지는 않았다.

### 경로 등록은 스트림이 그래프에 연결한다

- 선택: EventPath와 EventStream은 같은 등록 계약 IRegistrable을 구현한다. Where·When·Debug·ForOrder는 두 형식의 인스턴스 메서드로 제공하며, EventStream도 경로를 만드는 기본 기능을 직접 가진다. ulong 스트림·경로 전용 ForFlags는 인스턴스 메서드로 둘 수 없으므로 EventPathExtensions의 확장 메서드로 남긴다. 구독하면 각 경로 단계가 자기 단계를 PathInfo로 만들어 앞 단계로 넘기고, 끝의 스트림이 받은 PathInfo 체인을 따라 그래프의 노드 기능으로 노드를 찾거나 만든다. PathInfo는 등록 한 번에만 쓰는 기록이다.
- 이전 형태: 그래프 노드가 EventPath를 보관했고, 그래프가 경로 형식을 알았다. 이후 EventStream이 EventPath를 참조하지 않도록 경로 생성 기능을 확장 메서드로 두었지만, 스트림에서 경로를 만드는 책임이 API 소유 타입에 드러나도록 Where·Debug·ForOrder를 인스턴스 메서드로 옮겼다.
- 검토한 형태: 경로 전용 인터페이스를 따로 두는 형태는 각 경로가 이미 자기 스트림을 알고 있어 필요 없었다. PathInfo를 구조체로 만드는 형태는 C# 9에 ref 필드가 없어 체인을 참조로 이을 수 없으므로 기각했다. ForFlags를 FlagExtensions에 모으는 형태는 플래그 기능을 한곳에서 찾을 수 있지만, Core Level 1의 유틸리티가 Level 2의 EventStream·EventPath에 의존하게 되므로 기각했다.
- 장점: 그래프는 경로를 모르고 노드 단위 기능만 제공한다. 경로가 여러 갈래로 나뉘어도 등록 한 번은 선형 체인 하나이다. 기본 경로 연산의 정의를 EventStream에서 직접 찾을 수 있고, 스트림과 경로에서 같은 호출 문법을 사용한다. FlagExtensions는 비트 연산만 맡아 이벤트 형식에 의존하지 않는다.
- 대가: EventStream과 EventPath는 서로 참조한다. ForFlags만 확장 메서드로 남아 경로 연산의 정의가 두 곳에 나뉜다. 등록마다 경로 단계 수만큼 PathInfo를 할당한다. 2026-11-08 조사에서 단계당 56 B였다. 이 값은 ForFlags의 `ulong` 마스크 필드와 When의 target 필드를 추가하기 전에 측정했으며, 추가한 뒤의 크기는 측정하지 않았다.

### 경로 깊이를 256단계로 제한한다

- 선택: 연산·순서 그룹·스트림 연결을 합친 경로 깊이를 256단계까지 허용하고, 넘는 경로는 구성할 때 거부한다.
- 장점: 등록·전파·종료가 깊이만큼 호출 스택을 쓰므로 스택 넘침을 경로 구성 단계에서 막는다.
- 대가: 그보다 깊은 경로는 만들 수 없다.

## 상태 있는 연산자

### 상태는 연산자가 만든 스트림이 가진다

- 선택: Take·TakeWhile·Skip·SkipWhile은 경로 노드가 아니라 새 EventStream을 시작하고, 상태는 그 스트림이 가진다. 같은 스트림을 구독한 쪽끼리 남은 횟수와 진행 상태를 공유하고, 연산자를 다시 호출하면 새 상태로 시작한다.
- 이전 형태: 프로토타입과 본 구현은 상태 있는 연산을 경로 노드로 두고, 같은 경로를 재사용해도 구독마다 카운터를 따로 가졌다.
- 검토한 형태: 상태 있는 노드를 남은 횟수나 진행 상태가 같을 때만 공유하는 형태였다. 실제로 공유될 기회가 드물어 제외했다.
- 장점: 공유되는 경로 노드에 상태가 없으므로 공유 기준이 조건 하나로 끝난다. 경로 중간의 종료도 스트림 종료 한 가지로 표현된다.
- 대가: 늦게 구독한 쪽은 남은 상태를 이어받는다. 독립된 상태가 필요하면 연산자를 다시 호출해야 한다. 호출할 때마다 스트림을 만들므로 2026-11-06 측정에서 Take·Branch의 구독·해제는 개별 순회의 약 5배 시간과 4.7배 할당이 들었다.

### 연산 노드는 파생 스트림의 중첩 형식으로 둔다

- 선택: TakeStream·TakeWhileStream·SkipStream·SkipWhileStream이 EventStream을 상속하고, 횟수를 세는 Counter나 조건을 보는 Condition을 중첩 형식으로 가진다. 스트림을 만들 때 이 노드를 그래프의 루트로 주입하고, 노드는 끝나면 스트림의 완료 처리를 호출한다.
- 이전 형태: 연산 노드를 그래프 쪽 형식으로 두고 그래프가 연산 상태를 다뤘다.
- 장점: 연산자별 상태와 종료 처리가 한 형식 안에 모인다. 그래프는 연산 종류를 모른다. 연산 노드는 스트림마다 하나라서 경로 병합의 대상이 아니다.
- 대가: 연산자마다 파생 형식이 하나씩 생긴다. 루트 주입은 구독이 생기기 전인 생성 시점에만 할 수 있다.

### 종료는 그 시점의 활성 구독에 알린다

- 선택: 스트림이 끝나면 별도 규칙 없이 그 시점의 활성 구독에 완료를 알린다.
- 검토한 형태: 같은 전파 중에 추가되어 아직 값을 받지 않은 구독은 종료 통지에서도 빼는 형태였다.
- 장점: 종료 규칙이 하나이다. 끝난 스트림에 남는 구독이 없다.
- 대가: Take의 마지막 값을 처리하는 동안 추가된 구독은 그 값을 받지 않고 완료만 받는다.

## 조건 공유와 등록 검색

### 조건은 대리자로 받고 동등성으로 공유한다

- 선택: 조건은 `Func<T, bool>`로 받는다. 같은 부모 아래에서 메서드와 대상이 같은 대리자만 같은 조건으로 보고 WhereNode의 키 행을 공유한다.
- 이전 형태: 이름과 조건을 가진 Filter 객체를 받고, 같은 Filter 참조일 때 공유했다. Filter를 그 자리에서 만들면 공유되지 않았다.
- 검토한 형태: 대리자를 참조로 비교하는 형태는 C# 9에서 메서드 그룹을 넘길 때마다 대리자가 새로 만들어져 같은 함수도 공유되지 않으므로 기각했다. 이름으로 묶는 형태는 다른 조건이 조용히 합쳐질 수 있어 기각했다.
- 장점: 외부에 정의한 함수를 그대로 넘긴다. 정적 메서드, 필드에 저장한 대리자, 같은 객체의 인스턴스 메서드는 공유된다. 캡처한 대상이 다른 람다는 섞이지 않는다.
- 대가: 대리자 비교와 해시가 객체 참조보다 비싸다. 2026-11-08 조사에서 선형 검색은 형제 하나당 약 3 ns가 들었고, 색인을 써도 Filter 참조 색인을 쓰던 이전 구현보다 약 36 ns 느렸다. 그래서 조건이 8–64개인 부모에 구독 하나를 더하는 비용이 이전 구현보다 45–100% 컸다. 본문이 같아도 위치가 다르거나 호출마다 새로 만드는 람다는 공유되지 않으므로, 공유하려면 외부 함수를 넘긴다.

### 등록 검색은 조건 수에 따라 선형 검색과 색인을 나눈다

- 선택: WhereNode와 FlagsNode는 키 행이 16개 이하이면 행을 선형 검색하고, 17번째 행을 등록할 때 그 노드에 해시 색인을 만든다. 행 수가 줄어도 유지하다가 마지막 행을 제거하면 해제한다. Where는 대리자 동등성, Flags는 enum 형식과 무관한 mask 비트를 키로 쓴다. 색인은 등록 검색에만 쓰고 발행은 행 체인을 따른다.
- 이전 형태: 본 구현은 형제가 8개 이상인 부모에 Filter 참조 색인을 만들고 4개 미만이 되면 회수했다. 리팩터링 중에는 그래프 하나가 모든 부모의 색인을 가졌는데, 형제가 하나뿐이어도 해시를 계산해 구독 비용을 키웠다. 그래서 색인을 없애고 선형 검색만 두었더니, 이번에는 형제가 수천 개인 부모의 등록이 제곱으로 늘어 4만 구독의 준비가 기준 커밋의 18 ms에서 약 1.1 s가 되었다.
- 장점: 작은 노드는 해시 비용이 없고 큰 노드는 등록 검색 비용을 줄인다. 색인을 유지하므로 기준값 부근의 등록·해제가 색인 생성과 폐기를 반복하지 않는다. 노드가 행과 색인을 함께 소유하므로 그래프의 부모별 Where 색인 표가 필요 없다. 이전 키별 노드 구조의 2026-11-08 측정에서는 1만 구독의 전체 등록이 213 ms → 12.5 ms, 10만 구독이 8,141 ms → 52.5 ms였다. 이 수치는 현재 키 행 구조의 성능 근거로 사용하지 않는다.
- 대가: K 시나리오의 보존 메모리가 약 3% 늘었다. 기준값 바로 아래인 16개에서는 마지막 형제를 찾는 등록이 이전 구현의 약 2배였다. 기준값 8·16·32를 비교해 16을 골랐지만 모든 검색 패턴에 가장 빠른 값은 아니다.

### 비트 조건은 ForFlags 경로로 나눈다

**선택**

비트 조건은 Where와 별도의 경로 연산 ForFlags로 둔다.

- `ulong` 스트림에 어떤 flags enum이든 마스크로 받는다.
- 위치마다 FlagsNode 하나를 두고, 서로 다른 마스크 비트 값마다 내부 행 하나를 둔다. 행의 연결은 Gate와 다음 단계 노드를 참조한다.
- 각 FlagsNode는 값의 비트를 발행마다 한 번 읽고, 행 체인을 생성 순서대로 방문하며 HasAny로 판정한다. 등록 검색은 Where와 같은 16행·17행 적응형 색인 규칙을 따른다.

**검토한 형태와 기각 이유**

| 검토한 형태 | 기각 이유 |
| --- | --- |
| 값 동등성 `Where(T value)` | 객체별 대상 지정에는 유리하지만, 한 값이 여러 분류에 속하는 경우를 표현하지 못한다. |
| 변환 함수를 받는 형태 `Func<T, uint>` | 호출할 때마다 변환 함수를 넘겨야 하고, enum 전용 규칙과 맞지 않는다. |
| 스트림 형식 = enum (`EventStream<TFlags>`) | 스트림 하나가 enum 하나에 묶여, 서로 다른 enum의 비트를 한 스트림에 섞는 사용을 표현하지 못한다. 필요해지면 오버로드로 추가한다. |
| int 내부 표현 | 64비트 enum을 거부해야 한다. ulong은 모든 기반 형식을 손실 없이 담는다. |
| enum을 `: ulong`으로 선언하도록 강제 | 컴파일러가 강제할 수 없다. 부호 확장 문제는 ToBits로 해결된다. |
| 비트별 색인 | 여러 비트에 걸친 항목을 한 번만 방문하도록 중복을 걸러야 한다. 호출 순서가 비트 순서가 되어 등록 순서 규칙이 깨진다. |
| 이름 Filter | 일반적으로 조건 함수로 거르는 연산, 즉 Where와 같은 뜻으로 읽힌다. |
| 이름 For | ForOrder와 이름 길이로만 구분된다. |

**대가**

- 같은 위치의 서로 다른 마스크 수만큼 비트 검사를 한다.
- 비트만 같으면 enum 형식이 달라도 공유된다.
- FlagsNode와 다른 형제 사이는 생성 순서를 따른다.
- ulong 스트림에는 어떤 enum의 비트든 발행할 수 있어, enum 형식 안전성이 없다.
- 성능은 측정하지 않았다.

### 값 조건은 When 경로로 나눈다

**선택**

값 동등성은 Where·ForFlags와 별도의 경로 연산 When으로 둔다. EventStream&lt;T&gt;와 EventPath&lt;T&gt;의 인스턴스 메서드는 같은 형식의 target을 받고 EventPath&lt;T&gt;를 반환한다. EventCondition의 값 조건도 When으로 통일하며 OnUpdated(target, callback)은 이 한 단계 조건을 사용한다.

- EqualityComparer&lt;T&gt;.Default로 비교하며 참조 형식과 Nullable&lt;T&gt;의 null도 유효한 target이다.
- 같은 부모마다 WhenNode 하나를 두고 동등한 target마다 내부 행 하나를 공유한다. 부모나 순서 그룹이 다르면 공유하지 않는다.
- null이 아닌 target은 EqualityComparer&lt;T&gt;.Default를 사용하는 사전으로, null target은 별도 필드로 찾는다. 등록과 발행에 같은 구조를 사용하고 발행 값에 해당하는 항목 하나만 방문한다. 값 형식의 null 검사는 박싱 없이 처리한다.
- 행은 생성 순서의 행 체인에도 두어 완료·오류·폐기를 target과 관계없이 전달한다. 다른 형제와의 순서는 WhenNode 생성 순서이며 Gate 우선 규칙을 유지한다. 사전에서 찾은 행도 연결 상태와 발행 시작 시점의 Registration을 검사한다.
- 등록 후 target의 Equals·GetHashCode 결과가 바뀌는 경우는 지원하지 않는다. ulong에서도 전체 값의 동등성이며 ForFlags의 공통 비트 판정과 별개의 노드이다.

**검토한 형태와 기각 이유**

| 검토한 형태 | 기각 이유 |
| --- | --- |
| Where 위의 비교 람다 | target이 같아도 노드를 공유하지 않아 값 기준 등록 중복 판정과 어긋난다. |
| 이름 Equal | 모든 객체가 가진 Equals(object)와 한 글자만 다르다. |
| `When(Func<T, bool>)` 오버로드 | Where와 기능이 겹치고 null 인수가 target과 조건 함수 중 어느 것인지 모호해진다. |
| object 매개변수 | 값 형식을 박싱하고 형식이 틀린 target도 컴파일된다. |
| FlagsNode 방식의 선형 순회 | Equals가 일관되면 값 하나는 항목 하나에만 같으므로 사전 분기를 선택했다. 두 방식의 성능은 측정하지 않았다. |

**대가**

- null 전용 항목을 제외하면 발행마다 해시를 계산한다.
- PathInfo에 target을 보관하므로 크기가 늘어난다. 추가한 뒤의 크기는 측정하지 않았다.
- 이름이 C#의 when 가드처럼 읽힐 수 있다.
- 발행 중 비교 예외가 나면 같은 위치의 WhenNode와 모든 target 행의 연결을 통지 없이 해제하고 ExceptionHandler.Report로 보고한다. 중첩된 When의 정리에서 실패한 비교가 다시 호출되지 않도록 사전을 먼저 비운다. 형제 경로는 계속 방문한다.
- 등록 중 비교 예외는 Subscribe 호출자에게 전파하고 이번 등록으로 새로 만든 빈 행과 노드는 정리한다. 아직 구독이 없던 연산자·Branch·Merge 스트림은 이 정리로 비면 폐기된다.
- 성능은 측정하지 않았고 Unity Mono·IL2CPP에서의 할당도 검증하지 않았다.

## 순서 그룹

### 순서는 별도 스트림이 아니라 경로 연산으로 정한다

- 선택: ForOrder(order)가 순서 그룹의 경로를 만든다. 같은 위치의 그룹은 OrderedNode 하나의 순서 값별 행으로 모인다. 등록은 정렬 색인으로 찾고 발행·종료는 순서 값으로 정렬된 행 체인을 따른다. 별도 그룹 Node는 만들지 않는다. 순서 없는 구독자는 같은 연결 위치의 모든 그룹보다 먼저 호출한다. EventHub는 순서 그룹 없이 리스너와 직접 Updated 구독을 하나의 루트와 그 아래 경로에 등록한다.
- 이전 형태: 순서를 타입 인수로 받는 별도 스트림 형식 OrderedEventStream이 그룹마다 경로를 따로 두었다. 이름을 더 구분되게 바꾸는 안도 검토했지만, Where가 외부 함수를 받는 것처럼 순서도 외부 값을 받는 경로 연산으로 내렸다.
- 검토한 형태: 그룹 노드가 자기 순서 값을 갖는 형태는 모든 노드가 순서 값을 갖게 되므로 기각했다. 일반 노드가 순서 사전을 함께 갖는 형태도 일반 노드의 역할을 흐리므로 OrderedNode로 분리했다.
- 장점: 별도 스트림 형식이 없고, 경로 중간에서도 그룹을 나눌 수 있다. 순서 사전은 순서가 필요한 위치에만 생긴다.
- 대가: 그룹 사이에는 같은 대리자라도 조건을 공유하지 않는다. 그룹 묶음과 순서 없는 Where·Debug·스트림 연결 사이는 생성 순서를 따르므로, 순서가 중요하면 모두 그룹 아래에 둔다. 열거형을 int로 바꿔 비교하므로 int 범위를 벗어나는 값은 쓸 수 없다.

## 실패 처리

### 실패한 부분만 정리하고 첫 예외를 돌려준다

- 선택: 콜백 실패는 그 구독만, Where 조건 실패는 그 행의 연결만, Debug 로그 실패는 그 Debug의 연결만 정리하고 ExceptionHandler.Report에 넘긴다. When 비교 실패는 같은 노드의 모든 행을 해제하며 TakeWhile·SkipWhile 조건 실패는 그 스트림을 폐기한다. 보고가 예외를 던져도 나머지를 계속 방문하고, 순회를 마친 뒤 첫 보고 예외를 값을 넣은 쪽에 전달한다. 스트림 사이의 연결은 이 예외 때문에 끊기지 않는다.
- 이전 형태: 프로토타입은 처리기가 없으면 실패한 구독만 해제하고 실패를 드러내지 않았다. 예외를 그래프 밖으로 바로 던지면 공급원이 그 연결을 끊어 그래프 전체가 끊길 수 있었다.
- 장점: 처리기가 없어도 값을 넣은 쪽이 실패를 안다. 한 구독의 실패가 형제와 다음 값으로 번지지 않는다.
- 대가: 한 값에서 여러 번 실패해도 밖으로는 첫 예외 하나만 나간다. 외부 Observable이 관찰자의 예외를 잡거나 구독을 끝내는 방식은 그 공급원의 계약을 따른다.
- 보완: 2026-11-09에 Take의 마지막 값 콜백과 다른 구독자의 완료 콜백이 모두 실패하면 완료 예외가 먼저 기록된 값 예외를 덮어쓰는 결함을 고쳤다. 지금은 완료 처리를 마친 뒤 그 실패를 기존 기록에 합쳐 첫 예외를 유지한다.

## 측정과 문서

### 벤치마크는 별도 실행 파일로 둔다

- 선택: 측정 도구는 테스트 폴더의 별도 실행 프로젝트이다. 비교 기준은 git 커밋으로 지정해 그 커밋의 소스를 꺼내 같은 시나리오로 빌드한다. 시나리오마다 프로세스를 새로 띄우고 코어와 우선순위를 고정한다. 결과 폴더는 버전 관리에서 제외한다.
- 이전 형태: 테스트 프로젝트 안에 벤치마크 클래스를 두고, 변경 전 소스 사본과 독립 호스트를 저장소 밖에서 따로 컴파일했다.
- 장점: 이전 빌드의 실행 파일을 저장소에 두지 않고도 버전별로 비교한다. 계층형 컴파일과 코어 배치가 시나리오 사이에 이어지지 않는다.
- 대가: 기준 커밋도 지금과 같은 공개 API를 가져야 빌드된다. 조건을 Filter로 받던 커밋과 비교할 때는 API별 실행기를 따로 두어야 했다. 같은 코드도 측정한 날에 따라 1.5배까지 달라지므로 같은 측정 안의 값만 비교한다.

### 문서는 성격에 따라 위치를 나눈다

- 선택: 벤치마크 문서는 성능이 설계의 중요한 기준이므로 설계 문서와 같은 폴더에 둔다. 상태·동작 표, 테스트 계획, 결과 기록은 컨벤션에 따라 테스트 코드 옆의 docs에 둔다. 다이어그램은 사용자가 직접 관리하고, 코드에서 만든 클래스 다이어그램은 두지 않는다.
- 장점: 설계를 읽는 사람이 비용 근거를 같은 자리에서 본다. 테스트 문서는 다루는 테스트 코드와 함께 옮겨진다.
- 대가: 벤치마크 문서는 테스트 문서 위치 규칙의 예외이다. 원본 측정 자료는 버전 관리에서 제외되어 문서에 적힌 경로가 다른 환경에는 없다.

## 보류 항목

- **조건이 수십 개인 부모의 구독 비용.** 대리자 비교와 해시 때문에 이전 구현보다 구독이 45–100% 느리다. 지금은 이 비용을 받아들이고 기준값 16을 유지한다.
- **상태 있는 노드의 공유.** 서로 다른 연산자 호출이라도 남은 횟수나 진행 상태가 같으면 노드를 공유하는 방식이다. 공유될 기회가 드물어 구현하지 않았다.
- **비트별 발행 색인.** 마스크 키의 등록 색인은 FlagsNode의 적응형 색인으로 반영했다. 발행에서 일부 비트의 행만 고르는 색인은 중복 방문과 생성 순서를 함께 해결해야 하므로 서로 다른 마스크가 많아질 때 검토할 항목으로 남긴다.
- **공유 진단.** 호출마다 새로 만드는 람다는 공유되지 않으므로, 그래프의 노드 수와 공유 상태를 사용자가 확인할 수단이 필요할 수 있다. 지금은 테스트용 내부 노드 수만 있다.

## 확인하지 못한 사항

- 지금 구조를 Unity Mono·IL2CPP에서 측정하지 않았다. 마지막 Unity 측정은 2026-11-04 본 구현 기준이다. 대리자 비교와 해시 비용이 런타임마다 어떻게 다른지도 모른다.
- Unity Mono·IL2CPP에는 동적 PGO가 없으므로, 순회 구조를 결정할 때 .NET에서 PGO를 끈 두 조건을 Unity에 더 가까운 조건으로 보았다. 이 대응은 Unity에서 측정해 확인하지 않았다.
- When의 성능과 target 필드가 추가된 PathInfo 크기는 측정하지 않았다. When의 Unity Mono·IL2CPP 할당도 검증하지 않았다.
- 실제 게임의 조건 통과율, 구독 교체 빈도, 프레임 시간 기록이 없다. 측정의 통과율과 교체 횟수는 통제한 입력값이다.
- 조건이 수천 개일 때의 발행 회귀가 캐시 미스, 프리페치, TLB 가운데 어느 요인에서 오는지 하드웨어 카운터로 확인하지 않았다.
- 최신 구조의 측정 범위는 [벤치마크](Benchmark.md)의 시나리오와 측정 방법 장을 따른다. 과거 측정으로 Unity의 할당이나 256단계 경로의 스택 여유를 보장하지 않는다.
