## 1. 구조 종류

세 구조는 측정에 쓰는 공개 API가 같다. 구독 경로를 그래프 안에 저장하는 방식과 방문하는 방식이 다르다. 같은 위치에 종류가 다른 조건이 섞이면 자식 OOP와 논리=물리 OOP의 방문 순서도 다르며, 표는 논리=물리 OOP의 순서를 따른다.

| 이름 | 커밋 | 저장 방식 | 방문 방식 |
| --- | --- | --- | --- |
| 자식 OOP | 5478bbd | 키 항목마다 노드를 만든다. Where는 조건마다 WhereNode를 두고, When·Flags·순서 그룹은 위치 노드 아래에 키마다 항목 노드를 둔다. 다음 단계 노드와 출구는 그 노드의 자식 목록에 들어간다. | 노드가 자식 목록을 따라 재귀로 방문한다. |
| 논리=물리 OOP | 7f9e1e2 (현재 제품) | 같은 위치마다 WhereNode·WhenNode·FlagsNode·OrderedNode를 종류별로 하나씩 둔다. 키는 노드 안의 행이며, 행은 자기 연결로 다음 단계 노드와 출구를 참조한다. 다음 노드는 행이나 앞 노드의 일부가 아닌 별도 객체이다. | 노드가 행을, 행의 연결이 다음 노드를 따라 재귀로 방문한다. |
| 표 | d818fe7 (채택하지 않음) | 논리 구조는 논리=물리 OOP와 같다. 노드·행·구독을 객체 대신 그래프가 소유한 표의 칸으로 저장하고 번호로 참조한다. | 그래프가 명시적 스택과 반복문으로 방문하므로 경로 깊이와 무관하게 호출 스택 깊이가 일정하다. |

Where(a)에 구독 하나, Where(a).Where(x)에 구독 하나, Where(b)에 구독 하나를 등록하면 두 OOP는 다음과 같다. 표는 논리=물리 OOP와 같은 모양을 표의 칸으로 저장한다.

자식 OOP는 조건마다 노드가 생기고, 다음 노드와 출구가 그 노드의 자식이 된다.

```text
Root
├─ WhereNode a
│   ├─ 출구
│   └─ WhereNode x
│       └─ 출구
└─ WhereNode b
    └─ 출구
```

논리=물리 OOP는 같은 위치의 조건이 WhereNode 하나의 행이 되고, 각 행의 연결이 출구와 다음 노드를 참조한다.

```text
Root ─ 연결
       └─ WhereNode
           ├─ 행 a ─ 연결
           │         ├─ 출구
           │         └─ WhereNode
           │             └─ 행 x ─ 연결
           │                       └─ 출구
           └─ 행 b ─ 연결
                     └─ 출구
```

## 2. 시나리오

모든 시나리오는 두 가지 구독 방식 중 하나를 쓴다. Individual은 구독자가 콜백 안에서 자기 조건을 검사하고, Pipeline은 구독자가 Where 조건을 공유한다. Individual도 각 구조의 루트 발행과 구독자 호출을 거치므로 구조 차이가 완전히 없는 대조군은 아니다.

```csharp
// Individual traversal: every subscriber is visited and checks its own condition.
stream.Subscribe(value => { if (condition(value)) Handle(value); });

// Pipeline: subscribers share a condition node.
stream.Where(condition).Subscribe(Handle);
```

조건은 서로 다른 메서드 16개로 만든다. 같은 람다만 쓰면 JIT가 호출 지점을 인라인해 Individual의 조건 비용이 사라지기 때문이다. 콜백은 카운터만 올리며, 라운드마다 기대한 호출 횟수와 같은지 검사한다.

| 계열 | 구성 | 측정 작업 | 시나리오 |
| --- | --- | --- | --- |
| A | 조건 16종을 구독자에게 고르게 나누고 한 조건만 통과시킨다. 구독자의 약 16분의 1이 받는다. | 발행 | Individual·Pipeline × 16, 64, 256, 1000, 1024명 |
| B | 구독자 64명, 조건 16종에서 통과 조건 수를 바꿔 8·32·60·64명이 받는다. Direct는 조건 없이 64명이 직접 구독한다. | 발행 | Individual·Pipeline × 8of64, 32of64, 60of64, 64of64, Direct-64of64 |
| C | 구독자 64명 중 4명이 받는다. Kinds2·Kinds16은 받는 4명이 조건 하나를 공유하고 나머지 60명이 1종·15종을 나눠 쓴다. Kinds64는 64명이 모두 다른 조건을 쓴다. | 발행 | Pipeline × Kinds2, Kinds16, Kinds64 |
| D | 구독자 64명, 조건 16종 앞에 공통 조건 하나를 둔다. Rejected는 공통 조건이 거짓이고, Accepted는 참이어서 4명이 받는다. | 발행 | Individual·Pipeline × Rejected, Accepted |
| E | 구독자 64명이 조건 16종을 쓰는 스트림에서 구독 하나를 추가하고 바로 해제한다. ExistingNode는 기존 조건, NewNode는 새 조건, MethodGroup은 호출마다 새 대리자가 되는 메서드 그룹, Branch·Take는 Take(1)과 Branch로 만든 스트림에 구독한다. | 구독과 해제 | Individual-Subscribe, Pipeline-ExistingNode, NewNode, MethodGroup, Branch, Take |
| F | 상위 스트림에 Branch, Take(int.MaxValue), TakeWhile(항상 참), Skip(0), SkipWhile(항상 거짓)으로 만든 스트림을 64명이 구독하고, 값은 상위에 넣는다. | 발행 | Branch, Take, TakeWhile, Skip, SkipWhile |
| K | 구독자 4명마다 조건 하나를 둔다. 1,000·1만·10만·100만 명이면 조건이 250·2,500·2만 5천·25만 개이며, 한 조건만 통과해 4명이 받는다. | 발행 | Individual·Pipeline × 1000, 1만, 10만, 100만 |
| L | 조건 16종에서 구독자의 16분의 1이 받는다. | 발행 | Individual·Pipeline × 1만, 10만, 100만 |
| R | 조건 16종에서 처음 4명만 통과 조건을 쓰고 나머지는 거부 조건 15종을 나눠 쓴다. 4명만 받는다. | 발행 | Individual·Pipeline × 1만, 10만, 100만 |
| T | L과 같은 그래프에서 구독 하나를 추가하고 바로 해제한다. | 구독과 해제 | Individual·Pipeline × 1만, 10만, 100만 |

시나리오는 모두 63개이다. 측정에 사용한 시나리오 정의는 커밋된 [Scenarios.cs](../../../../../tests/02-Core/02-E.3-EventStream/Benchmarks/Scenarios.cs)와 같다.

## 3. 측정 방법

### 3-1. 실행 절차

- 환경은 Intel Core i7-14650HX, Windows x64, .NET SDK 10.0.404, 런타임 10.0.15이다. 라이브러리는 netstandard2.1, 측정 실행 파일은 net10.0이며 모두 Release 빌드이다.
- 세 구조는 같은 측정 소스로 빌드했다. 라이브러리만 해당 커밋의 소스로 바꾸었다.
- 시나리오마다 새 프로세스를 띄운다. 프로세스를 논리 CPU 0·1(affinity 0x3)에 고정하고 우선순위를 High로 둔다. 이 CPU는 코어 종류가 섞여 있어 고정하지 않으면 같은 시나리오도 값이 크게 달라진다.
- 시나리오의 그래프를 만든 뒤 1.5초 예열하고 0.5초씩 다섯 라운드를 측정한다. 라운드마다 작업당 시간과 할당을 재고 다섯 라운드의 중앙값을 그 회차의 값으로 쓴다.
- 작업은 발행 한 번 또는 구독 하나의 추가와 해제 한 번이다. 시간은 ns/작업, 할당은 B/작업이다.
- 구성 시간은 그래프를 처음 만드는 데 걸린 ms이며 첫 실행의 JIT 비용을 포함한다. 보존 메모리는 구성 전후 GC.GetTotalMemory(true)의 차이이다.
- 조건마다 세 회차를 실행했다. 실행 사이의 변화가 한쪽에 몰리지 않도록 회차마다 조건의 순서와 구조의 순서를 한 칸씩 돌렸다. 모든 항목이 완료됐고 모든 라운드의 호출 횟수 검사를 통과했다. 한 항목은 결과 파일 저장 충돌로 한 번 다시 실행했다.

### 3-2. JIT 조건

| 조건 | 설정 | 의미 |
| --- | --- | --- |
| default | DOTNET_TieredCompilation=1, DOTNET_TieredPGO=1 | .NET의 기본값이다. 실행 중 수집한 정보로 다시 컴파일하는 동적 PGO가 켜진다. |
| pgo-off | DOTNET_TieredCompilation=1, DOTNET_TieredPGO=0 | 단계별 컴파일은 그대로 두고 동적 PGO만 끈다. |
| tiered-off | DOTNET_TieredCompilation=0, DOTNET_ReadyToRun=0 | 처음부터 최적화 컴파일하며, 미리 컴파일된 프레임워크 코드도 쓰지 않는다. |

프로세스마다 다른 DOTNET_·COMPlus_ 환경 변수를 모두 지운 뒤 위 값만 설정했다. Unity의 Mono·IL2CPP에는 동적 PGO가 없으므로 pgo-off와 tiered-off를 Unity에 더 가까운 조건으로 본다. 이 대응은 Unity에서 측정해 확인하지 않았다.

### 3-3. 집계와 판정

- 시간은 회차별 중앙값의 평균이다. 회차 편차는 '가장 큰 회차 값 / 가장 작은 회차 값 - 1'이다.
- default는 2·3회차, pgo-off와 tiered-off는 세 회차를 쓴다. 측정 시작 후 약 7분 30초 동안 모든 시나리오가 약 1.55배 느렸고, 이 구간이 default 1회차의 자식 OOP 앞부분에 걸렸다. 구조 코드 차이가 작은 Individual도 같은 배율로 느렸으므로 측정 환경의 상태로 보며 원인은 확인하지 않았다. 공정한 비교를 위해 default는 세 구조 모두 2·3회차만 쓴다. 검사 결과는 [시간순 블록 검사](../../../../../tests/02-Core/02-E.3-EventStream/Benchmarks/results/jit-conditions-20261112/startup-window-blocks.md)에 있다.
- 비교는 '비교 대상 / 기준 - 1'이다. 변화율의 절댓값이 10% 이상이고 양쪽 회차 편차보다 클 때만 빠름·느림으로 판정한다. 10% 미만은 '10% 미만', 그 밖은 '보류'로 둔다. 이 판정은 측정의 해석 기준이며 통계적 유의성 검정이 아니다.
- 원본은 [결과 폴더](../../../../../tests/02-Core/02-E.3-EventStream/Benchmarks/results/jit-conditions-20261112)에 있으며 버전 관리에서 제외한다. 원본에는 이 문서에서 다루지 않는 두 구현의 기록도 함께 있다.

표는 채택하지 않은 구조라 코드와 빌드를 지웠으며 다시 측정하지 않는다. 핵심 구현은 [순회 구현 발췌](Traversal%20Samples.md)에 있다. 이 문서의 표는 보존한 측정 원본에서 다음 명령으로 다시 생성한다. 스크립트는 버전 관리에서 제외되는 tests/bin에 있다.

```powershell
python tests/bin/BenchmarkDoc/build-tables.py --results tests/02-Core/02-E.3-EventStream/Benchmarks/results/jit-conditions-20261112 --template tests/bin/BenchmarkDoc/Benchmark.template.md --output "docs/02. UniEngine/02-Core/02-E.3-EventStream/docs/Benchmark.md"
```

## 4. 결과 비교

### 4-1. 판정 요약

63개 시나리오에서 '논리=물리 / 자식'은 자식 OOP 대비 논리=물리 OOP의 판정이고, '표 / 논리=물리'는 논리=물리 OOP 대비 표의 판정이다.

| 조건 | 비교 | 빠름 | 느림 | 10% 미만 | 보류 |
| --- | --- | --- | --- | --- | --- |
| default | 논리=물리 / 자식 | 3 | 8 | 49 | 3 |
| default | 표 / 논리=물리 | 4 | 53 | 5 | 1 |
| pgo-off | 논리=물리 / 자식 | 12 | 2 | 46 | 3 |
| pgo-off | 표 / 논리=물리 | 4 | 53 | 5 | 1 |
| tiered-off | 논리=물리 / 자식 | 9 | 2 | 50 | 2 |
| tiered-off | 표 / 논리=물리 | 4 | 52 | 6 | 1 |

- 동적 PGO를 켠 default에서 논리=물리 OOP는 자식 OOP보다 8개 시나리오에서 느리다. B32·B60·B64·C2·D-Rejected의 Pipeline이 21~41%, A-Pipeline-256·1000·1024가 15~22% 느리다. 빠른 시나리오는 A-Pipeline-16, C-Kinds64, E-NewNode의 3개이다.
- PGO를 끈 두 조건에서는 46~50개가 10% 미만이고 9~12개가 빠르며 느린 시나리오는 2개이다. 자식 OOP가 PGO를 끌 때 더 크게 느려지기 때문이다. 예를 들어 B-Pipeline-64of64는 자식 OOP가 +42%, 논리=물리 OOP가 +17% 느려진다.
- 표는 세 조건 모두 52~53개에서 논리=물리 OOP보다 느리다. 빠른 4개는 모두 10만 명 이상의 큰 그래프로, K-Pipeline-100000·1000000과 L·R의 Individual이다.
