# EventStream 작업 목록

그래프 기반 EventStream을 본 구현으로 옮길 때의 작업 목록이다. 아래 '현재 상태'는 작업 착수 당시의 상태이다. 최초 측정은 [프로토타입 평가](EventStreamPrototype.md), 항목별 결정·검증·실행 환경별 측정 결과는 [본 구현 보고서](EventStreamImplementation.md)에 있다.

## 본 작업 전 결정

### ES-01 처리기가 없을 때의 예외

**현재 상태.** 프로토타입은 ExceptionHandler.Report가 다시 던지는 예외를 전파 경계 안에서 모두 처리한다. 처리기를 등록하지 않으면 콜백이나 조건이 실패해도 그 구독만 해제되고 실패가 드러나지 않는다. 공급원으로 쓰는 기존 EventStream이 구독자의 예외를 받으면 그 구독을 해제하므로, 예외가 그래프 밖으로 나가면 그래프 전체가 끊기기 때문이다.

**결정할 사항.** 공급원이 자신을 소유한 EventStream의 예외로는 연결을 끊지 않게 할지, EventStream이 순회를 마친 뒤 첫 예외를 발행한 쪽에 다시 던지는 경로를 공급원 밖에 둘지 정한다. 기존 EventStream처럼 처리기가 없으면 발행한 쪽이 실패를 알 수 있어야 한다.

### ES-02 Take 카운터의 단위

**현재 상태.** 같은 Take 경로를 두 번 구독하면 구독마다 별도의 카운터를 갖는다.

**결정할 사항.** 카운터를 구독마다 둘지, Take 호출로 만든 경로마다 둘지 정한다. 이후 Skip·SkipWhile·TakeWhile에도 같은 기준을 적용한다.

### ES-03 Take 종료 시 새 구독의 완료 통지

**현재 상태.** Take가 끝나면 아래의 모든 구독에 완료를 통지한다. 같은 전파 중에 추가되어 아직 값을 받지 않은 구독도 완료 통지를 받는다.

**결정할 사항.** 이 동작을 허용할지, 다음 전파부터 반영하는 구독은 종료 통지에서도 제외할지 정한다.

### ES-04 경로 크기 정책

**현재 상태.** 경로 등록 시 Where를 찾는 비용은 같은 부모의 자식 수에 비례하고, 등록·전파·종료는 경로 깊이만큼 호출 스택을 사용한다.

**결정할 사항.** 자식이 많은 노드의 형제 검색 방식과 경로 최대 깊이를 정할지 결정한다.

### ES-05 구독 전 Branch의 회수

**현재 상태.** Branch는 생성 직후부터 부모에 연결되며, 한 번도 구독하지 않으면 부모 종료나 명시적 Dispose까지 남는다.

**결정할 사항.** 첫 구독 전에도 자동으로 회수할지, 첫 구독 시점에 부모와 연결할지 정한다.

## 추가 측정과 조사

### ES-06 측정 범위 확장

다음 조건에서 기존 구조와 프로토타입을 같은 방식으로 비교한다.

- 필터를 통과하는 구독자가 대부분인 경우
- 필터 없이 모든 구독자가 값을 받는 경우
- 공통 조건이 거짓일 때 하위 전체를 건너뛰는 경우
- Unity의 Mono·IL2CPP 런타임
- 실제 게임의 필터 통과율과 구독 변경 빈도

### ES-07 구독 교체 시 기존 EventStream의 성능 저하

**현재 상태.** 기존 공유 Where에 구독 추가와 해제를 반복하면 라운드가 지날수록 프레임 시간이 늘었다(19.2, 36.9, 40.3 µs/프레임). 프레임당 할당량은 일정했다.

**할 일.** 원인을 확인한다. 구독마다 새로 만드는 등록 콜백이 호출 목록 캐시의 약한 참조 표에 쌓이는 것을 의심한다. 공급원으로 남는 기존 EventStream에도 영향이 있으므로 본 작업과 별도로 확인한다.

## 본 작업

### ES-08 이름 정리

- 기존 EventStream을 EventSource로 바꾸고, 공급원 하나와 그래프를 소유하는 새 형식이 EventStream 이름을 쓴다.
- 기존 IEventStream 인터페이스를 공급원 계약으로 남길지, 새 EventStream의 계약으로 옮길지 정한다.
- 프로토타입 네임스페이스와 폴더는 본 구현으로 옮긴 뒤 삭제한다.

### ES-09 연산자의 경로 빌더 전환

- Skip·SkipWhile·TakeWhile·Debug를 그래프 노드로 구현한다.
- 조건을 받는 연산자는 Filter 객체만 받고, 람다를 직접 받는 오버로드는 제거한다.
- 기존 확장 메서드의 Append는 Branch로 대체할지 정한다.

### ES-10 Merge

- 외부 스트림을 합치는 Merge는 공급원으로 둔다. 프로토타입은 이 경우만 구현했다.
- 같은 그래프의 분기끼리 합치는 경우를 부모가 여럿인 노드로 지원할지 정한다. 지원하면 같은 값이 두 분기를 모두 통과할 때의 중복 전달과 All 완료 모드의 부모별 완료 집계를 함께 구현한다.

### ES-11 EventRouter 제거

- EventRouter, IEventRouter, EventRouterExtensions를 제거하고 비트마스크 판정은 Filter로 표현한다.
- FlagExtensions 문서처럼 EventRouter를 언급하는 문서를 정리한다.

### ES-12 순서 그룹

- OrderedEventStream의 실행 순서 그룹을 새 EventStream의 구독 기능으로 흡수한다. 그룹 사이에서는 조건을 공유하지 않는 것을 기본안으로 한다.
- OrderedEventStream을 사용하는 EventHub를 새 구조로 옮긴다.

### ES-13 테스트 이전

- 기존 EventStream 테스트를 새 구조의 규칙으로 다시 정의한다. 분기별 Enabled에 의존하는 UniTest U1·U2와 하위 직접 발행에 의존하는 계약 C5·조합 I1은 Branch 기준으로 바꾼다.
- 할당 회귀 테스트와 벤치마크를 본 구현 기준으로 옮긴다.

### ES-14 문서 갱신

- EventStream 모듈의 README·EventStream·인터페이스·확장·연산자·OrderedEventStream·Usage 문서를 EventSource와 EventStream 용어로 다시 쓴다.
- EventRouter 문서를 제거하고, UniEngine 다이어그램의 Event Router 상자를 유지할지 정한다.

## 보류 항목

- **상태 있는 노드의 공유.** Take·Skip은 남은 횟수가 같을 때, SkipWhile·TakeWhile은 같은 조건이고 진행 상태가 같을 때만 공유하는 방식이다. 실제로 공유될 기회가 드물어 첫 구현에서는 제외한다.
- **비트마스크 색인.** 비트마스크 판정을 별도 Filter 종류로 두고 비트별 색인으로 해당 노드만 방문하는 방식이다. 서로 다른 조건이 많아질 때 검토한다.
- **공유 진단.** Filter 객체를 그 자리에서 만들면 공유되지 않으므로, 그래프의 노드 수와 공유 상태를 확인할 진단 수단을 검토한다.

## 처리 결과

| 항목 | 반영 결과 |
| --- | --- |
| ES-01 | 그래프가 실패한 구독·경로를 정리하고 남은 순회를 마친 뒤 첫 보고 예외를 발행자에게 돌려준다. 공급원과 그래프의 연결은 유지한다. |
| ES-02·03 | 상태는 구독별이다. 종료 시점에 활성인 구독은 마지막 값 수신 여부와 무관하게 완료를 받는다. |
| ES-04·05 | 경로 깊이는 Branch를 포함해 최대 256단계이다. 형제가 많은 부모에는 Where 색인을 사용한다. Branch는 첫 구독 시 연결된다. |
| ES-06 | 60/64 통과·64명 직접 구독·공통 조건 탈락을 비교했다. 환경별 실행 범위는 본 구현 보고서에 구분했다. 설계 단계인 게임에는 실측 로그가 없다. |
| ES-07 | 일회성 등록 델리게이트의 중복 캐시를 대조 실험으로 분리하고 공급원의 등록 경로를 수정했다. |
| ES-08·09 | EventSource와 IEventSource가 공급원 계약을 맡고 EventStream과 EventPath가 그래프를 구성한다. Append의 독립 분기는 Branch로 표현한다. |
| ES-10 | 외부 공급원 Merge의 완료를 입력별로 집계한다. 그래프 내부에 여러 부모를 둔 합류는 이번 구현의 범위에서 제외했다. |
| ES-11·12 | 마스크는 Filter 조건으로 표현한다. EventRouter를 제거하고 EventHub를 EventStream의 순서 그룹으로 옮겼다. |
| ES-13·14 | 공급원·그래프 테스트, UniTest, 벤치마크를 이관했다. 사용 문서를 새 API 기준으로 갱신했다. UniEngine 다이어그램은 사용자가 직접 정리한다. |
