# EventStream 본 구현과 비교 측정

EventStreamTodo ES-01–14를 수행한 결과이다. 기존 EventStream은 EventSource로 이관했고, 정식 EventStream은 공급원 하나와 구독 그래프를 소유한다. EventHub도 같은 그래프의 순서 그룹으로 이전했다.

## 교체 판단

수정된 [프로토타입 평가](EventStreamPrototype.md)의 0.0848 µs는 1.5초 이상 예열한 뒤 측정한 공유 Filter 결과이다. 최초의 0.4253 µs와 예열 조건이 다르다. 이번에는 정식 구현과 변경 전 소스를 같은 실행기로 새로 측정했다.

.NET 10에서 64명 중 4명이 값을 받을 때 기존 공유 Where는 0.9497 µs, 정식 공유 Filter는 0.1088 µs였다. 실제 Unity Windows 플레이어에서도 같은 비교가 Mono 2.3016 → 0.2742 µs, IL2CPP 1.4726 → 0.2353 µs였다. 60명이 받거나 필터 없이 64명 모두가 받는 경우에도 두 플레이어 모두 정식 구현이 빨랐다. 반대로 공통 조건 하나에서 전부 탈락하면 기존 구조가 Mono에서 0.0101 µs, IL2CPP에서 0.0113 µs 빨랐다. **여러 필터를 공유하거나 많은 수신자가 값을 받는 조건에서 교체 효과를 확인했다.**

## 결정과 구현

| 항목 | 결정과 적용 범위 |
| --- | --- |
| ES-01 예외 | 실패한 콜백의 구독이나 실패한 조건의 하위를 먼저 해제하고 ExceptionHandler.Report를 호출한다. 보고기가 없거나 보고기 자체가 던지면 남은 형제까지 방문한 후 첫 예외를 발행자에게 다시 던진다. EventSource, 외부 EventStream, Branch, Merge 사이의 내부 관찰자는 이미 보고한 예외 때문에 연결을 잃거나 중복 보고하지 않는다. 임의의 외부 IObservable이 관찰자의 예외를 처리하는 방식은 그 공급원의 계약에 속한다. |
| ES-02·03 상태와 종료 | Take·Skip·SkipWhile·TakeWhile은 같은 경로를 재사용해도 구독마다 독립적으로 진행한다. 진행 중 추가한 구독은 현재 값을 받지 않는다. 종료 통지는 종료 시점의 활성 구독에 보낸다. 예를 들어 마지막 값의 Branch 콜백에서 추가한 구독은 값을 건너뛰고 완료만 받는다. |
| ES-04 경로 크기 | 형제가 8개 이상인 부모에서 Where를 등록할 때 Filter 참조 색인을 만들고, 자식이 4개 미만이면 회수한다. 전파는 계속 생성 순서를 따른다. 연산·그룹·Branch를 포함한 누적 깊이 256을 넘기는 경로는 구성 시 거부한다. |
| ES-05 Branch | 첫 구독까지 부모 쪽 노드·구독 핸들·소유 공급원을 만들지 않는다. 미구독 Branch도 부모의 폐기 상태를 반영하며, 첫 구독 이후에는 마지막 해제 시 스스로 폐기된다. |
| ES-08 이름과 계약 | EventSource와 IEventSource가 발행·연결·종료 정책을 맡는다. EventStream은 IObservable이고 외부 공급원을 소유하지 않는다. 프로토타입 네임스페이스와 폴더는 제거했다. |
| ES-09 연산자 | Where·Skip·SkipWhile·Take·TakeWhile·Debug는 경로 빌더이다. 조건은 Filter 객체로 받고 Where만 같은 부모에서 같은 참조일 때 공유한다. 독립적인 발행·Enabled 제어가 필요하면 루트나 경로에서 Branch를 사용한다. |
| ES-10 Merge | 외부 공급원의 값은 입력별로 전달하고 완료는 입력별로 한 번만 센다. 생성 중 동기 완료·오류와 뒤늦게 반환된 연결도 정리한다. 그래프 내부의 다중 부모 노드는 이번 구현에서 제외했다. 같은 값의 두 분기 통과를 한 번으로 셀지에 대한 사용 사례가 없고, 외부 발행 두 건을 합치면 값이 같아도 두 번 전달해야 하기 때문이다. |
| ES-11·12 라우팅과 순서 | 마스크 판정은 공유 Filter로 표현한다. EventRouter 계열을 제거했다. 열거형 순서 그룹을 가진 EventStream은 그룹별 경로를 분리하고 전체 그룹에 같은 전파 시점을 적용한다. EventHub는 연결 수신자를 먼저, 직접 Updated 구독자를 다음으로 호출한다. |
| ES-13·14 이전 | 공급원·그래프·그룹의 계약 테스트와 할당 검사를 현재 API에 맞췄다. UniTest U1·U2와 하위 직접 발행 사례를 Branch로 옮겼다. 모듈 사용 문서와 EventHub·FlagExtensions 참조를 갱신했다. UniEngine 다이어그램은 사용자가 직접 정리하므로 변경하지 않는다. |

## ES-06 측정 범위

측정일은 2026-11-04 KST이다. Windows x64 빌드 26300, Intel Core i7-14650HX, .NET SDK 10.0.403과 .NET 10.0.14를 사용했다. 각 시나리오는 10,000회씩 1.5초 이상 예열한 후 200,000회씩 세 라운드를 측정했다. 예열과 매 라운드에서 구독자별 호출 수를 확인했다.

비교 대상은 변경 전 main 8aeac42의 작업 트리와 본 구현이다. 당시 EventStream·Handle·OrderedEventStream에는 로컬 수정이 있었다. 양쪽은 같은 벤치마크 소스와 각 런타임의 동일한 독립 실행기로 실행했다. 기본 Tiered JIT 설정을 사용한 .NET 결과와 Unity 6000.3.18f1 Windows x64 비개발 플레이어에 포함된 Mono 런타임을 독립 호스트에 적재한 결과를 구분한다. 후자는 Unity 장면이나 프레임 루프를 포함하지 않는다.

### Unity Windows 플레이어

Unity 6000.3.18f1에 공식 Windows Build Support (IL2CPP)를 설치했다. 이전 소스와 정식 소스를 각각 Mono와 IL2CPP로 빌드하여 네 개의 비개발용 Windows x64 플레이어를 같은 빈 장면에서 실행했다. IL2CPP 네이티브 컴파일 구성은 Release이다. 네 플레이어 모두 종료 코드 0으로 완료됐고 모든 라운드의 구독자별 호출 수가 일치했다. Mono의 할당 대조군이 유효하지 않았고, 이 버전의 IL2CPP는 스레드별 할당량 API가 미구현이므로 플레이어 할당량은 미측정이다.

### 실제 게임

현재 설계 중인 시스템으로, 실제 게임의 플레이 로그나 지정 장면은 없다. 위의 필터 통과율과 구독 변경 횟수는 통제한 입력값이다. 실제 게임의 평균 통과율·교체 빈도나 프레임 시간을 이 표에서 추정하지 않는다.

## ES-07 공급원 성능 저하 조사

EventSource의 전신은 등록마다 새 래퍼 델리게이트를 만들고 원본 콜백 목록을 별도로 보관했다. 이 래퍼를 AdaptiveAction에 추가하면 이미 준비한 원본 목록과 별개로 호출 목록 캐시의 ConditionalWeakTable에도 래퍼 항목이 생겼다. 대조 실험에서는 원본 콜백의 캐시를 유지하고 일회성 래퍼 캐시 등록만 우회했다. 새 .NET 10 NUnit 프로세스에서 각각 H-C만 실행했고 강제 GC는 호출하지 않았다.

| 기존 소스 대조 조건 | 1·2·3회차 (µs/프레임) | 1·2·3회차 GC 정지 누적 (초/라운드) | 중앙 B/프레임 |
| --- | --- | --- | ---: |
| 래퍼 캐시 사용 | 28.4133 / 52.1449 / 68.2913 | 3.3260 / 7.3352 / 10.6785 | 8046.6414 |
| 래퍼 캐시 우회 | 10.0068 / 8.3781 / 8.5987 | 0.0320 / 0.0291 / 0.0291 | 6912 |

이 대조에서 래퍼 캐시 등록을 없애자 라운드가 갈수록 시간이 늘던 현상과 GC 정지 시간 증가가 함께 사라졌다. 최종 EventSource는 원본 콜백 목록을 준비한 등록에만 AddPrepared를 사용한다. 일반 AdaptiveAction 등록과 원시 콜백의 캐시는 유지한다. 최종 NUnit H-S도 4.6882 / 4.6999 / 4.6557 µs, 세 라운드 모두 6912 B/프레임이었다. 이 실험은 해당 부하에서 캐시 등록의 영향을 분리한 것이며 영구적인 메모리 누수를 입증하는 시험은 아니다.

## 검증과 재현

Release 빌드는 경고 0개, 오류 0개였다. 대상 테스트 119개와 일반 전체 테스트 673개가 모두 통과했다. 명시적 성능 벤치마크는 일반 테스트에서 제외하고 별도로 실행했다. 고정 구독의 첫 전파·반복 전파와 Take(1).Branch()의 마지막 값·완료·폐기는 .NET 할당 회귀 검사에서 각각 0 B였다. 대상 테스트 결과와 U1·U2의 검증 범위는 [UniTest 실행 기록](../../../../../tests/02-Core/02-E.3-EventStream/UniTest/03-Results.md)에 있다.

```powershell
dotnet build tests/GoldenHind.Tests.csproj -c Release
dotnet test tests/GoldenHind.Tests.csproj -c Release --no-build --filter '(FullyQualifiedName~BlackThunder.UniEngine.Tests.EventStream|FullyQualifiedName~BlackThunder.UniEngine.Tests.EventSource)&TestCategory!=Benchmark'
dotnet test tests/GoldenHind.Tests.csproj -c Release --no-build
dotnet test tests/GoldenHind.Tests.csproj -c Release --no-build --filter 'FullyQualifiedName=BlackThunder.UniEngine.Tests.EventStreamBenchmarks.ComparePropagationAndSubscriptionChurn' --logger 'console;verbosity=detailed'
```

위 NUnit 명령은 본 구현을 측정한다. 비교용 독립 호스트는 동일한 EventStreamBenchmarks.cs를 EVENTSTREAM_STANDALONE으로 컴파일해 ComparePropagationAndSubscriptionChurn을 호출한다. 변경 전 소스와 연결할 때만 EVENTSTREAM_LEGACY도 정의한다. 같은 측정 조건에서 이번 NUnit 실행의 E는 0.1022 µs였으며 비교 표에는 독립 호스트끼리의 값을 사용했다.

독립 호스트 프로젝트, 변경 전 소스 사본과 측정별 원시 로그는 저장소에 보관하지 않는다.
