# 그래프 기반 EventStream 프로토타입 평가

공급원 하나와 이벤트 그래프를 소유하는 새 EventStream이 기존 전파 구조를 대체할 수 있는지 측정한 결과와 본 작업 전에 정할 문제를 정리한다.

이 문서의 수치·파일 목록·실행 명령은 프로토타입 측정 당시의 기록이다. 정식 API와 후속 측정, 현재 실행 명령은 [본 구현 보고서](EventStreamImplementation.md)에 있다.

## 교체 판단

64명 중 4명에게만 값을 전달할 때, 같은 Filter를 공유하는 프로토타입 E의 전파 시간은 0.0848 µs였다. 기존 EventRouter A의 1.1692 µs보다 92.7% 짧고, 기존 Where를 공유한 C의 0.3682 µs보다 77.0% 짧다. 일치하는 4명만 기존 EventStream에 직접 구독한 기준값 D의 0.0821 µs와는 3.3% 차이이다.

Filter를 전혀 공유하지 않은 F도 0.2003 µs로 C보다 45.6% 짧았다. 공유하지 않아도 중간 스트림을 거치는 비용이 사라지기 때문이다. 매 프레임 구독 16개를 교체한 경우에도 프로토타입이 기존 공유 Where보다 시간은 77.6%, 할당량은 39.6% 줄었다.

**성능 기준으로는 교체 근거가 충분하다. 본 작업은 5절의 예외 정책과 Take 의미를 정한 뒤 진행한다.** 필터를 통과하는 구독자가 대부분인 경우, 필터 없이 모든 구독자가 값을 받는 경우, Unity의 Mono·IL2CPP 런타임은 측정하지 않았다.

## 측정 조건

- 측정일은 2026-11-04 KST이다. Intel Core i7-14650HX, Windows x64 빌드 26300, .NET SDK 10.0.403, .NET 런타임 10.0.14에서 측정했다. 라이브러리는 netstandard2.1, NUnit 테스트 호스트는 net10.0이며 모두 Release 빌드이다.
- 비교 기준은 main의 8aeac42와 측정 당시 작업 트리이다. 기존 EventStream과 Handle에는 작업 시작 전부터 로컬 변경이 있었다. A–D와 프로토타입의 공급원은 같은 빌드의 구현을 사용했다.
- 시나리오마다 10,000회 단위의 예열을 1.5초 이상 반복한 뒤, 200,000회씩 세 라운드를 실행했다. 한 라운드의 경과 시간을 전파 수 또는 프레임 수로 나누고 세 결과의 중앙값을 사용했다. 할당량은 같은 구간의 GC.GetAllocatedBytesForCurrentThread 차이로 계산했다.
- 예열을 호출 횟수가 아니라 시간으로 정한 이유는 단계별 컴파일이 일정 시간이 지난 뒤에 최적화 코드로 교체하기 때문이다. 처음 측정에서는 10,000회 고정 예열을 사용했고, 프로토타입 코드를 처음 실행하는 E가 최적화 전 구간에서 측정되어 중앙값 0.4253 µs로 보고되었다. 같은 조건으로 다시 실행했을 때도 E는 세 번째 라운드에서야 0.0844 µs로 내려갔다.
- 값은 1u로 고정하고 구독자 i의 대상은 `1u << (i % 16)`으로 정했다. D는 일치하는 4명만 등록했다. 예열과 각 측정 라운드가 끝날 때 구독자별 호출 횟수를 검증했다.

## 벤치마크 결과

### 구독이 고정된 경우

시간의 단위는 µs/전파이다.

| 시나리오 | 구성 | 1회차 | 2회차 | 3회차 | 중앙값 | B/전파 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| A | 기존 EventRouter, 대상 구독 64개 | 1.1692 | 1.1749 | 1.1376 | 1.1692 | 0 |
| B | 기존 Where를 구독자마다 생성, 64개 | 1.5749 | 1.5834 | 1.5604 | 1.5749 | 0 |
| C | 기존 Where 16개에 각각 4명 구독 | 0.3717 | 0.3682 | 0.3679 | 0.3682 | 0 |
| D | 일치하는 4명만 직접 구독 | 0.0821 | 0.0813 | 0.0830 | 0.0821 | 0 |
| E | 프로토타입, 정적 Filter 16개 공유 | 0.0860 | 0.0848 | 0.0843 | 0.0848 | 0 |
| F | 프로토타입, 서로 다른 Filter 64개 | 0.2083 | 0.2003 | 0.1955 | 0.2003 | 0 |
| G | 프로토타입, 항상 통과하는 공통 Filter 아래 16개 공유 | 0.0980 | 0.0960 | 0.0929 | 0.0960 | 0 |

E는 D와 비슷한 수준이다. 전파 비용이 전체 구독자 수가 아니라 서로 다른 조건의 수와 실제로 값을 받는 구독자 수를 따른다. G의 공통 조건은 모든 값을 통과시키므로, G와 E의 차이는 경로가 한 단계 깊어질 때의 비용이다. 공통 조건이 거짓일 때 하위 전체를 건너뛰어 얻는 절약량은 측정 대상 밖이다.

### 프레임마다 구독을 변경하는 경우

64개의 기본 구독을 유지하고 프레임마다 임시 구독 16개를 추가한 뒤 한 번 전파하고 모두 해제했다. 임시 구독의 대상은 '(프레임 번호 + 임시 구독 번호) % 16'으로 순환했다. 매 프레임 기본 구독 4명과 임시 구독 1명이 호출된다. C는 저장해 둔 Where에 구독하고, E는 매번 Where(filter).Subscribe를 호출했다.

| 시나리오 | 3라운드 (µs/프레임) | 중앙값 (µs/프레임) | B/프레임 |
| --- | --- | ---: | ---: |
| H-C · 기존 공유 Where | 19.2354 / 36.9334 / 40.3273 | 36.9334 | 8046.6414 |
| H-E · 프로토타입 공유 Filter | 8.2674 / 8.2921 / 7.0310 | 8.2674 | 4864.0000 |

H-E는 경로와 구독 핸들을 새로 만드는 프레임마다 할당이 발생한다. 고정 구독의 0 B와 구별해 해석해야 한다. H-C는 라운드가 지날수록 프레임 시간이 늘었고, 이 증가는 6절에서 다룬다. 중앙값 비교는 이 증가를 포함한 값이다.

## 구현과 명세 해석

- 공급원 하나에 그래프를 한 번 연결한다. 구독 시 같은 부모 아래 같은 Filter 객체가 있으면 Where 노드를 재사용한다. Filter.Name은 공유 판정에 쓰지 않는다.
- EventPath는 명세가 허용한 대안인 불변 클래스로 구현했다. 각 연산이 이전 경로를 가리키므로 긴 경로의 앞부분을 복사하지 않고 여러 경로를 만들 수 있다. 경로 객체는 등록 시점의 비용으로 H-E에 포함된다. 요청된 공개 API 이외의 멤버를 추가하거나 기존 형식의 internal 멤버를 직접 사용할 필요는 없었다.
- 부모가 가진 생성 순서대로 깊이 우선 순회한다. 전파를 시작할 때 기록한 마지막 등록 번호 이후의 노드와 구독은 건너뛴다. 해제한 항목은 즉시 분리하되, 진행 중인 순회가 다음 형제로 갈 수 있도록 다음 항목으로의 연결을 유지한다. 마지막 구독을 제거하면 빈 조상도 바로 정리한다.
- Branch는 별도 공급원과 그래프를 소유한다. 부모의 종료는 Branch 그래프에 전달하고 소유한 공급원을 폐기한다. Take가 Branch를 완료시키는 마지막 전파도 할당 없이 처리한다.
- 외부 공급원의 Enabled 설정과 직접 발행은 InvalidOperationException으로 거부한다. 조회는 기존 IEventStream이면 그 Enabled를 따르고, 일반 IObservable이면 연결된 동안 true이다. Merge의 상위 완료는 기존 CompletionMode.All을 따른다.

## 본 작업 전에 정할 문제

이 절과 6절의 항목, 본 작업의 진행은 [EventStream 작업 목록](EventStreamTodo.md)에서 관리한다.

### 처리기가 없을 때의 예외

ExceptionHandler.Report는 처리기가 등록되지 않았으면 원래 예외를 다시 던진다. 프로토타입은 Report가 던지는 예외를 전파 경계 안에서 모두 처리하므로, 기본 설정에서는 콜백이나 조건이 실패해도 그 구독만 해제되고 실패가 어디에도 드러나지 않는다. 기존 EventStream은 이 예외를 발행한 쪽까지 전달한다.

이렇게 구현한 원인은 공급원 구조에 있다. 공급원으로 쓰는 기존 EventStream은 구독자가 예외를 던지면 그 구독을 해제한다. 따라서 예외가 그래프 밖으로 나가면 그래프 전체가 공급원에서 끊긴다. 본 작업에서는 다음 중 하나를 정한다.

- 공급원이 자신을 소유한 EventStream의 예외로는 연결을 끊지 않는다.
- EventStream이 순회를 마친 뒤 첫 예외를 발행한 쪽에 다시 던지는 경로를 공급원의 구독 처리 밖에 둔다.

### Take 경로의 재사용

Take 노드는 공유하지 않으며, 같은 EventPath를 두 번 구독해도 구독마다 별도의 카운터를 갖는다. 예를 들어 stream.Take(2)로 만든 경로 하나에 a와 b를 구독하면 a와 b는 횟수를 따로 센다. 같은 Take 호출로 만든 경로라면 횟수를 공유한다고 기대할 수 있으므로, 카운터의 단위를 구독으로 할지 Take 호출로 할지 정한다.

### Take 종료 시 새 구독의 완료 통지

Take가 끝나면 그 아래의 모든 구독에 완료를 통지한다. 같은 전파 중에 추가되어 아직 값을 받지 않은 구독도 완료 통지를 받는다. 이 동작을 허용할지 정한다.

### 경로 크기와 Branch 회수

- 경로 등록 시 Where를 찾는 비용은 같은 부모의 자식 수에 비례한다. 등록·전파·종료에는 경로 깊이만큼 호출 스택을 사용한다. 자식 수나 깊이가 매우 큰 경로를 지원하려면 형제 노드 검색이나 최대 깊이 정책을 별도로 정한다.
- Branch는 생성 직후부터 부모에 연결된다. 한 번도 구독하지 않은 Branch는 부모 종료 또는 명시적 Dispose까지 남는다. 첫 구독 전에도 자동 회수가 필요한지 정한다.

### 측정 범위 밖의 조건

이 측정은 동기식 단일 스레드에서 64명이 한 비트 값에 반응하는 경우를 다룬다. 필터를 통과하는 구독자가 대부분인 경우, 필터 없이 모든 구독자가 값을 받는 경우, 여러 스레드에서 발행하거나 구독을 변경하는 경우, Unity의 Mono·IL2CPP 런타임은 측정하지 않았다. 채택 시점에는 실제 게임의 필터 통과율과 구독 변경 빈도로 같은 비교를 한다.

## 기존 모듈에서 발견한 문제

H-C에서 기존 공유 Where에 구독 추가와 해제를 반복하면 라운드가 지날수록 프레임 시간이 늘었다. 이번 측정은 19.2354, 36.9334, 40.3273 µs였고, 1만 회 고정 예열을 쓴 처음 측정은 14.6294, 22.3190, 39.6364 µs였다. 프레임당 할당량은 일정했다.

이 증가는 프로토타입과 관계없이 현재 EventStream에서 나타난다. 원인은 확인하지 않았다. 구독마다 새로 만드는 등록 콜백이 호출 목록 캐시의 약한 참조 표에 쌓이는 것을 원인으로 의심하며, 별도로 조사한다.

## 검증과 재현

Release 빌드는 경고 0개, 오류 0개였다. 새 테스트 31개가 독립 실행에서 모두 통과했고, 이를 포함한 일반 전체 테스트 688개도 통과했다. 명시적 벤치마크 1개는 일반 실행에서 제외되고, 별도 실행에서 통과했다.

할당 회귀 테스트는 별도 인스턴스를 예열한 뒤 새 인스턴스의 첫 전파와 이후 10,000회 전파를 측정한다. 조건 통과·탈락, 비활성, Take(1).Branch()의 마지막 값 전달·완료·폐기 모두 첫 전파와 반복 구간이 각각 0 B였다.

