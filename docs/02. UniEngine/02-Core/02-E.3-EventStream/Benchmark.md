# EventStream 벤치마크

구독자가 각자 조건을 검사하는 개별 순회 방식과 구독자가 조건 노드를 공유하는 파이프라인 방식의 비용을 비교한다.

## 목차

- 결론
- 측정 방식
- 구독자 수
- 값을 받는 구독자 비율
- 조건 공유 정도
- 공통 조건
- 연산자 스트림
- 구독과 해제
- 대규모 구독
- Where 색인 전환
- 발행 회귀 재조사
- 키 행 구조 비교
- 배열 순회 임시 구현 비교

## 결론

- 구독자가 많고 값을 받는 구독자가 적을수록 파이프라인이 유리하다. 64명 중 4명이 받으면 3.0배, 1024명 중 64명이 받으면 17.9배 빠르다.
- 구독자가 16명 정도면 이점이 없다.
- 구독자 대부분이 값을 받으면 파이프라인이 12–19% 느리다. 통과한 Where마다 노드와 출구를 더 거치기 때문이다. 이때 가장 빠른 것은 Where 없는 직접 구독이다.
- 조건을 공유하지 않으면 파이프라인의 이점이 사라진다.
- 공통 조건이 거짓이면 하위 전체를 건너뛰어 33.2배 빠르다.
- 구독과 해제는 파이프라인이 더 비싸다. Take와 Branch는 호출할 때마다 스트림을 만들어 개별 순회의 약 5배 시간과 약 4.7배 할당이 든다.
- 파이프라인의 전파 비용은 전체 구독자 수가 아니라 조건 수와 값을 받는 구독자 수를 따른다. 100만 명 중 4명이 받으면 개별 순회는 20.6 ms, 파이프라인은 100 ns 미만이다.
- 조건 수가 구독자 수와 함께 늘어나면 파이프라인의 비용도 함께 늘어난다. 구독자 100만 명, 조건 25만 개에서 6.33 ms이다. 전파는 조건을 하나씩 평가하기 때문이다.

따라서 파이프라인은 많은 구독자가 일부 값만 받는 고빈도 이벤트에 맞다. 조건의 종류는 구독자 수와 무관하게 적게 유지하고, 모두가 받는 이벤트는 스트림에 직접 구독한다.

## 측정 방식

같은 EventStream에서 구독 방식만 다르게 측정한다. 구독 해제와 실패 처리 같은 공통 비용이 양쪽에 같이 들어가므로 차이는 구조에서 나온다.

```csharp
// Individual traversal: every subscriber is visited and checks its own condition.
stream.Subscribe(value => { if (condition(value)) Handle(value); });

// Pipeline: subscribers share a condition node.
stream.Where(condition).Subscribe(Handle);
```

- 측정일은 2026-11-06이다. Intel Core i7-14650HX, Windows x64 빌드 26300, .NET SDK 10.0.403, .NET 런타임 10.0.14를 사용했다. 라이브러리는 netstandard2.1, 실행기는 net10.0이며 모두 Release 빌드이다.
- 시나리오마다 별도 프로세스로 실행했다. 프로세스를 물리 코어 하나에 고정하고 우선순위를 높였다. 이 CPU는 코어 종류가 섞여 있어 고정하지 않으면 같은 시나리오도 값이 크게 달라진다.
- 조건은 서로 다른 메서드 16개로 만든다. 같은 람다만 쓰면 JIT가 호출 지점을 인라인해 개별 순회의 조건 비용을 지워 버려, 실제보다 개별 순회가 유리하게 측정된다.
- 1.5초 예열한 뒤 0.5초씩 다섯 라운드를 측정해 중앙값을 구하고, 전체를 두 번 실행한 평균을 표에 적었다. 콜백은 카운터만 올리며 라운드마다 호출 횟수를 검증했다.
- 두 실행의 차이는 대부분 10% 이내이고, 가장 큰 경우는 14%이다. 10%보다 작은 차이는 구조의 차이로 해석하지 않는다.
- 같은 코드의 절댓값이 측정한 날에 따라 1.5배까지 달랐다. 값은 같은 측정 안에서만 비교한다.
- 아래 기존 수치는 연산자 노드를 EventGraph에 두던 구현에서 측정했다. 이후 연산자 노드의 위치와 순서 그룹의 구조를 바꾸고 Where 색인을 제거했다. 2026-11-08에 조건이 많은 부모에만 색인을 만드는 방식으로 변경한 비교는 마지막의 'Where 색인 전환'에 따로 기록한다.
- 측정 코드와 실행 방법은 [벤치마크 도구](../../../../tests/02-Core/02-E.3-EventStream/Benchmarks/README.md)에 있다. 고정된 구독의 전파 할당은 모든 시나리오에서 0 B였다.

## 구독자 수

조건 16종을 구독자에게 고르게 나누고, 그중 한 조건만 값을 통과시킨다. 구독자의 16분의 1이 값을 받는다.

| 구독자 | 값을 받는 구독자 | 개별 순회 (ns/전파) | 파이프라인 (ns/전파) | 배율 |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 1 | 76 | 85 | 0.9 |
| 64 | 4 | 278 | 94 | 3.0 |
| 256 | 16 | 1413 | 133 | 10.6 |
| 1024 | 64 | 5740 | 320 | 17.9 |

개별 순회는 전체 구독자 수에 비례해 늘어난다. 파이프라인은 조건 수와 값을 받는 구독자 수를 따른다.

## 값을 받는 구독자 비율

구독자 64명, 조건 16종에서 조건을 통과하는 비율을 바꾼다.

| 값을 받는 구독자 | 개별 순회 (ns/전파) | 파이프라인 (ns/전파) | 배율 |
| ---: | ---: | ---: | ---: |
| 8 | 270 | 114 | 2.4 |
| 32 | 275 | 208 | 1.3 |
| 60 | 268 | 299 | 0.9 |
| 64 | 277 | 330 | 0.8 |

개별 순회는 받는 구독자 수와 거의 관계가 없다. 파이프라인은 값을 받는 구독자가 늘수록 노드와 구독을 더 많이 방문한다. 조건 없이 64명이 직접 구독하면 186 ns/전파이다. 이 값과 비교하면 통과한 Where 노드와 그 출구에 약 9 ns가 든다.

## 조건 공유 정도

구독자 64명 중 항상 4명이 값을 받게 두고, 나머지 60명이 나눠 쓰는 조건 수를 바꾼다. 같은 조건에서 개별 순회는 278 ns/전파이다.

| 조건 수 | 파이프라인 (ns/전파) |
| ---: | ---: |
| 2 | 31 |
| 16 | 92 |
| 64 (공유 없음) | 348 |

비용은 서로 다른 조건의 수를 따른다. 같은 대리자를 재사용하지 않으면 개별 순회보다 느려진다.

## 공통 조건

구독자 64명, 조건 16종 앞에 공통 조건 하나를 둔다.

| 공통 조건 | 개별 순회 (ns/전파) | 파이프라인 (ns/전파) | 배율 |
| --- | ---: | ---: | ---: |
| 거짓 | 252 | 7.6 | 33.2 |
| 참 | 327 | 97 | 3.4 |

개별 순회는 구독자마다 공통 조건을 평가한다. 파이프라인은 공유된 조건을 한 번 평가하고, 거짓이면 하위를 모두 건너뛴다.

## 연산자 스트림

구독자 64명이 연산자가 만든 스트림을 구독하고, 값은 상위 스트림에 넣는다.

| 구독 대상 | ns/전파 |
| --- | ---: |
| 상위 스트림 직접 구독 | 186 |
| Branch | 217 |
| Skip | 218 |
| TakeWhile | 224 |
| Take | 238 |
| SkipWhile | 241 |

연산자 스트림을 하나 거치면 약 30–55 ns가 더 든다. 상위 그래프의 연결, InputGate, 스트림의 검사를 지나기 때문이다. 상태 있는 연산자의 입구 노드는 Branch에 호출 한 번만 더한다.

## 구독과 해제

구독자 64명이 있는 스트림에서 구독 하나를 추가하고 해제하는 비용이다.

| 방식 | ns/회 | B/회 |
| --- | ---: | ---: |
| 개별 순회 | 67 | 304 |
| 파이프라인, 이미 있는 Where | 88 | 368 |
| 파이프라인, 새 Where 노드 | 169 | 528 |
| 파이프라인, 메서드 그룹을 직접 전달 | 178 | 528 |
| Branch | 318 | 1400 |
| Take | 327 | 1416 |

파이프라인은 구독할 때 경로를 찾고 노드를 관리하는 비용이 더 든다. 새 Where는 Where 노드와 출구를 함께 만든다. 메서드 그룹을 직접 넘기면 호출마다 대리자를 새로 만들므로, 자주 구독하는 코드는 대리자를 필드에 저장해 넘긴다. Take와 Branch는 스트림과 그래프를 새로 만든다. 고정된 구독에서는 문제가 되지 않지만, 매 프레임 Take(1)을 많이 만드는 코드는 이 할당을 고려한다.

## 대규모 구독

구독자를 1만, 10만, 100만 명으로 늘린다. 프로세스 분리, 코어 고정, 서로 다른 조건, 두 번 실행한 평균은 앞의 측정과 같다. 작업 시간을 재기 어려운 짧은 전파는 묶어서 측정했다.

참고로 초당 60프레임의 한 프레임은 16.7 ms이다.

### 값을 받는 비율이 일정한 경우

조건 16종에서 구독자의 16분의 1이 값을 받는다.

| 구독자 | 값을 받는 구독자 | 개별 순회 | 파이프라인 | 배율 |
| ---: | ---: | ---: | ---: | ---: |
| 1만 | 625 | 103.5 µs | 3.94 µs | 26.3 |
| 10만 | 6,250 | 1,705 µs | 105.0 µs | 16.2 |
| 100만 | 62,500 | 20.4 ms | 1.91 ms | 10.7 |

구독자가 100만 명이면 개별 순회는 이벤트 하나에 한 프레임을 넘게 쓴다. 양쪽 모두 구독자가 늘수록 한 명당 비용이 커진다. 개별 순회는 10.3 ns에서 20.4 ns로, 파이프라인은 값을 받는 구독자 한 명당 6.3 ns에서 30.5 ns로 늘어난다. 방문하는 데이터가 CPU 캐시를 벗어나기 때문으로 보이며, 원인을 따로 분리해 측정하지는 않았다.

### 소수만 받는 경우

조건 16종에서 구독자 수와 관계없이 4명만 값을 받는다.

| 구독자 | 개별 순회 | 파이프라인 |
| ---: | ---: | ---: |
| 1만 | 100.9 µs | 91 ns |
| 10만 | 1,712 µs | 96 ns |
| 100만 | 20.6 ms | 91 ns |

파이프라인의 비용은 구독자 수와 관계없이 거의 일정하다.

### 조건이 구독자와 함께 늘어나는 경우

구독자 4명마다 조건 하나를 두고, 그중 한 조건만 통과시켜 4명이 값을 받는다.

| 구독자 | 조건 수 | 개별 순회 | 파이프라인 | 배율 |
| ---: | ---: | ---: | ---: | ---: |
| 1만 | 2,500 | 103.0 µs | 11.7 µs | 8.8 |
| 10만 | 25,000 | 1,964 µs | 288 µs | 6.8 |
| 100만 | 250,000 | 23.6 ms | 6.33 ms | 3.7 |

전파는 부모의 조건을 모두 평가하므로 비용이 조건 수에 비례한다. 위 측정에서는 값을 받는 구독자가 4명뿐이어도 조건 25만 개를 평가하는 데 6.33 ms가 들었다. 현재는 조건이 많은 부모의 등록 검색에 해시 색인을 사용하지만, 발행 때 조건을 하나씩 평가하는 구조는 같다.

객체마다 조건을 만드는 구조에서는 조건을 늘리는 대신 객체마다 스트림을 두는 편이 낫다.

### 구독과 해제, 메모리

조건 16종의 스트림에서 구독 하나를 추가하고 해제하는 비용과, 구독 전체를 등록하는 비용이다.

| 구독자 | 구독·해제 1회, 개별 순회 | 구독·해제 1회, 파이프라인 | 전체 등록, 개별 순회 | 전체 등록, 파이프라인 |
| ---: | ---: | ---: | ---: | ---: |
| 1만 | 74 ns | 95 ns | 17 ms | 21 ms |
| 10만 | 83 ns | 103 ns | 49 ms | 55 ms |
| 100만 | 83 ns | 109 ns | 531 ms | 559 ms |

구독과 해제의 비용은 스트림이 커져도 거의 늘지 않는다. 전체 등록은 구독자 수에 비례한다.

구독자 한 명당 메모리는 개별 순회가 약 390 B, 파이프라인이 약 300 B이다. 개별 순회는 구독마다 조건을 담은 콜백을 따로 만들기 때문이다. 100만 명이면 약 300–390 MB이다. 구독자 4명마다 조건을 둔 구성의 파이프라인은 약 375 B이다.

## Where 색인 전환

2026-11-08에 색인 없이 형제를 검색하던 작업 트리와 조건 수에 따라 색인을 만드는 구현을 비교했다. 이 절의 기준은 앞선 리팩터링의 기준 커밋 cb62332가 아니라, 이번 변경 직전의 선형 검색 구현이다.

같은 부모 아래 서로 다른 Where 조건이 16개 이하이면 선형 검색을 유지하고, 17번째 조건을 등록할 때 해시 색인을 만든다. 색인은 그래프에서 부모별로 관리하므로 WhereNode의 크기와 필드 위치는 바뀌지 않는다. 조건 수가 줄어도 색인을 유지하며, 마지막 Where 조건이 제거되면 해제한다.

### 임계값 선택

임계값 8·16·32와 선형 검색을 별도 프로세스에서 두 번 교차 실행했다. 이 예비 비교는 0.5초 예열과 0.2초씩 다섯 라운드를 사용했으며, 표는 실행별 중앙값의 평균이다. 기존 조건은 같은 대리자를 사용하고, 새 조건은 등록 후 해제하여 다음 작업에서도 새 노드가 필요하도록 했다.

| 등록·해제 시나리오 | 선형 검색 | 임계값 8 | 임계값 16 | 임계값 32 |
| --- | ---: | ---: | ---: | ---: |
| 조건 16개, 첫 조건 재사용 | 57.3 ns | 68.4 ns | 57.6 ns | 53.4 ns |
| 조건 16개, 조건을 번갈아 재사용 | 73.4 ns | 76.8 ns | 79.2 ns | 77.8 ns |
| 조건 32개, 조건을 번갈아 재사용 | 93.1 ns | 69.1 ns | 70.9 ns | 98.3 ns |
| 기존 조건 8개, 새 조건 등록·해제 | 114.8 ns | 144.3 ns | 121.5 ns | 114.6 ns |

8은 작은 부모에서 색인을 너무 일찍 만들어 비용이 늘었고, 32는 조건 17–32개의 검색 개선을 늦췄다. 16을 선택하되 모든 검색 패턴에 가장 빠른 값이라고 해석하지 않는다. 예비 구현에서 임계값을 고른 뒤, 색인이 없는 경우에는 추가·제거 과정의 노드 형식 검사도 건너뛰도록 정리했다. 다음 표는 이 최종 코드의 검증이다.

### 최종 코드 비교

기존 벤치의 1.5초 예열과 0.5초씩 다섯 라운드를 사용했다. 프로세스 친화도는 0x3, 우선순위는 High이며, 두 번째 실행에서는 기준과 현재의 순서를 바꿨다. 시간은 실행별 중앙값의 평균이다.

### 호출과 형제 순회 분리

현재 구현을 바탕으로 다음 진단용 변형을 만들었다. Where 노드의 필드와 조건 대리자는 같은 구조를 유지했다.

- 직접 호출 변형은 부모가 WhereNode를 확인한 뒤 비가상 메서드를 호출한다. 기존 try/catch와 실패 처리는 유지했다. JIT 출력에서 Where의 직접 호출과 대리자 호출이 실제로 남는 것을 확인했다.
- 연결 리스트 대조군과 참조 배열 변형은 둘 다 전용 루트를 사용하고, 첫 예열 발행에서 같은 자식 참조 배열을 생성한다. 대조군은 기존 Next를 따라가고, 배열 변형은 그 배열을 순회한다. 따라서 추가 루트 형식과 배열 준비 비용을 두 변형에 맞췄다. 각 자식의 Parent·Registration 검사와 가상 Visit 호출은 유지했다.

## 배열 순회 임시 구현 비교

실험 코드와 추가 검증은 experiment/array-children의 커밋 cab9d8e1906a4b94742ef59ec15e18ac2f61c6b9에 보관한다. main에는 측정 기록만 반영하며 제품은 키 행의 체인 순회를 유지한다.

1단계 키 행 구조의 체인 순회와 참조 배열 순회를 비교하는 실험이다. 기준 커밋은 `7f9e1e21f833f3d762b3f96e70a3bf93cbb4fe8f`이고 실험 브랜치는 `experiment/array-children`이다. 실험 코드는 이 브랜치에 보관하며 main에 병합하지 않는다. 최종 측정 기록만 main에도 반영한다.

### 임시 구현의 범위

- Connection의 자식 체인과 WhereNode·FlagsNode의 행 체인만 `Slots<TItem>` 참조 배열로 바꾼다. When·OrderedNode의 행 체인과 Gate의 구독 체인은 유지한다. Where·Flags의 등록 검색 색인과 키 공유 규칙도 유지한다.
- 배열은 용량 1에서 시작해 필요할 때 두 배로 늘어난다. 새 항목은 항상 논리적 끝에 추가한다. 순회는 배열을 지역 변수에 붙잡지 않고 저장 필드의 인덱서를 매번 읽으므로 순회 중 배열이 커져도 현재 저장소를 참조한다. Registration 검사는 추가된 행·구독의 이번 발행 수신을 막는다.
- 각 항목은 자기 Slot 번호를 가진다. 제거는 이 번호의 칸을 null로 만들고 번호를 무효화하는 O(1) 작업이다. 진행 중인 순회가 있을 때는 다른 항목을 이동하지 않는다.
- 배열마다 진행 중인 순회 수를 Enter·Exit로 센다. Visit과 VisitEnd의 중첩도 포함하며, 가장 바깥 순회가 끝나면 남은 항목의 순서를 보존해 빈 칸을 당기고 이동한 항목의 Slot을 함께 갱신한다.
- 순회 없는 등록·해제 반복에서는 추가 시 배열이 가득 찼을 때만 빈 칸을 당긴 뒤 끝에 추가한다. 순회가 없고 모든 칸이 비면 경계값만 O(1)로 초기화한다. 따라서 제거 자체가 배열 전체를 이동하는 작업으로 바뀌지는 않는다.
- 공유 구독 Gate도 배열 끝에 추가하지만 별도 참조로 자식보다 먼저 방문한다. Gate 우선, 자식 생성 순서, 행 순서, 즉시 제거와 다음 발행부터 추가하는 계약을 유지한다.

- K-Pipeline-10000과 K-Pipeline-100000의 발행은 각각 -36.6%, -16.2%이다. 키 행을 2,500개·25,000개 방문하는 두 규모에서 배열이 빨랐으며 두 회차 모두 같은 방향이다. 체인·배열의 회차 편차는 1만 구독에서 약 3%·7%, 10만 구독에서 2%·1%로 관측된 차이보다 작다.
