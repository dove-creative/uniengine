## 키 행 OOP와 최초 OOP 소규모 재비교

2026-11-12에 표 방식의 채택을 중단하고 main의 키 행 OOP를 작업 기준으로 삼았다. 이후 JIT 조건별 다섯 구조 재비교를 거쳐 그래프 구조를 키 행 OOP로 확정했다. 최초 OOP 5478bbd와 main 53cc9e1을 비교했으며 양쪽 모두 객체 참조와 관리 호출 스택의 재귀 순회이다. main의 src 트리는 1단계 제품 커밋 7f9e1e2와 같고 사용자 WhereNode 줄바꿈 변경을 보존했다. 제품 코드·테스트·순서 계약은 이번에 수정하지 않았다.

키 행 측정용 Release 빌드는 성공했다. NuGet 취약성 조회 연결 실패 경고 NU1900 네 건과 오류 0건이며 최초 OOP는 앞선 측정의 Release 바이너리를 해시 확인 후 재사용했다. 기능 테스트는 다시 실행하지 않았고 아래의 기존 전체 1,059 통과·실패 0·건너뜀 0 기록을 참조한다.

1,000개 이하 대표 14개 시나리오를 양쪽 각각 두 번 실행한 56개 기록과 K 추가 세 쌍의 6개 기록이 모두 정상 종료했다. 모든 측정 라운드에서 기대 수신 횟수를 확인했다. 고정 구독 발행 54개 기록은 모두 0 B이며 E의 등록·해제 8개 기록은 별도이다. 조건 64종은 키 행이 13.12% 빨랐고 공통 조건 통과는 10.04% 느렸다. 11개 항목은 10% 미만 차이이며 K는 추가 측정에도 큰 편차가 남아 판정을 보류했다.

원본·구성 시간·보존 메모리·할당은 [결과 요약](../Benchmarks/results/oop-key-rows-small-20261112/summary.csv)과 같은 폴더의 info.txt에 있다. 벤치마크 문서는 이후의 JIT 조건별 측정만 싣는다. Unity Mono·IL2CPP, 스택 여유·프레임 수, 1,000개 초과 규모와 나머지 시나리오는 재검증하지 않았다.

## JIT 조건별 다섯 구조 재비교

2026-11-12에 cb62332, 최초 OOP 5478bbd, 현재 키 행 OOP, 배열 cab9d8e, 표 d818fe7을 같은 실행기로 비교했다. 제품·커밋된 벤치마크 코드는 변경하지 않았다. 재사용한 두 구조의 벤치마크·라이브러리 SHA-256 네 개가 기존 기록과 일치했고 새 세 구조의 Release 빌드는 각각 NU1900 경고 4건, 오류 0건으로 성공했다. cb62332는 Filter 인스턴스 공유를 보존하는 벤치마크 사본만 API에 맞췄다.

공통 63개는 이전 59개를 모두 포함하며 A·K의 Individual/Pipeline 1,000 규모 네 개가 추가됐다. 세 JIT 조건 × 다섯 구조 × 세 회차의 원본 2,835개, CSV 45개가 모두 완료됐고 누락·중복·최종 실패·측정 중단은 없다. 시간은 01:28:29~04:51:18, 약 3시간 22분 49.7초이다. 프로세스별 친화도 0x3·High·1.5초 예열·0.5초 × 5라운드와 수신 횟수 검증을 유지했다. 모든 runtimeconfig에 JIT 조건 덮어쓰기가 없고 부모 환경 변수는 원래 값 그대로였다.

CSV 저장 충돌 때문에 pgo-off/cb62332/1회/A-Pipeline-16을 한 번 재시도했다. 첫 측정도 종료 코드 0과 정상 CSV 출력을 보였으며 그 값을 삭제하지 않고 process-logs와 재시도 내역에 보존했다. 재시도 성공 후 전체 원본을 완성했다. 실제 2,836개 프로세스 모두 수신 검증을 통과했다. 채택 원본의 고정 구독 발행 2,295개는 할당 열이 전부 0 B이며 E·T 등록·해제 540개와 구분한다.

세 회차를 모두 포함한 집계에서는 default의 최초 OOP B·C·D 편차가 약 48~72%여서 과거 회귀의 재현을 판정하지 못했다. 원본을 시간순으로 다시 검사한 결과 01:28:29~01:35:57에만 모든 시나리오가 약 1.55배 느렸고, 이 구간이 default 1회차의 cb62332 전체와 first-oop 앞부분 43개 시나리오에 걸렸다. Individual 시나리오도 같은 배율로 느렸으므로 구조나 JIT가 아닌 측정 환경의 상태로 보며, 구체 원인은 확인하지 않았다.

다섯 구조 모두 default 2·3회차만 쓴 보충 집계에서 first-oop 대비 key-rows는 B32·B60·B64·C2·D-Rejected에서 +20.69%·+40.53%·+32.81%·+24.78%·+33.82%로, 11-11과 같은 방향과 크기였다. PGO를 끄면 B60(pgo-off +16.38%)을 제외하고 10% 미만으로 줄어, 두 날짜의 상대 차이는 주로 동적 PGO의 영향으로 본다. tiered-off의 소규모 상대비는 K1000 제외 13개에서 과거와 최대 1.46%p 차이이다. 절대 시간이 약 35~36% 작은 것은 느린 구간의 배율과 같은 수준의 측정 환경 차이로 본다. 배열의 1만·10만 K 개선과 표의 작은 그래프 다수에서의 회귀·100만 K 개선은 세 조건에서 관측됐다. 10%·양쪽 편차 기준을 통과한 구조 쌍은 default 211개(2·3회 보충 351개), pgo-off 336개, tiered-off 352개이다.

이 결과와 유지보수성을 근거로 그래프 구조를 키 행 OOP로 확정했다. 성능이 최우선인 처리는 EventStream의 구조를 바꾸지 않고 ECS로 다룬다. 결정과 대가는 [설계 결정](../../../../docs/02.%20UniEngine/02-Core/02-E.3-EventStream/docs/Design%20Decisions.md)에 있다.

세 구조의 측정 방법과 전체 결과 표는 [벤치마크](../../../../docs/02.%20UniEngine/02-Core/02-E.3-EventStream/docs/Benchmark.md)에 있다. 다섯 구조의 해시와 빌드 기록은 결과 폴더의 manifest.json과 info.txt에 있다. [전체성 검사](../Benchmarks/results/jit-conditions-20261112/analysis-validation.json), [표 1](../Benchmarks/results/jit-conditions-20261112/table1-structures.md), [표 2](../Benchmarks/results/jit-conditions-20261112/table2-conditions.md), [기준 통과 목록](../Benchmarks/results/jit-conditions-20261112/significant-pairs.md), [재시도 내역](../Benchmarks/results/jit-conditions-20261112/retry-details.md), [시간순 블록 검사](../Benchmarks/results/jit-conditions-20261112/startup-window-blocks.md), [보충 요약](../Benchmarks/results/jit-conditions-20261112/default-runs23-summary.md)을 연결한다. 원본과 스크립트는 버전 관리에서 제외한다. 기능 테스트는 재실행하지 않았으며 Unity Mono·IL2CPP 결과와 PGO의 구체 최적화는 검증하지 않았다.

## 키 행 구조 개편 검증

2026-11-11에 Windows·.NET SDK 10.0.404 Release로 1단계 키 행 구조를 검증했다. 본체 Release 빌드는 경고·오류 0건으로 성공했다. NodeCount는 키 노드와 스트림 연결을 세며 키 행은 제외한다. 이전 절의 512노드 같은 수치는 그 당시 구현의 기록으로 보존한다.

| 실행 범위 | 통과 / 실행 | 실패 | 건너뜀 |
| --- | ---: | ---: | ---: |
| EventStream·EventHub 선택 실행 | 490 / 490 | 0 | 0 |
| 최종 전체 테스트 | 1,059 / 1,059 | 0 | 0 |
| 전체 실행 중 EventStream | 319 / 319 | 0 | 0 |
| 전체 실행 중 신규 키 행 직접 사례 | 31 / 31 | 0 | 0 |
| 전체 실행 중 EventHub | 172 / 172 | 0 | 0 |

선택 실행은 약 4초이며 마지막 Debug 실패 회귀 1개를 추가하기 전의 결과이다. 최종 전체 실행은 그 사례까지 포함하며 실행기가 보고한 테스트 시간은 약 1분 23초이다. TRX의 시작부터 종료까지는 약 85.1초로 빌드 시간은 포함하지 않는다. 최초 샌드박스 선택 실행은 testhost 시작 후 진행되지 않아 Ctrl+C로 중단했고 통과 수에 포함하지 않았다. 실행 가능한 환경에서 선택·전체 테스트를 다시 실행했다.

### 확인한 계약

- KR1–KR3: 위치별 종류 노드와 키 행의 공유, 내부 Row의 비노드 형식, 별도 다음 노드 참조, Gate 우선, Where(a)→Flags(m)→Where(b) 등록의 a·b→flags 방문, 겹치는 b·c 마스크의 b1→b2→c1→c2 호출을 확인했다.
- KR4: Where·Flags의 16개 서로 다른 행과 중복 구독에서는 색인이 없고, 17번째 행에서 색인이 생겼다. 한 행까지 줄어도 같은 색인을 유지하고 마지막 행 제거 시 색인과 노드를 정리했다.
- KR5·KR9: 종류별 추가·제거·재등록, Where predicate 안에서 현재·다음 행 제거, Ordered 커서 앞뒤 행 추가, 종료의 Gate·노드·행 순서를 확인했다. 추가는 다음 발행부터, 제거는 즉시 반영했다.
- KR6: Where·Flags·When·Order·Debug 각각 정확히 256단계에서 발행 후 완료·오류·폐기를 실행한 15개 사례가 통과했다. 각 경로는 256노드이며 종료 후 0노드이고 257번째 단계는 거부했다.
- KR7: 16·17행의 고정 구독에서 첫 발행과 10,000회 반복 발행의 할당이 모두 0 B였다. 기존 int·Nullable·참조 형식 When 및 상태 연산자·Branch 할당 회귀도 통과했다.
- KR8: Where 실패는 해당 행, When 비교 실패는 노드 전체, Debug 포맷 실패는 해당 연결, TakeWhile·SkipWhile 실패는 해당 스트림만 정리했다. 중첩 When의 실패 비교 재호출 방지와 등록 실패의 빈 조상·대기 중 관계 스트림 폐기 회귀도 통과했다.

- B6–B7: 빈 항목·FlagsNode의 정리, 기본 스트림의 재사용과 관계 스트림의 자동 폐기, 마스크와 무관한 완료·오류·폐기, 연산자 조합과 ForFlags당 깊이 한 단계 계산을 확인했다.
- 할당 7개는 별도 인스턴스를 예열한 뒤 새 인스턴스의 첫 발행과 10,000회 반복 발행을 측정했고 모두 0 B였다. 단독 마스크의 통과·탈락·0·복합 비트와 최상위 비트를 사용하는 Where·ForOrder·Skip·Take·Branch 조합을 포함한다.

## 입력 계약과 종료 경로 보완 검증

2026-11-09에 구독 전 직접 입력 계약, Take의 복합 예외와 Merge·상태 연산자의 UniTest를 보완했다. .NET SDK 10.0.403으로 아래 범위를 모두 Release 실행했으며 실패·건너뜀은 없다.

| 실행 범위 | 통과 / 실행 |
| --- | ---: |
| EventStream 모듈 | 163 / 163 |
| 일반 전체 | 717 / 717 |

기존 EventStream 143개에 직접 입력 7개, Take 예외 8개, UniTest 실행 사례 5개를 추가했다. 전체 실행은 EventHub 등 소비 모듈을 포함한 회귀 검증이다. 본체와 테스트 빌드는 성공했으며, 패키지 취약성 정보 서버에 접근하지 못한 기존 NU1900 경고가 있었다.

### 직접 입력 계약

첫 구독은 상위 연결을 만드는 시점이다. 직접 OnNext는 구독 전에도 상태에 반영하며, Enabled가 false이면 직접·상위 입력 모두 상태를 바꾸지 않는다. Take·TakeWhile이 구독 전에 끝나면 연결을 만들지 않고 폐기되며 이후 구독을 거부한다. O2의 문구를 이 기준으로 정리하고 O6의 일곱 사례로 네 상태 연산자를 검증했다.

### 해결된 Take 복합 예외

- 상태: 수정 후 재검증 완료, 마지막 확인 2026-11-09.
- 재현: Take(1)의 마지막 값 콜백이 실패하고 다른 구독자의 완료 콜백도 실패한다. 직접 입력과 상위 입력에서 모두 발생했다.
- 기대: 남은 수신자에게 값과 완료를 전달하고 연결을 정리한 뒤 첫 보고 예외를 유지한다.
- 수정 전: 완료 예외가 먼저 기록된 값 예외를 덮어썼다. 보고기가 예외를 던질 때도 나중 보고 예외로 바뀌었다. F3의 여덟 사례 중 네 개가 실패했다.
- 수정 후: 완료 처리를 마친 뒤 그 실패를 기존 예외 기록에 합치며, 이미 기록된 첫 예외를 유지한다. 완료 실패를 중복 보고하지 않는다. F3 여덟 사례가 모두 통과했고 완료만 실패하는 경우의 예외 전달도 유지됐다.
- 기존 첫·반복 전파와 Take(1).Branch() 마지막 값의 무할당 테스트도 통과했다.

### UniTest 실행 경로

NUnit 실행 사례 수와 UniTest 종료 이력 수는 서로 다른 집계이다.

| 프로젝트 | NUnit 사례 | 확인한 종료 이력 |
| --- | ---: | ---: |
| 기존 Branch | 1 | U1–U2, 2개 |
| Merge | 1 | UM1–UM9, 9개 |
| 상태 연산자 | 4 | US1–US6, 6개 |

Merge는 첫 입력 완료·폐기 뒤 남은 입력을 발행하고 마지막 완료·폐기·오류·구독 해제를 조합했다. 양쪽 입력이 살아 있는 상태에서 마지막 구독을 해제하는 이력도 포함했다. 상태 연산자는 구독 전 직접 입력, 비활성화, 재활성화, 늦은 구독과 공유 상태, 정상 종료·마지막 해제·조건 실패를 확인했다. 모든 프로젝트는 기대한 종료 이력 목록까지 대조하고 재현에 사용한 스트림을 정리한다.

## Where 색인 검증

2026-11-08에 조건 수에 따라 선형 검색에서 해시 색인으로 전환하는 변경을 검증했다. 기존 132개와 추가 회귀 사례 11개를 포함한 EventStream 모듈 143개가 모두 통과했다. 이번 변경은 내부 등록 검색과 정리에 한정되어 프로젝트 전체 테스트는 다시 실행하지 않았다.

- 조건 8·16·17·32·33·64개에서 서로 다른 대리자 객체의 동등성과 다른 대상·메서드의 구분을 확인했다.
- 색인을 쓰는 두 부모에서 멀티캐스트 순서와 부모별 공유 범위를 확인했다.
- 발행 중 색인 생성과 제거·재등록은 현재 값의 전달 대상을 바꾸지 않으며, 새 구독은 다음 값부터 받았다.
- 조건이 줄거나 모두 해제된 뒤에도 재등록이 정상 동작했다. 조건 실패로 제거된 하위 경로도 다시 구성할 수 있었다.
- 상위 그래프가 살아 있어도 제거된 부모의 조건 대상은 GC로 회수됐다.

## 이전 사례와의 대응

이전 검증의 일반 전체 684개에서 686개로 늘었다. OrderedEventStream을 없애고 순서 그룹을 경로 연산 ForOrder로 바꾸면서 순서 목록 검증을 빼고, 순서 없는 구독자와 경로 중간의 그룹 사례를 추가했다.

그 이전의 683개에서 684개로 늘 때는 노드를 형식별로 나누고 InputGate와 OutputGate를 도입했으며, 기존 사례는 수정 없이 통과했다. 구독자가 먼저 만들어진 자식보다 앞서 호출되는 사례를 추가했다. Take·TakeWhile·Skip·SkipWhile의 상태를 각 파생 스트림에 중첩한 주입 노드로 옮긴 변경도 사례 수정 없이 통과했다.

그 이전의 681개에서 683개로 늘 때는 조건을 Filter 객체 대신 대리자로 받으면서 클로저가 다른 람다와 색인을 쓰는 형제의 공유 사례를 추가했다.

그 이전의 673개에서 681개로 늘 때는 EventSource 공개 형식과 Chain·Connect·TerminationMode를 없애면서 그 계약 사례를 빼고, 상태 공유·직접 입력·입력별 Merge·수신자 사례를 추가했다.

| 이전 검증 | 현재 검증하는 동작 |
| --- | --- |
| EventSource의 Chain·Connect, 핸들 인계 | 공개 API에서 제거했다. 새 스트림의 연결 수명과 폐기는 C1·C5로 검증한다. |
| Dispatch 호환성 | 파생 지점을 제거하여 사례를 뺐다. |
| 구독마다 독립적인 Take·Skip 상태 | 같은 스트림의 구독자가 상태를 공유하고, 연산자를 다시 호출하면 새로 시작한다. |
| 외부 공급원의 직접 발행 거부 | 모든 스트림이 값을 직접 받는다. 횟수·조건 반영과 재진입 거부를 C6으로 검증한다. |
| Merge의 All·Any 완료, 공급원 입력 | EventStream 입력의 All 완료, 입력 폐기, 입력별 전달을 M1·M2로 검증한다. Any 완료는 제거했다. |

## UniTest 상태 전이

U1과 U2는 NUnit 사례 하나에서 도달한 서로 다른 종료 이력이다. 첫 구독을 해제한 뒤 남은 구독만 4를 받으며, Branch가 비활성인 동안에는 짝수 조건의 누적 평가 횟수가 3으로 유지된다.

- U1에서는 재활성화 뒤 8을 전달하고 마지막 구독을 해제했다. 부모의 노드가 모두 제거되고 Branch가 폐기됐다. 이후 부모의 새 구독은 10을 받았고 필터 평가 횟수는 4에 머물렀다.
- U2에서는 Branch가 비활성일 때 부모를 완료했다. 남은 구독자만 완료를 한 번 받고 부모와 Branch가 폐기됐다.
