## ForOrderAsync 검증

2026-11-14에 .NET SDK 10.0.404·Linux x64·Release로 본체와 테스트를 빌드했다. 최종 전체 실행은 911개 통과, 실패·건너뜀 0개이며, 본체 빌드는 경고·오류 0개이다.

| 범위 | 통과 / 실행 |
| --- | ---: |
| 전체 | 911 / 911 |
| 전체에 포함된 EventStream | 238 / 238 |
| 신규 병렬 오더 | 23 / 23 |
| 전체의 기존 할당 검증 | 77 / 77 |

신규 사례는 두 작업의 실제 중첩, 작업 스레드와 발행 스레드의 구분, OnNext 완료 대기, 같은 순서 값의 병렬 우선과 그룹 재생성, 중첩 그룹·Branch·Take·Merge·직접 스트림 관찰자의 경계, 조건 공유와 실패를 확인했다. 멀티캐스트 해제, 지연 등록의 취소·등록 후 해제, 역순으로 요청된 변경의 방문 순서 반영, 완료·오류·폐기와 복수 실패, 다른 이벤트 형식의 변경, 명시적 직접 발행과 같은 스트림 재진입도 검증했다.

첫 전체 실행에서는 컨테이너의 MyDocuments가 빈 경로여서 기존 Configuration 사례 12개가 실패했다. 임시 XDG 설정에 존재하는 테스트 전용 문서 폴더를 지정한 뒤 전체 실행이 통과했다. 저장소의 Configuration 구현이나 테스트 기대값은 변경하지 않았다. 이후 동기 구독 루프의 분기를 조정한 최종 코드로 전체 실행을 다시 확인했다.

실행 환경은 DOTNET_CLI_HOME·NUGET_PACKAGES·DOTNET_ROOT를 쓰기 가능한 임시 경로로 지정하고, XDG_CONFIG_HOME의 user-dirs.dirs에 XDG_DOCUMENTS_DIR을 설정했다. 최종 실행 시간은 약 25초이다. [전체 실행 TRX](../../../obj/ForOrderAsync/20261114-final.trx)는 버전 관리에서 제외되는 테스트 산출물이다.

```sh
dotnet test tests/UniEngine.Tests.csproj -c Release --no-restore \
    --logger 'trx;LogFileName=20261114-final.trx' \
    --results-directory tests/obj/ForOrderAsync
```

기존 동기 경로의 대표 벤치마크 비교는 [벤치마크](../../../../docs/02.%20UniEngine/02-Core/02-E.3-EventStream/Benchmark.md)의 ForOrderAsync 도입 후 동기 전파 절에 기록한다. Unity Mono·IL2CPP 실행은 수행하지 않았다.

## ForFlags UniTest 상태 전이 보강 검증

2026-11-10에 ForFlags의 공유·수명과 발행 중 변경을 UniTest 상태 전이 프로젝트로 보강했다. .NET 10 Release 빌드에 성공했으며 EventStream 모듈 200개가 모두 통과하고 실패·건너뜀은 0개이다. 기존 198개에 신규 NUnit 사례 두 개를 추가했다.

| 신규 프로젝트 | NUnit 통과 / 실행 | 확인한 종료 이력 |
| --- | ---: | --- |
| ForFlags 공유와 수명 | 1 / 1 | UF1–UF8, 8개 |
| ForFlags 발행 중 변경 | 1 / 1 | UFM1–UFM6, 6개 |

신규 NUnit 사례 수 2개와 그 안에서 확인한 UniTest 종료 이력 수 14개는 서로 다른 집계이다. 두 프로젝트 모두 CompactProject와 CompactLab을 Inline 모드로 실행하고, 각 단계의 단언뿐 아니라 실제 종료 이력 목록이 기대 경로와 일치하는지 확인했다. 재현에 사용한 모든 모델의 스트림도 실행 후 정리했다.

- UF1–UF8: 다른 enum의 같은 마스크 비트를 공유하고 순서 그룹 사이에서는 분리했다. 첫 구독 해제 뒤 남은 수신자와 노드 수를 유지했으며, 비활성 중 상위·직접 입력은 차단하고 재활성 뒤에는 다시 전달했다. 비활성·재활성 상태 각각에서 완료·오류·폐기·전체 해제를 검증했다. 값이 맞지 않았던 최상위 비트 구독까지 종료 신호를 받고, 전체 해제 시 중간 노드 정리와 마지막 상위 연결 해제 및 Source 재사용을 확인했다.
- UFM1–UFM6: 현재 콜백에서 기존 항목에 구독과 새 항목을 추가하거나, 뒤 항목을 제거·재등록하거나, 현재 항목과 뒤 항목을 제거했다. 현재 발행에서는 추가가 보이지 않고 제거는 즉시 반영되며, 다음 발행은 변경된 순서를 따랐다. 각 경로를 전체 해제와 완료로 끝내며 노드·핸들 정리와 통지 순서를 확인했다.

이번 보강은 테스트와 테스트 문서만 변경했으므로 EventStream 모듈을 다시 실행했다. 아래의 전체 856개 통과는 앞선 ForFlags 공개 API 구현 시점의 결과이며, 이번 보강 뒤 전체 테스트 프로젝트를 다시 실행한 결과는 아니다. 벤치마크와 Unity Mono·IL2CPP 검증은 추가로 수행하지 않았다.

이번 실행은 첫 시도에 성공했으며 testhost 연결 오류는 없었다. 원본 결과는 버전 관리에서 제외되는 [EventStream 실행 TRX](../../../obj/EventStreamFlags/20261110-forflags-unitest.trx)에 있다.


## ForFlags와 FlagExtensions 검증

2026-11-10에 ForFlags 경로 연산과 FlagExtensions의 ulong 지원·ToBits를 추가하고 .NET 10 Release에서 전체 테스트를 실행했다. 본체는 netstandard2.1, 테스트는 net10.0으로 빌드에 성공했으며 최종 실행은 856개 통과, 실패·건너뜀 0개이다.

| 실행 범위 | 통과 / 실행 |
| --- | ---: |
| 일반 전체 | 856 / 856 |
| 전체 실행에 포함된 EventStream | 198 / 198 |
| EventStream 중 신규 ForFlags 기능 사례 | 28 / 28 |
| EventStream 중 신규 ForFlags 할당 사례 | 7 / 7 |
| 전체 실행에 포함된 FlagExtensions | 22 / 22 |

위 모듈별 수는 전체 실행 결과에서 분류한 부분집합이다. 기존 EventStream 163개에 기능 28개와 할당 7개를 추가했다. 전체 실행은 현재 작업 트리의 소비 모듈까지 포함하며, 다른 작업으로 추가된 사례도 함께 실행했다.

- B1–B3: HasAny 통과·탈락과 복합 비트, 값 0의 차단, int 부호 비트와 ulong 최상위 비트, 구성 시 예외, enum 형식이 달라도 같은 비트인 항목의 공유와 부모·순서 그룹의 분리를 확인했다.
- B4–B5: 항목·형제의 생성 순서와 Gate 우선 호출, 발행 중 새 FlagsNode·항목·구독의 다음 값 반영, 현재·다음 항목과 같은 항목의 뒤 구독 제거, 제거 후 재등록의 순서·가시성을 확인했다.
- B6–B7: 빈 항목·FlagsNode의 정리, 기본 스트림의 재사용과 관계 스트림의 자동 폐기, 마스크와 무관한 완료·오류·폐기, 연산자 조합과 ForFlags당 깊이 한 단계 계산을 확인했다.
- 할당 7개는 별도 인스턴스를 예열한 뒤 새 인스턴스의 첫 발행과 10,000회 반복 발행을 측정했고 모두 0 B였다. 단독 마스크의 통과·탈락·0·복합 비트와 최상위 비트를 사용하는 Where·ForOrder·Skip·Take·Branch 조합을 포함한다.
- FlagExtensions 22개는 ulong HasAny·HasAll·Combine, 빈 목록과 0 마스크, 여덟 enum 기반 형식의 비트 보존과 ToBits의 할당을 검증했다.

최초 실행은 빌드 성공 후 `vstest.console 프로세스가 90초 후 testhost 프로세스에 연결하지 못했습니다.`라는 오류로 중단됐다. 테스트 단언 실패가 아니라 실행 환경의 연결 시간 초과였으며, 샌드박스 밖에서 같은 빌드를 다시 실행해 위 결과를 얻었다.

## 입력 계약과 종료 경로 보완 검증

2026-11-09에 구독 전 직접 입력 계약, Take의 복합 예외와 Merge·상태 연산자의 UniTest를 보완했다. .NET SDK 10.0.403으로 아래 범위를 모두 Release 실행했으며 실패·건너뜀은 없다.

| 실행 범위 | 통과 / 실행 |
| --- | ---: |
| EventStream 모듈 | 163 / 163 |
| 일반 전체 | 717 / 717 |

기존 EventStream 143개에 직접 입력 7개, Take 예외 8개, UniTest 실행 사례 5개를 추가했다. 전체 실행은 EventHub 등 소비 모듈을 포함한 회귀 검증이다. 본체와 테스트 빌드는 성공했으며, 패키지 취약성 정보 서버에 접근하지 못한 기존 NU1900 경고가 있었다.

### 직접 입력 계약

첫 구독은 상위 연결을 만드는 시점이다. 직접 OnNext는 구독 전에도 상태에 반영하며, Enabled가 false이면 직접·상위 입력 모두 상태를 바꾸지 않는다. Take·TakeWhile이 구독 전에 끝나면 연결을 만들지 않고 폐기되며 이후 구독을 거부한다. O2의 문구를 이 기준으로 정리하고 O6의 일곱 사례로 네 상태 연산자를 검증했다.

### 해결된 Take 복합 예외

- 상태: 수정 후 재검증 완료, 마지막 확인 2026-11-09.
- 재현: Take(1)의 마지막 값 콜백이 실패하고 다른 구독자의 완료 콜백도 실패한다. 직접 입력과 상위 입력에서 모두 발생했다.
- 기대: 남은 수신자에게 값과 완료를 전달하고 연결을 정리한 뒤 첫 보고 예외를 유지한다.
- 수정 전: 완료 예외가 먼저 기록된 값 예외를 덮어썼다. 보고기가 예외를 던질 때도 나중 보고 예외로 바뀌었다. F3의 여덟 사례 중 네 개가 실패했다.
- 수정 후: 완료 처리를 마친 뒤 그 실패를 기존 예외 기록에 합치며, 이미 기록된 첫 예외를 유지한다. 완료 실패를 중복 보고하지 않는다. F3 여덟 사례가 모두 통과했고 완료만 실패하는 경우의 예외 전달도 유지됐다.
- 기존 첫·반복 전파와 Take(1).Branch() 마지막 값의 무할당 테스트도 통과했다.

### UniTest 실행 경로

NUnit 실행 사례 수와 UniTest 종료 이력 수는 서로 다른 집계이다.

| 프로젝트 | NUnit 사례 | 확인한 종료 이력 |
| --- | ---: | ---: |
| 기존 Branch | 1 | U1–U2, 2개 |
| Merge | 1 | UM1–UM9, 9개 |
| 상태 연산자 | 4 | US1–US6, 6개 |

Merge는 첫 입력 완료·폐기 뒤 남은 입력을 발행하고 마지막 완료·폐기·오류·구독 해제를 조합했다. 양쪽 입력이 살아 있는 상태에서 마지막 구독을 해제하는 이력도 포함했다. 상태 연산자는 구독 전 직접 입력, 비활성화, 재활성화, 늦은 구독과 공유 상태, 정상 종료·마지막 해제·조건 실패를 확인했다. 모든 프로젝트는 기대한 종료 이력 목록까지 대조하고 재현에 사용한 스트림을 정리한다.

## Where 색인 검증

2026-11-08에 조건 수에 따라 선형 검색에서 해시 색인으로 전환하는 변경을 검증했다. 기존 132개와 추가 회귀 사례 11개를 포함한 EventStream 모듈 143개가 모두 통과했다. 이번 변경은 내부 등록 검색과 정리에 한정되어 프로젝트 전체 테스트는 다시 실행하지 않았다.

- 조건 8·16·17·32·33·64개에서 서로 다른 대리자 객체의 동등성과 다른 대상·메서드의 구분을 확인했다.
- 색인을 쓰는 두 부모에서 멀티캐스트 순서와 부모별 공유 범위를 확인했다.
- 발행 중 색인 생성과 제거·재등록은 현재 값의 전달 대상을 바꾸지 않으며, 새 구독은 다음 값부터 받았다.
- 조건이 줄거나 모두 해제된 뒤에도 재등록이 정상 동작했다. 조건 실패로 제거된 하위 경로도 다시 구성할 수 있었다.
- 상위 그래프가 살아 있어도 제거된 부모의 조건 대상은 GC로 회수됐다.

## 이전 사례와의 대응

이전 검증의 일반 전체 684개에서 686개로 늘었다. OrderedEventStream을 없애고 순서 그룹을 경로 연산 ForOrder로 바꾸면서 순서 목록 검증을 빼고, 순서 없는 구독자와 경로 중간의 그룹 사례를 추가했다.

그 이전의 683개에서 684개로 늘 때는 노드를 형식별로 나누고 InputGate와 OutputGate를 도입했으며, 기존 사례는 수정 없이 통과했다. 구독자가 먼저 만들어진 자식보다 앞서 호출되는 사례를 추가했다. Take·TakeWhile·Skip·SkipWhile의 상태를 각 파생 스트림에 중첩한 주입 노드로 옮긴 변경도 사례 수정 없이 통과했다.

그 이전의 681개에서 683개로 늘 때는 조건을 Filter 객체 대신 대리자로 받으면서 클로저가 다른 람다와 색인을 쓰는 형제의 공유 사례를 추가했다.

그 이전의 673개에서 681개로 늘 때는 EventSource 공개 형식과 Chain·Connect·TerminationMode를 없애면서 그 계약 사례를 빼고, 상태 공유·직접 입력·입력별 Merge·수신자 사례를 추가했다.

| 이전 검증 | 현재 검증하는 동작 |
| --- | --- |
| EventSource의 Chain·Connect, 핸들 인계 | 공개 API에서 제거했다. 새 스트림의 연결 수명과 폐기는 C1·C5로 검증한다. |
| Dispatch 호환성 | 파생 지점을 제거하여 사례를 뺐다. |
| 구독마다 독립적인 Take·Skip 상태 | 같은 스트림의 구독자가 상태를 공유하고, 연산자를 다시 호출하면 새로 시작한다. |
| 외부 공급원의 직접 발행 거부 | 모든 스트림이 값을 직접 받는다. 횟수·조건 반영과 재진입 거부를 C6으로 검증한다. |
| Merge의 All·Any 완료, 공급원 입력 | EventStream 입력의 All 완료, 입력 폐기, 입력별 전달을 M1·M2로 검증한다. Any 완료는 제거했다. |

## UniTest 상태 전이

U1과 U2는 NUnit 사례 하나에서 도달한 서로 다른 종료 이력이다. 첫 구독을 해제한 뒤 남은 구독만 4를 받으며, Branch가 비활성인 동안에는 짝수 조건의 누적 평가 횟수가 3으로 유지된다.

- U1에서는 재활성화 뒤 8을 전달하고 마지막 구독을 해제했다. 부모의 노드가 모두 제거되고 Branch가 폐기됐다. 이후 부모의 새 구독은 10을 받았고 필터 평가 횟수는 4에 머물렀다.
- U2에서는 Branch가 비활성일 때 부모를 완료했다. 남은 구독자만 완료를 한 번 받고 부모와 Branch가 폐기됐다.
