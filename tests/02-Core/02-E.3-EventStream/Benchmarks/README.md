# EventStream 벤치마크

EventStream의 구조를 바꿀 때 이전 버전과 전파·구독 비용을 비교하는 측정 도구이다. 측정 결과와 해석은 [벤치마크 문서](../../../../docs/02.%20UniEngine/02-Core/02-E.3-EventStream/Benchmark.md)에 정리한다.

## 목차

1. 구성
2. 실행
3. 측정 방식
4. 결과 해석
5. 시나리오

## 구성

| 파일 | 역할 |
| --- | --- |
| `EventStreamBenchmarks.csproj` | 측정 실행 프로젝트이다. 테스트 프로젝트와 별도로 빌드하며 `dotnet test`에 포함되지 않는다. |
| `Scenarios.cs` | 측정할 시나리오이다. 공개 API만 사용하므로 같은 코드를 이전 커밋의 라이브러리에도 빌드할 수 있다. |
| `Program.cs` | 시나리오 하나를 한 프로세스에서 측정하고 결과를 CSV 한 줄로 출력한다. |
| `run.ps1` | 기준 커밋과 작업 트리를 각각 빌드하고 시나리오를 번갈아 실행한 뒤 변화를 요약한다. |

이전 빌드의 실행 파일은 저장소에 두지 않는다. 비교 기준은 git 커밋으로 지정하고, `run.ps1`이 그 커밋의 `src`와 빌드 설정을 임시 폴더에 꺼내 같은 시나리오로 빌드한다. 기준 커밋도 지금과 같은 공개 API를 가져야 빌드된다. 예를 들어 조건을 `Filter<T>`로 받던 커밋은 기준으로 쓸 수 없다.

## 실행

저장소 안 어디서든 PowerShell로 실행한다.

```powershell
./tests/02-Core/02-E.3-EventStream/Benchmarks/run.ps1 -Baseline <커밋> -Quick
```

| 매개변수 | 기본값 | 의미 |
| --- | --- | --- |
| `-Baseline` | `HEAD` | 비교 기준 커밋이다. 기본값이면 커밋되지 않은 변경만 비교한다. |
| `-Quick` | 꺼짐 | 대표 시나리오 6개만 실행한다. 1분 남짓 걸린다. 끄면 전체 59개를 실행하며 2회 기준으로 20분 가까이 걸린다. |
| `-Runs` | `2` | 기준과 현재를 번갈아 실행하는 횟수이다. |
| `-Affinity` | `0x3` | 프로세스를 고정할 코어 마스크이다. 같은 물리 코어의 논리 코어를 지정한다. |
| `-Output` | `results/<시각>` | 결과 폴더이다. `results`는 git에서 제외된다. |

결과 폴더에는 빌드·실행별 CSV, 요약인 `summary.csv`, 기준 커밋과 실행 환경을 적은 `info.txt`가 남는다. 측정 중에는 다른 무거운 작업을 하지 않는다.

시나리오 하나만 직접 측정할 수도 있다.

```powershell
dotnet run -c Release --project ./tests/02-Core/02-E.3-EventStream/Benchmarks -- A-Pipeline-64 0x3
```

## 측정 방식

- 시나리오마다 별도 프로세스로 실행한다. JIT 상태와 코어 배치가 시나리오 사이에 이어지지 않게 하기 위해서이다.
- 프로세스를 지정한 코어에 고정하고 우선순위를 높인다. 성능 코어와 효율 코어가 섞인 CPU에서는 고정하지 않으면 같은 시나리오도 값이 크게 달라진다.
- 1.5초 예열한 뒤 0.5초씩 다섯 라운드를 측정해 중앙값을 쓴다. 짧은 작업은 묶음으로 반복해 시간을 잰다.
- 라운드마다 콜백 호출 횟수를 검증한다. 기대한 횟수와 다르면 그 시나리오를 실패로 처리한다.
- 조건은 서로 다른 메서드 16개로 만든다. 같은 람다만 쓰면 JIT가 호출을 인라인해 개별 순회 쪽이 실제보다 유리하게 측정된다.

`Program.cs`가 출력하는 CSV 열은 시나리오 이름, 중앙값 ns, 가장 빠른 라운드 ns, 가장 느린 라운드 ns, 작업당 할당 바이트, 구성 시간 ms, 구성 후 남은 메모리 바이트 순서이다.

## 결과 해석

- 값은 같은 실행 안에서만 비교한다. 같은 코드도 측정한 날에 따라 1.5배까지 달라진 적이 있다.
- 두 실행의 차이보다 작은 변화는 구조의 차이로 해석하지 않는다. 지금까지의 측정에서 실행 간 차이는 대부분 10% 이내였다.
- 한 실행만 튄 값은 다시 측정해 확인한다.

## 시나리오

| 묶음 | 내용 |
| --- | --- |
| A | 구독자 수(16–1024)를 늘리며 16분의 1이 값을 받는다. |
| B | 구독자 64명 중 값을 받는 비율을 바꾼다. `B-Direct`는 조건 없는 직접 구독이다. |
| C | 구독자 64명 중 4명이 받으며 공유하는 조건 수를 바꾼다. |
| D | 공통 조건 하나를 앞에 두고 거짓과 참인 경우를 비교한다. |
| E | 구독 하나를 추가하고 해제하는 비용이다. 이미 있는 Where, 새 Where, 메서드 그룹, Branch, Take를 비교한다. |
| F | 연산자가 만든 스트림을 거쳐 구독자 64명에게 전달한다. |
| L·R·K·T | 구독자 1만·10만·100만 명 규모이다. L은 16분의 1이 받고, R은 4명만 받고, K는 구독자 4명마다 조건을 둔다. T는 구독 하나를 추가하고 해제한다. |

이름의 `Individual`은 구독자가 각자 조건을 검사하는 개별 순회, `Pipeline`은 Where 노드를 공유하는 파이프라인이다.
