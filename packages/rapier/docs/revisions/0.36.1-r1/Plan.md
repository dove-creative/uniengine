# Rapier 0.36.1 개조 및 검증 계획

기존 Rapier 0.36.1의 충돌 검사 이후 운동 갱신 문제에 대해 원본을 수정하지 않는 대안을 먼저 검증하고, 필요할 때 임시 패치를 적용·검증하는 계획이다.

2026-11-23에 무수정 대안의 수면 전환 실패를 확인하고 아래 패치 경로를 구현했다. 원본 비교와 적용 절차를 함께 보존하며, 실행 결과와 완료 범위는 [검증 결과](../../investigation/03.%20Results.md)에 기록한다.

## 목차

- 목표와 기준
- 기존 버전의 문제와 수정 방향
- 원본 보존과 수정본 구성
- 적용·검증 순서
- 검증 위치와 통과 기준
- 결과 기록과 완료 기준
- 공식 수정 버전으로의 전환

## 목표와 기준

새 동적 강체에 `DetectCollisions` 후 `Step`을 호출해도 정상적으로 운동하게 하는 것이 목표이다. DetectCollisions는 시간이나 운동을 적분하지 않고 충돌 정보를 갱신하며, Step은 그 이후에도 필요한 물리 상태 갱신을 완료해야 한다.

| 항목 | 기준 |
| --- | --- |
| 원본 Rapier | `rapier2d`, `rapier2d-f64`, `rapier3d`, `rapier3d-f64`의 정확한 버전 0.36.1 |
| Parry | 각 구성의 0.31.1 유지, 소스 수정 없음 |
| 패치 후보 식별자 | `0.36.1-r1`. 공식 Rapier 버전이나 연결 DLL 버전과 구분하며 Cargo 패키지 버전에는 사용하지 않음 |
| 구조 | PhysicalSpace C# 객체 → UniEngine 전용 Rust C ABI → Rapier·Parry 유지 |
| 검증 구성 | Windows x64, Rust/Cargo 1.99.1, MSVC, Release, 2D/3D × f32/f64. 회귀 사례는 debug assertion을 켠 빌드에서도 실행 |
| feature | 원본 기본값 유지. block-solver는 rapier2d·rapier2d-f64·rapier3d-f64에 기본 포함되며 rapier3d에는 미포함 |
| 공개 계약 | 공개 Rust API와 C ABI의 시그니처 유지 |
| 작업 단계 | 0단계 개조·검증. 제품 C# API, 제품 DLL 채택과 1단계 구현은 별도 범위 |

기존 실패 결과는 [0단계 결과](../../investigation/03.%20Results.md)에 보존하며, 최소 재현 코드와 네 구성 결과는 [등록 이슈 #1084](https://github.com/dimforge/rapier/issues/1084)에 있다. 원본에서 확인한 사실과 아직 검증하지 않은 수정 가설을 구분한다.

## 기존 버전의 문제와 수정 방향

### 확인한 동작과 원인 가설

높이 2의 동적 Ball 강체에 중력 Y = -9.81과 시간 간격 1/60초를 설정하고 Step을 10번 실행한다. 원본에서는 Step만 호출하면 낙하하지만, 첫 Step 전에 DetectCollisions를 호출하면 높이 2·Y 속도 0에 머문다. 네 구성 모두 질량은 양수이고 수면 상태는 false이다.

배포 소스의 CollisionPipeline은 변경 강체 목록을 가져와 island 인자 없이 사용자 변경을 처리한 뒤 강체의 변경 플래그와 목록을 정리한다. PhysicsPipeline은 같은 종류의 변경을 처리하면서 활성 상태와 실제 조인트 상태도 갱신한다. 충돌 검사에서 기록을 먼저 소비해 다음 Step이 신규 강체의 활성 상태 등록을 놓친다는 것이 현재 원인 가설이다.

[#815](https://github.com/dimforge/rapier/issues/815)와 [#662](https://github.com/dimforge/rapier/issues/662)의 변경 추적 문제도 회귀 대상으로 삼는다. 목록만 비우고 플래그를 남기거나, 플래그만 보존하는 수정은 후속 변경을 목록에 다시 넣지 못하게 할 수 있으므로 두 상태의 일관성을 함께 유지해야 한다.

### 확정한 개조 방식

초기 후보는 CollisionPipeline의 변경 목록·플래그를 보존하여 다음 Step에 처리를 넘기는 방식이었다. 그러나 검사 시점의 접촉 처리에도 활성 집합 등록이 필요하므로 이 후보를 채택하지 않았다. 실제 패치는 기존 PhysicsPipeline의 사용자 변경·실제 조인트·접촉 갱신을 재사용하고, 시간 간격 0의 경로가 persistent island 초기화까지 완료하도록 한다.

네 배포 crate에 같은 [공통 패치](../../../revisions/0.36.1-r1/collision-update.patch)를 적용한다. 수정 파일은 `src/pipeline/physics_world.rs`와 `src/pipeline/physics_pipeline/substep.rs`이다. `CollisionPipeline` 자체는 수정하지 않는다. 원본·수정 파일 해시와 배포 메타데이터는 [provenance.json](../../../revisions/0.36.1-r1/provenance.json)에 고정한다.

1. `PhysicsWorld::detect_collisions`는 월드의 IntegrationParameters를 복사하고 복사본의 `dt`만 0으로 만든다. 실제 island·조인트·soft body·CCD 저장소를 PhysicsPipeline에 전달한다. 원래 설정은 콜백 panic 시에도 덮어쓰지 않는다.
2. PhysicsPipeline의 시간 간격 0 분기에서 solver contact graph를 정리하기 전에 `islands.update_islands(..., &[])`를 호출한다. 빈 수면 관찰 목록을 전달하므로 수면 타이머를 진행시키지 않으며, 첫 정상 Step 전에 persistent island bootstrap과 구조 검증을 완료한다.
3. 변경 목록·플래그 정리는 기존 PhysicsPipeline 경로를 사용한다. 충돌 검사 이후의 편집·질량·부모·활성 상태 변경도 같은 처리 경로를 따른다.
4. 두 파일의 변경 위치에 UniEngine·날짜·수정본 식별자를 영어 주석으로 명시한다. 원래 라이선스 고지를 유지하고 패치 적용에 `git -c core.autocrlf=false apply`를 사용하여 LF와 해시를 보존한다.

이 경로는 검사 호출마다 물리 상태의 변경 처리를 완료한다. 반복 검사와 제거·재삽입의 공개 상태를 검증하되, 내부 버퍼 용량이나 전체 성능이 개선됐다고 표현하지 않는다. 일반 `CollisionPipeline::step`을 직접 호출하는 사용까지 해결 범위로 확대하지 않는다.

### 접촉과 활성 집합 불변식

원본의 IslandManager는 island가 하나라도 있으면 접촉 상대인 고정되지 않은 활성 강체가 활성 집합에 등록돼 있어야 한다는 조건을 debug assertion으로 검사한다. 이미 Step한 월드에 새 동적 강체를 다른 강체와 접촉한 상태로 추가하고 DetectCollisions를 호출하면, 충돌 검사의 접촉 시작 처리가 등록 전의 강체로 이 조건을 검사한다. 원본에도 같은 상태가 있으며, 위 후보안의 2번에서 활성 상태 등록을 다음 Step까지 지연하면 패치 후에도 남는다.

실행 중인 월드에 접촉하는 새 강체를 삽입하는 원본 사례에서 Debug assertion 실패를 재현했다. 따라서 다음 Step까지 등록을 미루지 않고, PhysicsPipeline의 기존 사용자 변경 처리로 접촉 검사 전에 등록하도록 확정했다. 새 월드와 기존 월드는 별도 회귀 테스트로 검증한다.

### 원본을 수정하지 않는 대안

0.36.1의 PhysicsPipeline은 시간 간격이 0 이하인 Step에서 사용자 변경을 적용하고 접촉을 갱신한 뒤 동역학을 건너뛴다. 이 경로는 실제 island manager와 조인트 집합을 사용하므로, 연결 계층의 DetectCollisions를 이 경로로 구현하면 원본을 수정하지 않고 목표를 달성할 가능성이 있다. 아직 실행하지 않았다.

대안 검증에서는 월드의 IntegrationParameters를 복사하고 그 사본의 `dt`만 0으로 설정하여 PhysicsPipeline에 전달한다. 월드에 설정된 원래 시간 간격은 유지하고, 이후 정상 Step이 그 시간 간격으로 진행되는지 확인한다. 원본의 기본 DetectCollisions 호출과 이 대안 호출은 테스트에서 명시적으로 구분한다. 대안이 통과해도 원본 DetectCollisions 자체가 수정되었다고 기록하지 않는다.

### 구현 방식 결정 기준

실제 비교에서는 원본 `dt=0` 대안도 `검사 → sleep() → 검사 → 첫 Step`에서 수면 중 한 번 이동했다. 초기 persistent island bootstrap이 첫 정상 Step의 수면 관찰 이후에 이루어지는 경로와 관련되며, bootstrap을 검사에서 완료한 패치는 같은 사례를 통과했다. 따라서 무수정 대안은 채택하지 않고 위 두 파일의 패치를 선택했다. 상세 수치와 원본·대안·수정본 결과는 검증 결과 문서에 둔다.

원본 재현과 접촉·활성 집합 검증 후, 패치를 작성하기 전에 `dt=0` 대안을 같은 회귀 사례로 검증한다. 네 구성의 Release·debug assertion 빌드에서 운동 비적분, 접촉·이벤트·조인트 갱신, 다음 Step의 정상 동작을 모두 만족하면 원본 무수정 대안을 우선 채택한다.

대안이 계약을 만족하지 못하면 실패 사례와 미채택 이유를 기록하고 패치 경로를 선택한다. 이때 접촉 처리 전 활성 집합 조건까지 만족하도록 개조 후보안을 확정한 뒤 패치를 작성한다. 어느 경로도 검증을 통과하지 못하면 미해결 상태를 유지한다. 구현 방식 선택은 1단계 제품 API 구현 승인과 구분한다.

## 원본 보존과 수정본 구성

원본 기준은 Git 태그가 아니라 실제 배포 `.crate`와 기존 Cargo.lock의 체크섬이다. Rapier의 출판 메타데이터는 커밋 `475caa3ff4646fd9a796b67d14116256f4962bc7`과 `dirty: true`를 기록하므로, 깨끗한 Git checkout으로 원본을 대신하지 않는다.

원본 및 `dt=0` 대안 비교에는 기존 원본 패키지·lock을 사용한다. 패치 경로에는 아래 자료와 Cargo 경로 대체를 사용한다. 자료 생성과 준비 스크립트를 구현했으며 원본 캐시는 유지한다.

| 자료 | 관리 기준 |
| --- | --- |
| 원본 압축 파일 | 패키지 폴더의 `upstream/0.36.1`에 네 Rapier 배포 압축 파일을 원형 그대로 보존하고 SHA-256을 기존 lock과 대조함 |
| 원본 lock | 원본 검증 작업공간의 Cargo.lock 유지. 계획 수립 시 SHA-256은 `3BBE34905093B9FFDDF862E033B2A88B36C1CB7FF2BE4398CB838B4E82096992`임 |
| 패치와 출처 자료 | 패키지의 `revisions/0.36.1-r1`에 공통 패치, 원본·패치 체크섬, 변경 파일과 적용 후 체크섬을 보존함. 계획 문서는 `docs/revisions/0.36.1-r1`에서 관리함 |
| 수정본 lock | 패키지의 `revisions/0.36.1-r1/Cargo.lock`을 보존하여 원본 lock과 구분함 |
| 수정 소스 | 검증한 원본을 비추적 `obj`의 수정본 작업공간에 풀고 패치를 적용해 생성함. Cargo 레지스트리 캐시의 원본은 수정하지 않음 |
| 실행 산출물 | 원본·수정본과 실행을 구분한 `obj` 하위 출력에 로그·DLL·내보내기·출처 manifest를 기록함. 최초 0단계 산출물은 덮어쓰지 않음 |

수정본 작업공간에서만 `[patch.crates-io]`로 네 Rapier 패키지를 생성한 로컬 소스에 연결한다. Parry와 나머지 의존성은 원본과 같은 버전·feature를 유지한다. 경로 의존성으로 바뀐 Rapier 항목은 Cargo.lock의 레지스트리 체크섬만으로 검증할 수 없으므로 원본 압축 파일, 적용 패치, 수정 소스의 체크섬을 따로 검증한다. 실제 해석된 의존성 경로도 대조한다.

생성한 Rapier crate의 패키지 버전은 0.36.1로 유지한다. `0.36.1-r1`을 패키지 버전으로 쓰면 semver의 pre-release로 해석되어 `=0.36.1` 요구를 만족하지 않으므로, Cargo는 patch를 사용하지 않고 경고만 남긴 채 레지스트리 원본으로 빌드한다. 수정본 식별자는 폴더·manifest·변경 주석에만 사용한다.

## 적용·검증 순서

아래 순서로 비교·구현·검증한다. 구현된 실행 진입점은 `scripts/Investigate.ps1`이며, 원본 압축 파일에서의 소스 생성은 `PrepareRevision.ps1`, 실제 Cargo 의존성 경로 검사는 `VerifyResolvedDependencies.ps1`이 담당한다.

1. 원본 패키지 체크섬과 빌드 입력을 검증하고, 공용 Rust 실험 테스트에 회귀 사례를 추가한다. 같은 테스트 소스와 기존 lock을 사용하는 원본 작업공간에서 기존 대조 사례와 문제 사례를 네 구성으로 실행한다.
2. 새 월드와 이미 Step한 월드의 '삽입 시 접촉' 사례를 Release와 debug assertion을 켠 빌드에서 실행한다. 활성 집합·접촉 연결 실패가 발생하는 조건을 기록한다.
3. 원본을 수정하지 않고 `dt=0` 대안을 같은 회귀 사례로 검증한다. 원본 기본 경로와 대안의 호출 방식·결과를 구분하며 다음 Step의 원래 시간 간격 유지도 확인한다.
4. 위 구현 방식 결정 기준에 따라 대안 또는 패치 경로를 선택하고 근거를 기록한다. 패치가 필요하면 활성 상태 등록 시점을 포함한 개조 후보안을 먼저 확정한다.
5. 패치 경로를 선택한 경우에만 공통 패치를 작성하고 원본의 별도 사본에 적용한다. 압축 파일의 경로가 작업공간을 벗어나거나 원본 체크섬이 다르거나 패치가 적용되지 않으면 중단한다.
6. 빌드·검증에서 원본 기본 경로, `dt=0` 대안, 패치 적용 경로를 명시적으로 구분한다. 적용한 경로·패키지·lock·출력을 manifest에 기록하고 다른 경로로 조용히 대체하지 않는다. 패치 적용 경로에서는 실제 의존성 경로와 수정본 체크섬을 검증한다.
7. 채택 후보 경로의 네 구성 Release DLL과 기존 Rust·C 소비 검증을 실행한다. 원본 대안 검증에서 이미 통과한 회귀 사례는 구현이나 빌드 구성이 바뀐 경우 다시 실행하며, 패치 경로에서는 Release·debug assertion 빌드의 회귀 사례를 모두 실행한다. 의존성 준비 이후에는 `--locked --offline`과 기본 feature·unwind panic 경계를 유지한다. 원본 문제 사례의 실패는 비교 근거로 보존하고 채택 후보의 실패를 무시하지 않는다.
8. 빌드·의존성 변경에 대한 저장소 검증 기준에 따라 본체 Release 빌드와 전체 .NET 회귀 검증을 실행한다. 일반 dotnet 명령에 Rust 빌드를 연결하지 않는다. 장시간 테스트는 [AGENTS](../../../../../AGENTS.md)의 사전 확인 규칙을 따른다.
9. 새 작업 디렉터리에서 선택한 경로를 다시 준비·빌드하여 수동 캐시 수정에 의존하지 않는지 확인한다. 패치 경로는 보존한 원본과 패치로 수정 소스를 재생성한다. 검증한 입력·lock·feature·도구와 실제 산출물 해시를 기록하며, 서로 다른 경로에서 DLL 바이트가 같다는 보장까지 임의로 확대하지 않는다.

현재 실행 방법은 [네이티브 프로젝트 안내](../../README.md)를 따른다. 원본 비교는 `investigation/Cargo.toml`, 수정본 검증은 준비 스크립트가 생성한 별도 manifest를 사용한다. 원본 lock과 수정본 lock의 차이는 네 Rapier 항목의 registry source·checksum 제거뿐이어야 한다.

## 검증 위치와 통과 기준

회귀 테스트는 기존 공용 Rust 실험 소스인 `investigation/src/lib.rs`의 `tests` 모듈에 추가하여 네 구성에서 같은 사례를 실행한다. C 소비 검증은 기존 `investigation/tests/consumer.c`를 유지한다. 이 패키지의 문서 통합 구조에 따라 테스트 계획과 결과는 `docs/investigation`에서 함께 관리한다.

상세 사례·통과 기준은 [0단계 검증 계획](../../investigation/02.%20Plans.md)의 '후속 갱신 경로 비교 검증' 절을 기준으로 한다. 이 문서에는 구현 방식 선택과 적용 순서를 두고, 검증표를 중복 관리하지 않는다. [실행 결과](../../investigation/03.%20Results.md)는 실제 실행 후에만 추가한다.

채택 후보는 네 구성에서 Release·debug assertion 회귀 검증, 기존 Rust·C 소비·ABI 검증과 저장소 통합 검증을 통과해야 한다. 원본 기본 경로의 실패는 비교 근거로 보존한다. 원본 대안이 통과해도 원본 DetectCollisions 자체의 문제가 해결되었다고 표시하지 않는다.

기존 upstream 전체 테스트, 선택 feature와 다른 플랫폼까지 검증한 것으로 표현하지 않는다. 추가 실패나 계약 차이가 발견되면 완료로 표시하지 않고 사례와 원인 분석을 기록한다.

## 결과 기록과 완료 기준

실행 결과는 [0단계 결과](../../investigation/03.%20Results.md)에 원본 기본 경로·dt=0 대안·패치 적용 경로별로 구분해 추가한다. 원본 실패 표와 최초 로그는 보존하며 다음을 기록한다.

- 비교·선택한 경로와 채택·미채택 이유, 구성·버전·lock·원본 출처이다. 패치 경로에는 패치 식별 정보를 추가하고 무수정 대안에는 패치 미적용을 명시한다.
- 실제 실행한 명령, 도구 버전, feature, 종료 코드와 통과·실패·무시 건수이다.
- 최소 재현의 높이·속도·질량·수면 상태와 각 회귀 사례의 관찰 결과이다.
- DLL·내보내기·출처 manifest와 실제 사용한 의존성 경로의 검증 근거이다. 패치 경로에는 원본에서 수정 소스를 생성한 근거를 포함한다.
- 반복 검사 비용, 남은 실패와 아직 검증하지 않은 범위이다.

네 구성에서 선택한 경로의 검증과 저장소 통합 검증이 통과해야 연결 계층의 갱신 계약 충족을 기록한다. 원본 기본 경로의 문제, 무수정 대안의 대응, 원본 패치의 해결 여부는 각각 구분한다. [Revisions](../Revisions.md)에는 상태와 해결방안 요약만 갱신하고 상세 결과는 링크로 연결한다. [라이선스 고지](../../Third%20Party%20Notices.md)와 패키지·설계 문서에는 실제 채택 경로와 패치 적용 여부를 반영한다.

검증 결과를 보고한 뒤 사용자 확인을 받아 1단계로 넘어간다. 이 계획의 완료는 C# 제품 API나 전체 PhysicalSpace API Coverage의 완료를 뜻하지 않는다.

## 공식 수정 버전으로의 전환

공식 수정이 포함된 배포 버전을 채택할 때는 새 버전의 원본·의존성·라이선스를 확인하고 원본 기본 경로로 같은 회귀 사례를 실행한다. 네 구성과 연결·통합 검증이 통과하면, 패치 경로를 사용한 경우 로컬 패치와 Cargo 경로 대체를 활성 빌드에서 제거한다. dt=0 대안을 사용한 경우에는 원본 기본 경로가 같은 계약을 충족하는지 확인한 뒤 연결 계층의 갱신 경로를 전환한다. 새로운 lock과 출처를 기록하고, 이 문제의 계획·비교·검증 이력은 보존한다.

공식 수정 버전이라는 이유만으로 해결을 가정하지 않는다. 업스트림 이슈에 댓글을 추가하거나 PR을 보내는 작업은 별도 요청에 따른다.
