# 0단계 네이티브 검증 계획

Rapier 0.36.1·Parry 0.31.1을 별도 Rust 연결 DLL에서 사용할 수 있는지 확인한다. 원본과 무수정 dt=0 대안, Rapier 로컬 수정본 0.36.1-r1을 구분하여 검증한다. 제품 API 구현과 전체 API Coverage 완료 검증은 다음 단계의 범위이다.

충돌 검사 이후 운동 갱신 문제의 구현 방식 선택·적용 순서는 [개조·검증 계획](../revisions/0.36.1-r1/Plan.md)에, 상세 비교 사례는 아래 '후속 갱신 경로 비교 검증' 절에 둔다. 공통 테스트 소스와 준비·검증 스크립트를 구현했으며 실제 비교 결과는 [Results](03.%20Results.md)에 기록한다.

## 구성

- Windows x64, Rust/Cargo 1.99.1, 기존 MSVC, Release와 unwind panic 경계이다.
- 2D/3D × f32/f64를 서로 다른 DLL로 빌드한다.
- 원본 기본 feature를 사용한다. 2D의 기본 block-solver를 포함하며 parallel·FEM·simd8·강화 결정론 등은 별도 활성화하지 않는다.
- 전체 Cargo 의존성을 정확한 lock과 체크섬으로 고정하고 다운로드 이후에는 offline으로 빌드한다.
- Rust 직접 사례와 C 소비 사례이며 UniTest 랜덤 상태 전이 테스트가 아니다.

## 후속 갱신 경로 비교 검증

공용 Rust 사례는 `investigation/src/lib.rs`의 `tests` 모듈에서 2D/3D × f32/f64 네 구성이 공유한다. `collision_` 접두사의 13개 회귀와 기존 연결·ABI 사례 6개를 구분한다. C 소비 검증은 `investigation/tests/consumer.c`를 사용하며 `ue_probe_run` 내부에서도 새 강체의 검사 후 Step을 실행한다. 상세 계획과 결과는 이 `docs/investigation` 폴더에 함께 둔다.

비교 경로는 원본의 기본 DetectCollisions, 원본 PhysicsPipeline의 `dt=0` 대안, 패치 적용 PhysicsWorld이다. 같은 초기 상태와 사용자 조작을 사용한다. 테스트 환경 변수 `UE_PROBE_TEST_COLLISION_PATH`의 `world`는 사용하는 의존성의 PhysicsWorld를, `zero-step`은 직접 PhysicsPipeline 호출을 선택한다. 패치 여부는 환경 변수가 아닌 manifest·lock·실제 의존성 경로로 판정한다.

회귀 사례는 네 구성에서 Release와 debug assertion을 켠 빌드로 각각 실행한다. 수치 비교는 정밀도에 맞는 허용 오차를 명시한다. 원본 기본 경로의 알려진 실패는 비교 근거이며, 대안이나 패치 경로의 실패를 무시하거나 예상 성공으로 처리하지 않는다. 원본 대안이 통과한 결과와 원본 DetectCollisions 자체의 수정 여부도 구분한다.

| 사례 | 확인할 동작과 통과 기준 |
| --- | --- |
| 최소 재현 | 원본에서 기존 DetectCollisions → Step 문제가 재현됨. 대안 또는 패치 경로는 Step만 실행한 대조 사례와 검사 후 Step 사례 모두 높이 감소·음의 Y 속도를 보이며 수치가 허용 오차 안에서 일치함 |
| 원래 시간 간격 유지 | `dt=0` 대안은 복사한 설정의 시간 간격만 0으로 사용하며 월드의 설정은 보존함. 다음 정상 Step이 원래 시간 간격으로 운동하고, 반복 검사나 오류 이후에도 설정이 바뀌지 않음 |
| 반복 충돌 검사 | 검사 512회 동안 자세·속도·원래 dt와 깨어 있는 상태가 유지되며, 이어지는 Step이 원래 dt로 정상 운동함 |
| 검사 후 사용자 편집 | 위치를 바꾸고 다시 검사하면 콜라이더 위치와 접촉·겹침이 갱신됨. 변경을 다시 편집하는 순서에서도 #815·#662 유형의 변경 추적 문제가 재발하지 않음 |
| 콜라이더 변경 | 이미 존재하는 강체에 연결된 콜라이더의 형상·질량·부모 변경을 검사와 다음 Step이 반영함 |
| 실행 중 삽입 | 한 번 이상 Step한 월드에 새 동적 강체를 추가한 뒤 검사해도 다음 Step에서 새 강체가 정상 운동함 |
| 삽입 시 접촉 | 새 월드와 한 번 이상 Step한 월드에서 각각 새 동적 강체를 다른 강체와 접촉한 상태로 추가한 뒤 검사와 Step을 실행함. 새 강체 두 개가 서로 접촉하는 경우를 포함함. debug assertion 실패 없이 활성 집합 등록과 접촉 연결이 이루어지고, 접촉한 동적 강체들이 같은 island로 잠들고 깨어남 |
| 상태 전환 | 처음부터 수면인 강체, 수면·깨우기, 활성화·비활성화, 고정·운동학적·동적 유형 전환을 검사함. 첫 Step 전과 정상 Step 후의 수동 sleep을 각각 Step만 실행한 대조 사례와 비교함 |
| 조인트 연동 | fixed impulse joint가 연결된 강체의 위치·유형·활성 상태 변경 후 검사와 Step으로 제약·활성 상태를 갱신함. multibody joint의 상세 전이는 이번 사례에 포함하지 않음 |
| 제거·재삽입 | 100회 반복하여 오래된 핸들 거부, 남은 강체 1개·활성 강체 1개, 제거 후 활성 강체 0개와 정상 운동을 확인함. 내부 변경 버퍼 용량은 직접 검사하지 않음 |
| 이벤트 | 상태가 바뀌지 않은 반복 검사에서 Started/Stopped를 중복 발생시키지 않으며 실제 겹침 전이는 보존함 |
| 기존 연결 검증 | 기존 Rust 사례와 추가 회귀 사례, 네 구성 C 소비 검증 204개 assertion, 내보내기 6개 심볼·ABI·오류·진단·콜백 검증이 통과함 |
| 저장소 통합 | 본체 Release 빌드와 전체 .NET 테스트가 통과하고 일반 dotnet 명령이 Rust를 요구하지 않음 |
| 재현성과 실패 처리 | 새 작업 디렉터리의 준비·빌드가 성공함. 잘못된 원본 체크섬·잘못된 의존성 경로는 빌드 전에 거부됨. 패치 경로에서는 적용 불가능한 패치도 거부됨 |

수치 비교는 f32 `1e-5 × (1 + |기대값|)`, f64 `1e-10 × (1 + |기대값|)` 허용 오차를 사용한다. 콜백 panic 사례는 검사 중 예외 후 원래 dt 보존을 확인하며 부분 갱신 월드의 재사용 가능성까지 보장하지 않는다. 접촉 수면 사례는 중력 0에서 두 Ball을 접촉시키고 300 Step 후 함께 수면·깨우기를 확인한다. 이벤트 사례는 세 번 왕복 편집의 Started/Stopped 각 1회와 반복 검사 중복 0회를 확인한다.

원본 비교 명령은 다음과 같다. `world`/`zero-step` 각각 Release와 `--release`를 제외한 Debug에서 실행한다. 원본 비교의 실패는 의도적으로 기록하되 수정본 실패를 성공으로 처리하지 않는다.

```powershell
. ./packages/rapier/scripts/EnterBuildEnvironment.ps1
$env:UE_PROBE_TEST_COLLISION_PATH = 'world'
cargo test --manifest-path packages/rapier/investigation/Cargo.toml --workspace --release --locked --offline --no-fail-fast --target x86_64-pc-windows-msvc --target-dir packages/rapier/obj/collision-update/target collision_ -- --nocapture --test-threads=1
./packages/rapier/scripts/Investigate.ps1 -OutputDirectory packages/rapier/obj/collision-update/new-run
```

새 출력 경로를 사용해야 한다. 수정본 스크립트는 전체 19개 Release 사례와 13개 Debug 회귀를 구성별로 실행하고, C assertion 51개·내보내기 6개를 구성별로 확인한다. 원본 8개 아카이브·소스, 패치 적용 후 파일 전체, Cargo 경로와 lock을 검증한다. 별도 새 소스·target 디렉터리의 Release 빌드와 C 소비로 재생성을 확인한다. 복사한 입력의 체크섬 오류, 재적용 불가능한 패치, 원본 registry 또는 다른 로컬 소스로의 잘못된 해석은 빌드 전에 거부해야 한다. 실제 실행 명령·관찰값·종료 코드·통과 및 실패 건수는 [결과](03.%20Results.md)에 기록한다.

## 패키지 경로 빌드 검증

폴더 통합처럼 동작을 바꾸지 않는 재배치는 테스트를 다시 실행하지 않고 빌드로 확인한다. `packages/rapier`에서 환경 설정 스크립트가 기존 Rust/Cargo를 찾는지 확인하고, 별도 `obj/relocation-check/target`에 네 구성의 Release DLL을 빌드한다. 본체 Release 빌드와 문서 상대 링크·이전 경로 잔존·obj의 Git 제외 상태도 확인한다. 최초 0단계 DLL·manifest·실행 로그는 그대로 보존한다.

## 범위의 한계

### 업스트림 이슈용 최소 재현

기존 연결 코드·C ABI·직접 Parry 의존성을 제외한 별도 Rust 테스트를 `obj/stage0/upstream-repro`에서 실행한다. 정확한 Rapier 0.36.1 네 패키지와 기본 feature를 사용한다. 높이 2의 새 동적 Ball 강체에 중력 -9.81과 시간 간격 1/60초를 설정하고 Step을 10번 실행한다. 대조 사례와 첫 Step 전에 DetectCollisions를 한 번 호출하는 사례를 별도 테스트로 비교한다. 두 경우 모두 높이 감소와 음의 Y 속도를 기대하며, 실제 높이·속도·질량·수면 상태와 테스트 종료 코드를 보고한다. 결과와 재현 소스는 등록 이슈에 보존한다.

### 제품 구현

실험 함수 내부에서 생성한 월드·도형은 Rust 수명으로 정리한다. 제품용 월드 핸들 저장소, 모든 도형·필터·이벤트·폐기 계약과 실제 물리 훅은 아직 구현하지 않는다. C# 객체 API, 관리 예외 수집, IL2CPP 실행, f64 공개 수학 타입과 선택 feature 조합은 이번 실험의 검증 완료 항목으로 표시하지 않는다.

실제 원본 기능과 문서 계약이 충돌하면 그 항목을 보고하고 확인받는다. 0단계 결과를 보고한 후 사용자 확인을 받아 1단계로 넘어간다.
