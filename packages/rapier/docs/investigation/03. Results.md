# 0단계 네이티브 검증 결과

2026-11-23에 [검증 계획](02.%20Plans.md)을 실행했다. 최초 원본 검증에서는 충돌 검사 이후 운동 갱신이 실패했다. 후속 로컬 수정본 0.36.1-r1은 정해진 0단계 회귀·연결·저장소 검증을 통과했다. 아래 최초 원본 결과를 보존하고 후반의 '0.36.1-r1 비교·검증 결과'에 원본·대안·수정본을 구분한다. 제품 C# API와 1단계 구현 완료를 뜻하지 않는다.

도구는 승인된 최소 프로필로 `packages/rapier/obj/tools`에 설치했으며 시스템 PATH를 변경하지 않았다. 기존 MSVC를 사용했고 CMake·바인딩 생성기는 사용하지 않았다. 실제 배포 crate의 출판 커밋은 Rapier `475caa3ff4646fd9a796b67d14116256f4962bc7`, Parry `3383f51cbbe9af70565427e7a66c605e1557c1fc`이며 모두 `dirty: true`이다. 이는 출판자의 메타데이터이다. 비교 기준 Rapier 태그의 커밋과 같은 소스라고 가정하지 않고 Cargo.lock의 체크섬으로 실제 배포본을 고정했다.

`VerifyDependencies.ps1`은 8개 .crate의 SHA-256을 Cargo.lock과 대조하고, 압축 파일의 일반 파일 2,631개를 실제 빌드 입력과 바이트 해시로 비교했다. 모두 일치했다. 패키지별 체크섬·커밋·파일 수는 [의존성 manifest](../../obj/stage0/dependencies.json), DLL 체크섬은 [패키지 기록](../../../README.md)과 [DLL manifest](../../obj/stage0/binaries.json)에 있다. manifest와 원본 실행 로그는 비추적 검증 산출물이다.

원본 공개 구성 요소의 별도 크레이트 접근은 네 구성에서 컴파일했다. 원래 `SharedShape` 참조를 해제해도 복제 참조와 콜라이더가 유지됐다. 비동적 충돌 조합을 명시적으로 활성화한 두 독립 콜라이더에서 센서 겹침을 확인했다. Parry의 두 Ball 거리 결과는 2이며 결과 타입은 스칼라가 아닌 `ShapeDistance`이다. 제품용 연결에서는 distance·subshape1·subshape2를 함께 보존해야 한다.

C 소비자는 DLL 값을 복사해 기대값으로 쓰지 않고 C 헤더·컴파일러의 `sizeof`, `_Alignof`, `offsetof`로 기대 ABI를 구성했다. 15개 descriptor 필드 각각의 불일치, 잘못된 크기·null·시간 입력, 실패 시 출력 보존, 성공 시 진단 초기화, C 콜백·사용자 데이터와 실패 상태를 검증했다. Rust 측에서 진단의 스레드 분리도 확인했다. `options=0`은 실험 ABI의 추가 옵션 값이며 원본의 모든 feature를 조회·검증했다는 뜻이 아니다.

의도적인 panic 주입은 상태 코드 3으로 반환했고 다음 정상 호출이 성공했다. 로그의 `Stage 0 panic boundary test`는 이 검증의 예상 진단이다. `DetectCollisions` 회귀 테스트의 실패와 구분한다. panic 이후 임의의 제품 월드가 계속 유효하다는 계약까지 검증한 것은 아니다.

네 DLL은 Windows 시스템 DLL·UCRT와 `VCRUNTIME140.dll`에 의존한다. 이 PC에서 실제 로드에 성공했으며, 런타임이 없는 별도 PC의 설치·배포는 검증하지 않았다.

## 최초 원본 실패: 충돌 검사 이후 시뮬레이션

`investigate_step_after_collision_only_update`는 새 월드에 높이 2의 동적 강체와 반지름 0.5의 Ball 콜라이더를 넣고, 기본 중력·시간 간격으로 Step을 10번 실행한다. 비교 사례에는 첫 Step 직전에 `detect_collisions(&(), &())`를 한 번 추가한다. 질량은 양수이며 두 사례 모두 `sleeping=false`이다.

| 구성 | Step만 실행한 높이 / Y 속도 | DetectCollisions 후 Step 높이 / Y 속도 | 기대와 판정 |
| --- | --- | --- | --- |
| 2D f32 | 1.8603438 / -1.6349996 | 2 / 0 | 두 경로 모두 중력 운동을 해야 하나 후자는 정지, 실패 |
| 3D f32 | 1.8603438 / -1.6349996 | 2 / 0 | 동일 실패 |
| 2D f64 | 1.8603437499999997 / -1.635 | 2 / 0 | 동일 실패 |
| 3D f64 | 1.8603437499999997 / -1.635 | 2 / 0 | 동일 실패 |

실제 배포 소스에서 CollisionPipeline은 변경 강체 목록을 가져와 island 인자 없이 사용자 변경을 처리한 뒤 변경 플래그와 목록을 정리한다. PhysicsPipeline은 사용자 변경을 처리할 때 island를 갱신한다. 이 흐름이 처음 등록된 강체의 활성 island 등록을 놓치는 원인으로 추정된다. 이 기록은 위 재현 사례에 대한 분석이며 모든 관련 상태 전이의 원인을 확정한 것은 아니다.

최초 원본 검증 당시에는 원본 수정·버전 변경·보정 코드·요구 계약 축소를 적용하지 않았다. 실패 테스트를 제거하거나 무시하지 않았고 당시 `Investigate.ps1`도 독립 검증을 마친 뒤 실패를 반환했다. 요청서의 확인 조건에 따라 후속 대응을 보류한 뒤 수정 계획과 구현을 진행했다. 아래 후속 결과는 최초 실패와 구분한다.

## 0.36.1-r1 비교·검증 결과

### 비교 경로와 결과

공통 소스의 `collision_` 회귀 13개를 네 구성에서 비교했다. 원본은 기존 `investigation/Cargo.toml`·Cargo.lock을, 수정본은 원본 압축 파일과 공통 패치에서 생성한 별도 workspace를 사용했다. 모든 비교는 Windows x64, 기본 feature, Rust/Cargo 1.99.1, `--locked --offline`이다. 표의 건수는 네 구성 합계이며 원본과 대안의 Cargo 종료 코드는 101, 수정본은 0이다.

| 경로 | Release 회귀 | Debug 회귀 | 판정 |
| --- | --- | --- | --- |
| Rapier 원본 PhysicsWorld | 16 통과·36 실패 | 16 통과·36 실패 | 검사 후 운동·변경 반영·활성 집합 실패 재현 |
| Rapier 원본 PhysicsPipeline dt=0 | 48 통과·4 실패 | 48 통과·4 실패 | 초기 수면 전환 실패로 미채택 |
| Rapier 수정본 PhysicsWorld | 52 통과·0 실패 | 52 통과·0 실패 | 이번 13개 회귀 계약 통과 |

원본 Debug의 '이미 Step한 월드에 접촉 강체 삽입'에서는 `island_manager/manager.rs:141`의 `rb.is_fixed() || !rb.is_enabled() || rb.ids.active_island_id != u32::MAX` assertion이 실패했다. 새 월드·기존 월드 사례를 분리하여 한 실패가 다른 사례를 가리지 않도록 했다.

무수정 dt=0 대안은 보통의 낙하를 복구했지만, 새 강체에 `검사 → sleep() → 검사 → 첫 Step`을 실행하면 `sleeping=true`인 채로 한 번 이동했다. 대조 사례는 높이 2를 유지했고 대안은 f32 1.9982969, f64 1.9982968749999999였다. 수정본은 네 구성 모두 높이 2·수면 true를 유지했다. 정상 Step 이후 수동 수면과 처음부터 수면인 강체도 별도로 통과했다.

수정본의 원래 최소 재현은 Step만 실행한 대조군과 일치했다. f32 높이 1.8603438·Y 속도 -1.6349996, f64 높이 1.8603437499999997·Y 속도 -1.635였으며 모두 질량 양수·수면 false였다. 수정본은 persistent island 초기화를 정상 Step 전에 완료한다. 이것이 초기 수면 관찰의 island 식별자 갱신 순서와 관련된다는 분석을 지지하지만 업스트림 전체 상태 전이의 원인을 증명한 것은 아니다.

512회 검사 중 자세·속도·dt·깨어 있는 상태 보존, 다음 정상 운동, 접촉 강체의 같은 island와 공동 수면·깨우기, 형상·질량·부모 변경, 활성·유형 전환, fixed impulse joint 제약, 100회 제거·재삽입의 핸들·활성 수, Started/Stopped 중복 억제, 콜백 panic 후 원래 dt 보존을 통과했다. 반복 검사를 포함한 13개 회귀 실행 시간은 구성별 Release 0.00초, Debug 0.02~0.03초로 실행기에 표시됐다. 개별 호출 성능 벤치마크나 내부 변경 버퍼 용량 검사는 아니다.

### 중간 실패와 한계

초기 회귀 코드의 값·참조 API 차이로 컴파일 오류가 발생해 수정했다([초기 로그](../../obj/collision-update/upstream-release.log)). 원본 대안의 수면 전환 실패는 초기 수면·정상 Step 이후 수동 수면·첫 Step 이전 수동 수면으로 분리하여 확인했고, 마지막 실패를 제거하지 않고 최종 13개 회귀에 남겼다. 준비 스크립트의 첫 실행에서는 Windows Git 설정이 수정 파일을 CRLF로 바꾸어 해시 검사가 중단했다. `core.autocrlf=false`를 적용한 뒤 LF 파일 해시 검사와 전체 수정본 검증을 통과했다. 중간 출력은 `obj/collision-update/verified-r1`에 보존했다.

일반 CollisionPipeline 직접 호출은 수정하지 않았다. 조인트 검증은 fixed impulse joint이며 multibody joint의 상세 전이, soft body, 선택 feature, 다른 플랫폼, 전체 upstream 테스트는 포함하지 않는다. 콜백 panic 사례는 dt 보존만 확인하며 부분 갱신 월드 복구를 보장하지 않는다. 이번 완료 범위는 0단계의 정해진 직접 사례·C ABI·통합 검증이며 1단계 진행은 결과 보고 후 별도 확인한다.

## 검증하지 않은 범위

제품용 월드 핸들 저장소와 전체 도형·필터·이벤트·Dispose 계약, 실제 물리 훅, C# DllImport·GCHandle·관리 예외 처리, IL2CPP, 제품 DLL 출력 복사, 선택 feature, Windows x64 이외 플랫폼은 미검증이다. f64는 네이티브 실험만 수행했으며 공개 C# 수학 타입의 정의 위치는 아직 결정하지 않았다. 원본 테스트 전체를 실행한 결과가 아니라 별도 연결 프로젝트의 직접 사례와 ABI 소비 검증이다.

[네이티브 대응 조사](../../../../docs/02.%20UniEngine/01-Infrastructure/03-M.4-PhysicalSpace/Native%20Coverage.md)는 원본 멤버와 실제 실험 진입점의 대응을 기록한다. C# 멤버는 모두 미구현이며 API Coverage 전체 완료를 뜻하지 않는다.
